# Группа проекта и автоматическая организация задач

Дата: 03.10.2026. Статус: согласованное направление, спецификация первого этапа. Реализация последующих этапов ещё не выполнена.

## Цель

В каждом проекте одна рабочая группа. Каждая задача имеет отдельную тему. Команда автоматически готовит постановку и черновик графа; владелец получает готовый план для проверки, ручной настройки и запуска.

## Зафиксированные правила

- Создание задачи и подготовка плана не дают разрешения выполнять задачу. Исполнение начинается после «Согласовать и запустить».
- Ручной выбор шаблона и настройка состава сохраняются. Автоматика не перезаписывает ручной план.
- Граф определяет исполнителей, зависимости, результаты и приёмку. Чат служит обсуждению; сообщение само по себе не закрывает этап и не разрешает следующий.
- Обязательные рабочие слоты плана материализуются в существующие строки subtasks. Дочерние карточки не заменяют их: на слотах остаются состояние, прогресс и артефакты.
- В зависимостях с передачей результата требуется явный контракт артефакта и его приёмки. Завершение предшественника без документа не считается передачей документа.
- Участники знают состав, обязанности, зависимости, текущую ревизию плана и адрес своей темы.
- Новый участник разрешён для конкретного блока, устранимого его компетенцией: причина, ожидаемый результат и связь с заблокированным узлом обязательны. Общего «усилить команду» недостаточно.
- Владелец разрешил сначала автоматическое подключение при таких блоках без дополнительного согласования. Это не разрешение менять цель, границы задачи или права доступа. Изменение фиксируется в графе и теме.
- Критик виден участником графа и темы. Последовательный возврат направляется первому этапу, требующему исправления, с повтором зависимых этапов; независимые параллельные ветки могут получать отдельные стрелки.

## Предлагаемая модель следующего этапа

Это проектные решения для реализации, а не уже существующий API.

- Группа связана с project_id; уникальность обеспечивается БД, а не названием.
- Тема связана с группой и task_id; одна тема на карточку независимо от числа ревизий плана. Дочерняя карточка получает свою тему и ссылку на родительскую.
- Общая тема проекта хранит общие договорённости. Рабочая история и контекст модели разделяются по теме и роли, чтобы задачи не смешивались.
- Членство группы даёт список участников проекта; состав команды каждой темы берётся из её плана. Получение доступа проверяется отдельно от членства.
- Новые сообщения и документы доступны только тем, кто имеет доступ к соответствующей задаче. Упоминание не повышает права.
- Подготовка хранит состояние, версию входа и устойчивый идентификатор операции: повтор события или перезапуск не создаёт вторую тему, план либо уведомление.
- При изменении постановки подготовка старой версии не может подменить новую. Утверждённый план не пересобирается из-за очередной синхронизации Linear.

## Жизненный цикл

Новая задача → создание/поиск темы → проверка постановки → уточнение при необходимости → черновик графа → уведомление владельцу → согласование конкретной ревизии → материализация слотов и запуск → работа/блок/доработка → результат.

При ошибке подготовки задача остаётся доступной, отображается причина и возможность повторить подготовку. Исполнители не стартуют. Согласование устаревшей ревизии отклоняется с показом актуальной.

Чатовый ответ и выполнение слота не должны порождать два конкурирующих запуска, изменяющих один результат. Механизм доставки в активный запуск и ответа спящего участника выбирается на этапе 3 после проверки runtime; до этого обещать автоматическое пробуждение нельзя.

## Этапы и приёмка

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| 1. Правила и аудит | Этот документ | Основа отделена от отсутствующих механизмов; границы согласования явны |
| 2. Группы и темы | Модель БД, API, навигация iOS | Две задачи имеют разные темы в одной группе; повторные события не дают дублей; личные чаты работают |
| 3. Связь агентов | Инструменты и контекст темы в рабочих запусках | Адресат реально получает сообщение; нет смешения тем, повторного выполнения и бесконечной переписки |
| 4. Автоподготовка | Устойчивая очередь подготовки новых задач | Linear и локальная задача дают черновик; неполные данные дают вопрос; перезапуск продолжает работу без дублей |
| 5. Согласование | Граф и действие «Согласовать и запустить» | Запускается ровно утверждённая ревизия один раз; обязательные слоты создаются |
| 6. Живой граф | Присоединение и циклы доработки синхронизированы с темой | Причина присоединения видна; правильный получатель возврата; артефактная приёмка удерживает зависимости |
| 7. Полный сценарий | Отчёт и воспроизводимая проверка | Импорт → подготовка → согласование → блок → участник → Критик → исправление → результат; несколько задач и восстановление после перезапуска |

Перед включением автоматического исполнения необходимо отдельно проверить и развернуть локальную защиту запуска и цикл Критика. Возможность группы/тем не зависит от их предварительного деплоя.
