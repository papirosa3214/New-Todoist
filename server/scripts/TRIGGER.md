# Будильник TaskFlow

> Живёт здесь с 18.08.2026. Раньше лежал отдельным репозиторием в
> `~/Проекты/Инфраструктура/taskflow-trigger` — по наследству от
> `kaneo-trigger`. Причины переезда: служба намертво завязана на API и
> `AGENT-PROTOCOL.md` этого приложения и правится вместе с ним, а рядом
> (`server/scripts/mcp_server.py`) уже лежит такая же обвязка агента.
>
> Служба: `~/.config/systemd/user/taskflow-trigger.service`
> (`systemctl --user status|restart taskflow-trigger`).

Доска TaskFlow сама зовёт Клода в работу — то же назначение, что у
`kaneo-trigger`, но без вебхуков.

## Почему не вебхуки

В Kaneo другого пути не было: доска умеет только «выстрелить и забыть» —
пока приёмник лежит, события теряются безвозвратно.

У TaskFlow канал уже есть и он лучше:

- **WebSocket** (`ws://localhost:3001/ws?token=…`) — живой поток событий;
- **уведомления хранятся в базе** (`GET /api/notifications`) — то, что
  пришло, пока служба не работала, никуда не делось, и при старте она это
  добирает.

Побочная польза: пока сокет открыт, Клод показан **онлайн** на экране
агентов (`server/src/ws.ts` пишет `users.status` по открытию и закрытию
сокета) — отдельного пинга присутствия не нужно.

## Тумблер: за что берётся, а за что нет

Ровно один признак — **задача назначена на агента**. Это и есть явное
«за эту задачу браться можно», как метка «Можно двойнику» на доске Kaneo.
Не назначено — служба молчит, что бы в задаче ни происходило.

Дополнительно пропускаются: задачи не в статусе `active`, уже взятые в
работу (`in_progress`), ждущие проверки (`review`) и заблокированные
(`blocked`), а также собственные действия агента — иначе отчёт разбудил бы
сам себя.

### Одно исключение: комментарий по сданной задаче

Задача в `review` — тема закрытая, будильник за неё не берётся. Кроме
одного случая: **кто-то написал по ней комментарий**. Тогда исполнитель
всё-таки приходит, но в режиме ответа (`REPLY_ONLY`):

- без `claim` и без аренды — карточка остаётся на проверке у владельца;
- ровно один заход, свой промпт («ответь и уходи»), состояние менять
  запрещено;
- отказ захода тоже не меняет состояние — только записка в ленту.

Почему так, а не «вернуть задачу в работу»: забрать сданную работу обратно
агент не может по матрице переходов (`AGENT-PROTOCOL.md`) — это дверь
владельца. Просят доработать — исполнитель отвечает и просит вернуть
карточку в работу.

⚠️ Отвечаем только на **чужой** комментарий (`actor_id != assignee_id`).
Без этой проверки получается петля: ответ агента порождает уведомление
создателю задачи, оно приходит в соединение службы и будит агента снова.
Поймано живьём 27.08.2026 — DeepSeek ответил четыре раза подряд на один
вопрос.

## Как работает заход

1. `POST /api/tasks/:id/claim` — задача взята в работу.
2. Аренда продлевается службой каждые 4 минуты (`/heartbeat`), пока процесс
   жив: 15-минутный срок аренды не должен истекать под работающим Клодом.
3. `claude -p` с промптом: задача, шаги, лента, правила из `AGENT-PROTOCOL.md`.
4. Ушёл, не закрыв задачу, или превысил час — служба сама переводит задачу
   в `blocked` с объяснением. Задача никогда не остаётся молча висеть
   «в работе».

Принять задачу (`completed`) может только Максим — агент доводит до
`review`.

## Запуск

Служба пользовательская, без sudo:

```bash
systemctl --user daemon-reload
systemctl --user enable --now taskflow-trigger
systemctl --user status taskflow-trigger
```

Токен не лежит на диске и не печатается: юнит запускает скрипт через
`vault-run.py`, ключ `TASKFLOW_AGENT_TOKEN` попадает только в окружение
процесса.

Журнал: `~/.local/state/taskflow-trigger/trigger.log`, вывод самих заходов —
`task-<id>.log` там же.

## Сухой прогон

Проверить, что служба видит события и правильно решает, кого будить, не
запуская настоящего Клода и ничего не меняя в задачах:

```bash
TASKFLOW_TRIGGER_DRY=1 python3 ~/.claude/vault-run.py \
  --secret TASKFLOW_TOKEN=TASKFLOW_AGENT_TOKEN -- python3 trigger.py
```

Нужен, когда над той же задачей уже идёт живая сессия: два агента на одной
карточке — гарантированная каша.
