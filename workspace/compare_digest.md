# Собранные источники (даigest) — сравнение подходов к взаимодействию агентов внутри одного приложения

## S1. Anthropic Engineering, «How we built our multi-agent research system» (июнь 2025; https://www.anthropic.com/engineering/built-multi-agent-research-system)
- Архитектура: orchestrator-worker. Ведущий агент декомпозирует запрос, создаёт субагентов, работающих параллельно; собирает ответ.
- Результат: на их внутреннем research-eval multi-agent (Opus 4 lead + Sonnet 4 subagents) выиграл у single-agent Opus 4 на 90.2%. На BrowseComp 95% вариативности объясняется расходом токенов, из них 80% — самим расходом токенов.
- Стоимость: агенты тратят ~4x больше токенов, чем чат; multi-agent ~15x больше, чем чат. Выгодно только для дорогих задач.
- Инфраструктура: агенты состоятельны, ошибки накапливаются → нужны durable execution, checkpoints, retry, продолжение с места сбоя. Деплой через rainbow-деплой (две версии одновременно). Синхронное исполнение ведущего — узкое место: нельзя перенаправить субагента, один медленный блокирует всех.
- Оценка: гибкие проверки результата (rubric + LLM-as-judge), а не шагов; начинать с ~20 запросов; человеческая проверка обязательна.
- Подводные камни: LLM-агенты пока плохо координируют и делегируют в реальном времени; задачи с общим контекстом и множеством зависимостей (например, кодинг) — плохие кандидаты.
- Ограничение: вендорский блог одной компании, внутренние метрики, не рецензируемые.

## S2. A2A Protocol, «A2A and MCP: Detailed Comparison» (a2a-protocol.org; A2A v1.0 — под Linux Foundation)
- MCP — «вертикальный» слой: углубляет одного агента (инструменты, ресурсы), в том числе нескольких агентов под одной крышей одного приложения.
- A2A — «горизонтальный» слой: связывает агентов через границу (другая команда/организация): обнаружение (Agent Card), переговоры, делегирование, общая задача, обмен состоянием.
- Рекомендованная комбинация: A2A — координация, MCP внутри каждого агента — его инструменты.
- Ограничение: спецификация описывает внешнюю (кросс-организационную) координацию; внутри одного приложения она избыточна — хватает прямых вызовов и общего состояния.

## S3. Beam.ai, «6 Multi-Agent Orchestration Patterns That Actually Work in Production» (15.04.2026)
1. Orchestrator-worker — сценарий: кросс-функциональные процессы с ясной декомпозицией, единая точка ответственности; фейлы: оркестратор — единая точка отказа, переполнение контекста при 4+ исполнителях, стоимость растёт с числом вызовов.
2. Sequential pipeline — сценарий: документы, контракты, модерация, линейные зависимости; фейлы: каскадирование ошибок без отката, накладные расходы (~950 мс координации на 4 агентах; 29k против 10k токенов на 3 агентах).
3. Fan-out/fan-in — сценарий: 4+ независимых задач, сокращение времени до 75%; фейлы: лимиты API (15 агентов × 10 rps = 150 при лимите 100), квадратичные гонки на общем состоянии (N(N-1)/2), галлюцинирующая «консенсусная» агрегация.
4. Multi-agent debate / maker-checker — сценарий: комплаенс, контроль качества; фейлы: зацикливание (Microsoft советует не более 3 агентов в групповом чате), каскадирующая симофания, ложный консенсус.
5. Dynamic handoff — сценарий: заранее неизвестно, какой специалист нужен; фейлы: бесконечные циклы передачи, потеря контекста при каждой передаче, недетерминированная маршрутизация → невозможна отладка.
6. Adaptive planning — сценарий: открытые задачи без заранее известного пути; фейлы: медленная сходимость, уход цели (goal drift), непредсказуемая стоимость.
- Выбор: начинать с простейшего подходящего; Princeton NLP: один агент с теми же инструментами совпал или обошёл multi-agent на 64% задач; multi-agent даёт +2.1 п.п. точности примерно вдвое дороже.
- Ограничение: отраслевой блог вендора с собственным продуктом; часть цифр без ссылок на первичные работы.

## S4. Salesforce, «Agentforce Multi-Agent Orchestration» + admin.salesforce.com (продуктовая документация, GA с 15.06.2026)
- Модель: primary agent (Super Agent) — единая точка входа для пользователя, маршрутизирует задачи; secondary/connected subagents — специалисты со своим контекстом и данными, возвращают результат главному агенту.
- Внутри одной организации Salesforce; с сентября 2026 — «Orchestrate Other Agents (Beta)».
- Механика передачи: главный агент передаёт входные переменные connected-агенту, ждёт его рассуждения и логику, затем забирает управление.
- Ограничение: маркетинговая документация, независимых замеров эффекта нет.

## S5. CrewAI Docs, «Processes» (docs.crewai.com/en/concepts/processes)
- Два процесса: sequential (заранее заданный порядок, выход предыдущей задачи — контекст следующей) и hierarchical (менеджер-агент/manager_llm планирует, распределяет задачи, проверяет результаты).
- Процесс — явная настройка, а не протокол; агент остаётся частью того же приложения.
- Ограничение: документация фреймворка, без независимых замеров.

## S6. LangChain/LangGraph docs, «Persistence» (docs.langchain.com/oss/python/langgraph/durable-execution)
- Два механизма: checkpointer (снимки состояния графа в пределах thread: непрерывность диалога, human-in-the-loop, time travel, отказоустойчивость) и store (данные между тредами: предпочтения, факты, общее знание).
- Инфраструктурные требования: в проде — постоянный checkpointer (PostgresSaver); MemorySaver/SQLite — только для разработки; Agent Server берёт персистентность на себя; нужен контроль роста чекпойнтов (ретенция), thread_id ≤255 символов; для данных, пересекающих границы графов, — shared state via Store.
- Ограничение: документация вендора.

## S7. Microsoft Agent Framework 1.0 (GA 02–03.04.2026) объединил Semantic Kernel и AutoGen; AutoGen в maintenance mode (сообщество, форк AG2) (InfoQ 08.2026; blckalpaca; alicelabs)
- Оркестрационные паттерны AutoGen перенесены в графовый workflow: sequential, concurrent, handoff, group chat, Magentic-One.
- Build 2026: Agent Harness, Hosted Agents (GA) — среда исполнения и управления агентами, а не только библиотека; коннекторы к GitHub Copilot SDK и Claude Agent SDK с сохранением политик идентичности/безопасности/наблюдаемости; встроенные MCP-клиент и A2A-карты; декларативный YAML; телеметрия OpenTelemetry.
- Инфраструктурная цена: нужен рантайм (Agent Harness/Hosted Agents) для исполнения и политик — облачная платформа Azure, а не только библиотека.
- Ограничение: вторичные пересказы, первичные анонсы Microsoft не читал.

## S8. CopilotKit / AG-UI (dev.to 2026; GeekWire: привлечено $27 млн, 2026)
- AG-UI — протокол взаимодействия агента с человеком через приложение (поток событий от рантайма к фронтенду); в отличие от MCP (инструменты) и A2A (агенты).
- AgentCore Gateway — централизованное обнаружение/маршрутизация MCP-серверов и политики; AWS Bedrock AgentCore Runtime добавил поддержку AG-UI в марте 2026 (аутентификация и масштабирование).
- Для сценария «внутри одного приложения» AG-UI — слой представления, а не координации.

## S9. Статьи-сравнения фреймворков (cowork.ink «AG2 vs CrewAI vs LangGraph vs OpenAI Agents SDK» 2026; Splunk blog; pickaxe.co)
- LangGraph: явное состояние, граф, персистентность и переходы — сильнее всего для stateful workflow, но больше кода на старте.
- CrewAI: роли и «экипажи», быстрый прототип; self-host бесплатен, облако платно (50 выполнений/мес на бесплатном тарифе).
- OpenAI Agents SDK: самый быстрый прототип, handoffs, но привязка к моделям OpenAI (vendor lock-in).
- Microsoft Agent Framework: рекомендован для enterprise-стека Microsoft/.NET; миграция LangGraph ↔ CrewAI — 3–6 недель, на Agent Framework — 4–8 недель.
- Цены (pickaxe, оценка): AG2 $0; CrewAI $0 self-host…$25/мес облако; LangGraph $0…$39/мес с LangSmith; команда из 5 человек — LangSmith ~$195/мес только за места.
- Ограничение: блоги с элементами маркетинга, часть цифр — оценки автора; для выбора нужен пилот.

## S10. База знаний TaskFlow, урок «2026-10-07-agent-comms-chat-vs-step-pipeline.md»
- В TaskFlow канал `agents` практически мёртв; общение внутри ролей сводится к длинным служебным отпискам; инструкция «зови коллегу» не работает в изолированных сессиях.
- Эталонные системы: обмен сообщениями — часть работы (pub-sub/actor), сообщение будит следующего участника; у нас работа — конвейер шагов, переписка рядом.
- Ограничение: наблюдение о нашей системе, не о внешних практиках; полезно как требование к «живому» каналу координации.

## Итоговые рамки сравнения
Для каждого подхода фиксируем:
1) Сценарий применения (тип задачи, число агентов, границы доверия);
2) Требования к технической инфраструктуре (процесс/сервис, состояние, персистентность, наблюдаемость, изоляция, платформа);
3) Достигаемый результат (какая доля задач решается лучше, стоимость, предсказуемость, отлаживаемость).
