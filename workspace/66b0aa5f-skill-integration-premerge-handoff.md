# Перенос принятой правки в main из роли

## Когда так

Роль всегда работает в своём worktree (`git worktree add` в
`~/.local/state/taskflow-runs/worktrees/<taskId>`), а главная копия
`/home/maksim/Проекты/New-Todoist` принадлежит `maksim`. Ролевой запуск идёт под
`tfrole`, поэтому запись в файлы главной копии закрыта, а каталог `.git`
доступен (в нём ACL `user:tfrole:rwx`). Получается ловушка: сдвинуть
`refs/heads/main` можно, и это **неправильно**.

## Почему сдвигать указатель нельзя

1. Живое дерево main останется на старом содержимении, HEAD уйдёт вперёд —
   индекс разойдётся, `git status` покажет правки, которые никто не делал.
   Владельцу это выглядит как порча репозитория.
2. Сторож выкладки `server/scripts/deploy-when-idle.py` (таймер
   `taskflow-deploy-idle.timer`) работает по рабочему дереву: проверяет
   `git branch --show-current`, чистоту `server/` и `git rev-parse HEAD`.
   Указатель без файлов он пропустит.
3. Итог — видимость переноса без переноса. Ровно тот случай, который в карточке
   7efcc173 уже признан неверным.

## Рецепт

1. **Сверить, что переносить.** Принятая версия = коммит из fix_pack и отчёта
   QA. Проверить, что в main её нет:
   `git grep -l step_topic_progress main -- server/src` (пусто = не перенесено);
   живая база — только на чтение:
   `sqlite3 "file:/home/maksim/Проекты/New-Todoist/server/taskflow.db?mode=ro"
   "select count(*) from schema_migrations; select count(*) from sqlite_master
   where name='step_topic_progress';"`
2. **Проверить номер миграции.** Хвост `server/src/migrations.ts` на main:
   `git show main:server/src/migrations.ts | grep -nE "id: ['\"]" | tail`.
   Номера не зарезервированы за карточкой и заняты быстро — если номер в ветке
   роли пересекается с main, он обязан быть переименован **до** слияния. Учти:
   часть миграций в main записана compact-строкой без пробела после `{`, их не
   видно grep `'^ { id: "'` — ищи по `id: "15[0-9]`.
3. **Собрать слияние в своём worktree:**
   ```
   git checkout -b integration/<taskId-short>-ready main
   git merge --no-ff roles/<taskId> -m "merge(<task>): <что переносим>"
   ```
   Рабочая ветка роли остаётся нетронутой. Ветку слияния **не удалять** — на ней
   держится подготовленный перенос.
4. **Проверить совместное дерево** (все команды vitest с `--configLoader runner`,
   см. грабли):
   - `npx tsc --noEmit` в `server/`;
   - целевой набор `npx vitest run --configLoader runner test/<цель>.test.ts`;
   - соседние наборы, к которым правка прикасается;
   - миграция на копии живой базы:
     ```
     cp /home/maksim/Проекты/New-Todoist/server/taskflow.db /tmp/<task>/live-copy.db
     chmod u+w /tmp/<task>/live-copy.db
     DB_PATH=/tmp/<task>/live-copy.db npx tsx -e "import { runMigrations } from './src/migrations'; runMigrations();"
     ```
     Сравнить счётчики и `pragma_integrity_check` до/после, прогнать дважды
     (идемпотентность).
5. **Отделить «свой» регресс от чужого.** Любое падение соседнего набора
   проверяй на чистом main: `git checkout --detach main`, прогон, вернуться на
   свою ветку. Падает и там — оно существовало до переноса.
6. **Оформить передачу** — `workspace/<task>-integration-handoff.md`: что
   принято, что слито, SHA слияния, таблица проверок, причина невыполнения,
   одна команда владельца, что произойдёт после неё.
7. **Заблокировать шаг** (`taskflow_subtask_work`, `block_type=capability`), а не
   сдавать: перенос не выполнен. Спорное решение (сдвигать ли указатель) —
   спросить `taskflow_consult` и приложить ответ в отчёте.

## Команда владельца

Ветка слияния — потомок main, поэтому перенос строго перемоткой вперёд:

```
git -C /home/maksim/Проекты/New-Todoist merge --ff-only integration/<taskId-short>-ready
```

Перед отдачей проверить: `git merge-base --is-ancestor main integration/<taskId-short>-ready`.

Альтернатива, если владелец не хочет выполнять команды: ACL на рабочее дерево
главной копии, после чего перенос выполнит роль.

## Выкладку вручную не делать

Роли работают внутри процесса сервера: перезапуск оборвал бы ход твоей и чужих
ролей. За это отвечает сторож `deploy-when-idle.py` — после того как код попал в
main, он сам дождётся тишины (нет живых попыток за 10 минут, очередь чата
пуста, дважды с паузой 90 секунд), сделает резервную копию базы, прогонит
`tsc --noEmit`, соберёт `dist`, перезапустит сервис, проверит `/api/health` и
напишет владельцу в «Состояние системы». В отчёте писать раздельно: перенесено
в main — да/нет; выложено и проверено на живом сервисе — да/нет.

## Грабли

- **`node_modules` в worktree — симлинк на главную копию**, а она только для
  чтения. `npx vitest run` падает с `EACCES` на попытке создать
  `node_modules/.vite-temp/…`. Лечится флагом `--configLoader runner`.
- **Падать на соседних наборах — нормально**, если те же падения есть на чистом
  main. Не «чинить» чужое и не писать «регрессий нет» без прогона на чистом main.
- **Проверка «коммит поверх main» при сдаче может быть отключена** для шага
  интеграции — это не значит, что проверять совместное дерево не надо.
- **Не сдавать шаг, если перенос не выполнен.** Сдача читается как «перенесено».
- **Не переключать своё рабочее дерево на main надолго**: `--detach` для
  контрольного прогона безопасен, но надолго оставаться на main не нужно.
