# Разбор причины: сервер не пишет в тему задачи при смене состояния шага плана

Карточка `66b0aa5f-a974-4474-911e-77a39f815b79`, шаг `root_cause` (`fe271329`).
Роль: Архитектор. Вход: артефакт `bug_report` этапа analysis.
Дата среза кода: 17.10.2026, ветка `roles/66b0aa5f-...`, основа main `779ec8b5`.

## 1. Контекст

### Ожидаемое поведение
Каждая смена состояния шага плана (начал работу / сдан / заблокирован /
авто-перезапущен / брошен) даёт в теме задачи **ровно одну** строку от «Система»
с названием шага и новым состоянием. Строка идёт только в тему задачи, не в
общий чат. Повторный запрос с тем же состоянием, повторный запуск хода,
перезапуск сервера и восстановление слотов дублей не добавляют.

### Наблюдаемое
Строка не появляется вовсе. В ленте карточки (`task_events`) смены состояний
видны, в теме задачи (`chat_messages` по `chat_id` темы) — нет.

### Устройство двух хранилищ (проверено по коду)

**Лента карточки** — таблица `task_events`. Пишется единственной функцией
`logEvent()` (`server/src/agentState.ts:336-358`). Это INSERT в `task_events`
плюс побочный вызов `queueOrchestratorEvent` (вебхук оркестратору). Больше
`logEvent` **ничего не делает** — ни broadcast в чат, ни записи в `chat_messages`.

**Тема задачи** — таблица `chat_messages`, где `chat_id` указывает на строку
`chats` с `task_id = <задача>` и `parent_chat_id IS NOT NULL` (тема создаётся
`ensurePlanTopic()`, `server/src/lib/projectTopics.ts:20`).

**Это две разные таблицы.** Между ними нет ни триггера, ни подписки, ни
вызова. Отсюда и причина.

### Где меняется состояние шага

`UPDATE subtasks SET agent_state = …` встречается в **18 местах** (проверено
`grep -rn "UPDATE subtasks SET agent_state"`):

| Файл | Что делает |
|---|---|
| `routes/subtasks.ts:522, 868` | сдача/отпускание шага агентом и владельцем |
| `routes/subtask-artifacts.ts:121, 164` | приём и отзыв артефакта |
| `runtime/planSubtaskAdmission.ts:252` | старт шага (в т.ч. автостарт) |
| `runtime/planSubtaskAdmission.ts:265, 435, 455, 510, 594, 629` | сброс при неудаче/обрыве |
| `runtime/planSubtaskAdmission.ts:473, 576` | автоблок по числу обрывов |
| `runtime/stalledStepWatcher.ts:187, 212` | сторож зависших: перезапуск / блок |
| `runtime/planReviewLifecycle.ts:110, 117, 286` | маршрут после ревью |
| `runtime/planMutations.ts:409, 451` | блок по зависимости, сброс плана |
| `runtime/slotRestart.ts:46` | перезапуск слота владельцем |
| `agentState.ts:330` (`releaseSubtaskWork`) | снятие работы со всех шагов задачи |

**Ни одно из этих мест не пишет в `chat_messages`.** Часть зовёт `logEvent`
(это попадает в ленту), часть не зовёт ничего.

### Почему «просто добавить вызов в logEvent» — не решение
1. `logEvent` пишет в журнал, а не в тему: придётся либо научить его писать в
   чат (тогда **каждое** событие, включая `unreachable_role`, `rule_superseded`,
   `task:archived`, попадёт в тему задачи — шум), либо фильтровать по виду
   события (это утечка знания о шагах в общий журнал).
2. Значительная часть мест вообще не зовёт `logEvent` (`planSubtaskAdmission:265`,
   `stalledStepWatcher:187`, `slotRestart:46`, `releaseSubtaskWork`,
   `planMutations:451`). Навесить вызов на `logEvent` их не покроет — придётся
   править 18 мест точечно, и каждое новое место забудет.
3. `releaseSubtaskWork` одним UPDATE гасит сразу много шагов задачи — при
   вызове из него наивная реализация даст лавину строк.

## 2. Варианты

### Вариант A. Правка во всех 18 местах
Вызов общей функции в каждом месте смены состояния.
- Плюс: явно, читаемо, легко отлаживать.
- Минус: 18 точек правки в горячем коде запуска; каждое новое место состояния
  (а их добавление продолжается) снова про него забудет. Регрессия
  высоковероятна и не будет поймана компилятором.

### Вариант B. Триггер SQLite на `subtasks` + очередь строк (рекомендую)
Триггер `AFTER UPDATE OF agent_state, done ON subtasks WHEN …` пишет строку в
новую таблицу-очередь `step_topic_progress`; отдельный проход (в существующем
цикле `scheduler.ts`) переносит строки в `chat_messages`.
- Плюс: **одна** точка правки, новая смена состояния попадает в тему
  автоматически; идемпотентность обеспечивается уникальным индексом в БД, а не
  дисциплиной вызова; ровно тот приём уже применён в проекте дважды —
  `review_history_state AFTER UPDATE OF agent_state ON tasks`
  (`lib/reviewHistory.ts:21`) и `enqueue_new_task_preparation AFTER INSERT ON
  tasks` (`migrations.ts:3115`). Оба работают на живых данных.
- Минус: нужен проход-разносчик; строка может прийти в тему с небольшой задержкой
  (цикл планировщика), а не в тот же такт смены состояния.

### Вариант C. Читать журнал `task_events` и дописывать в тему постфактум
Фоновый проход читает новые `subtask_started` / `subtask_review` /
`subtask_released` / `stalled_step_auto_restart` и дописывает строки.
- Плюс: почти не трогает код.
- Минус: **не проходит критерий приёмки.** Пропущены «брошен», «авто-перезапуск
  без старта», смены, сделанные в обход `logEvent`, — а по срезу аналитика
  именно они заметны. Журнал не полон, восстановить из него нечего.

## 3. Решение

**Вариант B — триггер на `subtasks` плюс очередь `step_topic_progress`.**

### Ключ идемпотентности
`(subtask_id, new_state, attempt_key)`, где `attempt_key` =
`current_attempt_id`, а при NULL — `cycle:<admission_cycle>`.
Готовая реализация этого ключа уже есть в проекте: `attemptKeyFor()` в
`runtime/stalledStepWatcher.ts:176-181`, с тем же обоснованием
(«повторный тик не заведёт второе сообщение»).

Почему именно так:
- повторный запуск хода → новый `attempt_id` → **новая** строка (это разные
  попытки, дублем не является);
- перезапуск сервера и восстановление слотов (`recoverInterruptedPlanSubtasks`,
  `stalledStepWatcher`) не меняют состояние на новое → **строка не
  добавляется**;
- повторный запрос с тем же состоянием → `agent_state` не меняется → триггер с
  условием `NEW.agent_state IS NOT OLD.agent_state` не срабатывает.

Уникальный индекс `UNIQUE(subtask_id, new_state, attempt_key)` делает
идемпотентность свойством базы, а не аккуратностью вызова: повторный тик
планировщика или повторный UPDATE просто не вставят вторую строку.

### Тексты строк
По образцу `returnExpiredQuestion()` (`runtime/roleMessageWait.ts:214-239`) —
это ближайший рабочий образец служебной строки в теме: `from_user_id =
'taskflow_system'`, `channel='chat'`, `message_type='system'`, `chat_id` темы,
`task_id` задачи. Тот же системный пользователь уже используется в
`lib/kbTriageWatcher.ts:52`.

| Новое состояние | Текст строки |
|---|---|
| `in_progress` | `▶️ «<название шага>»: @<роль> начал работу` |
| `blocked` | `⛔ «<название шага>»: @<роль> — шаг заблокирован (<причина>)` |
| `done` (сдача) | `✅ «<название шага>»: @<роль> сдал результат` |
| авто-перезапуск | `🔁 «<название шага>»: поток остановился, сервер перезапускает попытку (<n> из <m>)` |
| брошен | `🛑 «<название шага>»: шаг брошен (<причина>)` |
| снятие `in_progress` без сдачи (NULL) | `⏸ «<название шага>»: работа снята без сдачи` |

Оговорка по объёму: `releaseSubtaskWork` гасит много шагов задачи одним
запросом. Чтобы тема не наполнялась лавиной, в триггере для перехода в NULL
оставляем только переходы `in_progress → NULL` (то есть сняли именно работу, а
не «шаг и так был свободен»); массовое снятие при закрытии задачи порождает
ноль строк. Это осознанное усечение: владельцу важнее «шаг в работе перестал
работать», чем перечисление всех свободных шагов закрываемой карточки.

### Границы файлов реализации
- **новый** `server/src/lib/stepTopicProgress.ts` — тексты, сборка ключа,
  `insertTopicProgressLine()`, проверка закрытой темы;
- **правка** `server/src/migrations.ts` (запись в конец списка) — таблица
  `step_topic_progress` + уникальный индекс + триггер;
- **правка** `server/src/runtime/scheduler.ts` — один вызов разносчика в
  существующем цикле;
- **правка** `server/src/index.ts` (или `db.ts` рядом с
  `installReviewHistory()`) — установка схемы при старте, по образцу
  `reviewHistory.ts`.

Что НЕ трогаем: `runtime/planSubtaskAdmission.ts`,
`runtime/stalledStepWatcher.ts`, `routes/subtasks.ts`, `agentState.ts`,
`lib/projectTopics.ts` — все 18 мест смены состояния остаются как есть.

## 4. Последствия

### Что становится лучше
- Строка появляется на **каждой** смене состояния, включая те, что сегодня не
  пишутся в журнал вообще.
- Новое место смены состояния в коде попадает в тему автоматически, без
  правки.
- Идемпотентность не зависит от того, какой процесс пишет: перезапуск сервера,
  повторный тик, восстановление слотов дублей не дают.

### Что меняется для пользователя
Тема задачи перестаёт быть «молчаливой»: при переходе `agent_state` из
`in_progress` в NULL там появляется строка «работа снята без сдачи». Это может
выглядеть как шум при плановом закрытии/архивации карточки — поэтому переходы в
NULL при массовом снятии подавлены (см. выше). Проверить на живых данных нужно
именно этот случай.

### Риски
1. **Задержка.** Строка приходит на тике планировщика, а не в такт смены
   состояния. Если нужен мгновенный отклик в iOS — разносчик надо вызывать
   также из `inProcessRun` после старта/сдачи шага.
2. **Рост таблицы.** Очередь будет копиться, если разносчик не отработает.
   Нужен индекс по `delivered_at` и очистка строк старше N дней (годится
   `taskPurge`).
3. **Закрытая тема.** `setTaskTopicClosed()` переводит тему в read-only. Строка
   в закрытую тему писаться не должна — разносчик обязан проверять
   `isTaskTopicClosed(taskId)` и **не** отправлять в очередь повторно, иначе
   стопка растёт вхолостую.
4. **Двойная правка.** Эта же работа идёт в карточке
   `7efcc173-2841-478a-b1e7-f9253a5492f4` (там уже был шаг Архитектора и
   Разработчика). Риск двух разных реализаций одного и того же — решение за
   владельцем.

## 5. Раскатка и откат

### Раскатка
1. Миграция добавляет только новую таблицу и триггер. **Ни одна существующая
   таблица не меняется** — риск для живых данных нулевой на этапе схемы.
2. Флаг `step_topic_progress_enabled` в `server_settings_registry` (по образцу
   `widgetFeatureFlag.ts`, `serverSettingsRegistry.ts`). По умолчанию **выключен**:
   схема есть, строки копятся, в тему не пишется.
3. Прогон на копии БД: включить флаг, создать задачу с планом, прогнать
   сценарий (старт → сдача → блок → авто-перезапуск → обрыв), сверить число
   строк в теме с числом смен состояния.
4. На живой базе сначала включить флаг **на одной карточке** (whitelist
   task_id), смотреть тему день.
5. Общий флаг — после того как Максим увидит строки и скажет, что они нужны
   именно в таком виде.

### Откат
- **Быстрый (без правки кода):** выключить флаг и рестарт сервиса. Разносчик
  перестаёт переносить строки; в очереди они лежат и не теряются.
- **Полный:** удалить строки из `step_topic_progress`, `DROP TRIGGER`,
  `DROP TABLE`. Уже написанные в `chat_messages` строки остаются — откат
  убирает механизм, а не написанное. Чистить их вручную только по явному
  решению владельца.
- Откат не трогает `task_events` и логику шагов: ни один путь выполнения шага
  не меняется, меняется только то, что пишется в тему.

### Проверки для приёмки (для этапа builder/QA)
1. Одна смена состояния → ровно одна строка в теме.
2. Пять видов смены из таблицы выше → пять строк, тексты по образцу.
3. Повторный UPDATE с тем же состоянием → строки нет.
4. Перезапуск сервера при незакрытом шаге → строки нет.
5. Восстановление слотов (`recoverInterruptedPlanSubtasks`) → строки нет.
6. Массовое снятие (`releaseSubtaskWork` при закрытии задачи) → строк нет.
7. Строка идёт в тему задачи и **не** попадает в общий чат проекта.
8. Тема, закрытая `setTaskTopicClosed`, не принимает строки и не растёт в очереди.
