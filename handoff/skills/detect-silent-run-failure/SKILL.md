# Молчащий ход → видимый сбой

Симптом: провайдер ответил «успешно», но без содержания — пустой `content`,
расход 0/0, ошибки нет. Сервер такой ход считал успешным: `runFailure` не
ставился, «Не смог ответить» не писался, heartbeat тикал, сторож через
10 минут закрывал попытку как `auto_restarted`. Наблюдение 21.10.2026:
13 молчащих ответов подряд у роли critic_verifier (opencode / space-bunny-free).

## Рецепт

### 1. Распознавание — в одном месте, на границе провайдера

`server/src/runtime/providerFailover.ts` (рядом с `lastAssistantLimitError`):

```ts
export function emptyAssistantAnswer(message: any): string | null
export function lastAssistantEmptyAnswer(session: any): string | null
```

Пусто = у последнего ответа ассистента нет НИ текста, НИ вызова инструмента.
Не пусто (у них свои пути, поведение менять нельзя):

- текст в `content` (`type: "text"`, непустой после trim);
- вызов инструмента (`type: "toolCall"`) — ход ещё идёт;
- `stopReason: "error"` — ошибка модели (лимит провайдера и т. п.);
- `stopReason: "aborted"` — отмена.

Проверять надо ПОСЛЕДНИЙ ответ в сессии: промежуточный пустой ответ между
вызовами инструментов — это нормальный ход.

### 2. Рабочий ход (`server/src/runtime/inProcessRun.ts`)

Ловить сразу после `session.prompt(...)`, рядом с проверкой лимита провайдера:

- `runFailure = new Error(причина)` — ход падает, а не «проходит с тишиной»;
- попытку закрыть САМИМ: `UPDATE attempts SET ended_at=..., outcome='failed',
  reason=<причина> WHERE id=<current_attempt_id> AND ended_at IS NULL`.
  Шаг плана потом закроет её через settle (шаг заблокируется с причиной, в
  ленте карточки появится сообщение о сбое); карточка без шага плана — своей
  попыткой не закрывается, её надо гасить здесь же;
- для карточки без шага плана — ещё и `POST /api/tasks/:id/state` со
  `state: "blocked"`, `block_type: "transient"` и причиной в комментарии
  (тот же путь, что при сорванном запуске).

### 3. Живой чат (`server/src/runtime/chatLiveTurn.ts` + `server/src/routes/chats.ts`)

- В `LiveTurn.onEvent` на событии `message_end` с сообщением роли
  ассистента — запомнить причину (`emptyAnswerReason()`); последний ответ
  ассистента перезаписывает пометку, обычный ответ снимает её.
- В `routes/chats.ts`, где раньше стояло общее «Ход завершился без текста
  ответа»: если причина известна — `failure = new Error(причина)` и
  `replyText = chatRunFailureText(failure)` → в чат ложится «Не смог ответить:
  модель вернула пустой ответ…» вместо тишины.

### 4. Словарь причин

- `server/src/runtime/failureReasons.ts`: код в закрытый список + подпись +
  правило классификатора (текст ошибки → код). Проверь, что ни одно раннее
  правило не перехватывает твой текст раньше твоего правила (например,
  «нет текста ответа» ловится правилом про доступ).
- `server/src/runtime/failurePolicy.ts`: политика по коду — `Record` требует
  ключ для каждого кода, без него `tsc` не проходит. Для пустого ответа —
  `block`: повтор в той же сессии у сломанного провайдера придёт таким же
  пустым, а блок с причиной виден и в ленте, и в `attempts.reason`.

## Проверка

- Тест сначала падает на старом коде: провайдер вернул пустой content →
  `attempts.outcome` должен стать `failed`, в `attempts.reason` — «пустой
  ответ», в ленте карточки — сообщение о сбое. Зафиксируй красный прогон.
- Обычный ответ (текст + расход > 0) ведёт себя как раньше; вызов
  инструмента, ошибка модели и отмена не считаются пустым ответом.
- `npx tsc --noEmit` — чисто.
- Полный прогон серверных тестов: сравни с тем же прогоном на исходном
  коммите (временный worktree + symlink на `server/node_modules`). В этом
  репозитории на 21.10.2026 было 24 упавших файла (62 теста) от окружения —
  боевой `role-routing.yaml`, отсутствующие `server/scripts/role-prompts/*.md`,
  нет учёток ролей. Сравнение «до/после» отделяет твоё от чужого.
- Длинные прогоны — в фоне: `nohup bash -c "npx vitest run > /tmp/x.log 2>&1;
  echo EXIT=$? >> /tmp/x.log" &`.

## Грабли

- Не расширяй детект на ошибку модели и отмену: у них свои причины, свои
  сообщения и свои политики.
- Не путай пустой ответ с «ход закончился без сдачи» (`step_stalled`): у
  первого есть конкретная причина от провайдера, у второго — нет.
- Не оставляй попытку открытой «на потом»: если шаг плана её закроет через
  settle — хорошо, но карточка без шага плана останется висеть, и сторож
  спишет её как `auto_restarted` — то есть ровно та молчание, которое чинили.
- На живой сервер фикс не выкладывай сам: коммит в ветку роли, перенос в
  `main` — за ответственным за интеграцию.
