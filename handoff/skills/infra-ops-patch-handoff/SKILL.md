# Счётчик доставки тревог в ~/infra-ops: правило потери и передача правки

## Признаки

- Утренняя сводка `autonomy-110` пишет одно и то же «у отправителей НЕ УШЛО N»
  несколько дней подряд, хотя уведомления доходят (ложная тревога).
- Обратный случай: сводка пишет «потерь за 36 ч нет», а в журнале за те же дни есть
  строки с непустой причиной сбоя (тихий пропуск потерь).
- Карточка на диагностику заводится каждое утро из тикета `inbox/…/_diagnostic/…`.
- `git status` в `/home/maksim/infra-ops` по нужному файлу: правка предыдущей карточки
  не применена.

## Главная ловушка: у поля reserve ДВА смысла

`alert_send.py` пишет в журнал `~/.claude/alert-undelivered.log` из двух мест, и
значение `reserve` означает разное:

| запись | что означает reserve | дошла ли тревога |
|---|---|---|
| успех с первой попытки | `дошёл (через n8n)`, `error` пуст | да |
| первая попытка сорвалась, вторая прошла | `дошёл (через n8n)`, `error` НЕПУСТОЙ | **да** |
| обе попытки сорвались | `дошёл` / `не дошёл` / `промолчал` | **нет** |
| отправитель со своей дорогой | `своя дорога` | нет (он сам отметил потерю) |

`дошёл` без «(через n8n)» — это **доклад о сбое**, доставленный запасной дорогой в
Telegram мимо n8n. Тревога в этой строке не дошла.

**Правило потери:** строка — потеря, если причина непустая И `reserve != "дошёл (через n8n)"`.
**Счётчик «доставлено»:** только строки с пустой причиной ИЛИ `reserve == "дошёл (через n8n)"`.

Что будет, если ошибиться (обе проверенные ошибки уже были на этой машине):

- `startswith("дошёл")` в счётчике «доставлено» → в число доставленных попадают
  предупреждения: 14.10.2026 сводка писала «потерь нет (доставлено 4)» про четыре
  сорванные тревоги. За всю историю журнала так 19 строк.
- «потеря = непустая причина» без исключения на повтор → две настоящие строки, где
  тревога дошла со второй попытки (13.10 xray-target-guard, 14.10 mcp-net-watch),
  считаются потерями, и ложная тревога возвращается.

## Что делать

1. **Сначала проверить, не повтор ли это.** Дата файла против даты прошлой карточки и
   `git status` по конкретному файлу. Повторный разбор = проверка «применена ли прошлая
   правка», а не новая диагностика.
2. **Считать по журналу, а не по числу докладов.** Журнал пишется на КАЖДУЮ отправку.
   Разложить строки по форме из таблицы выше и убедиться, что сумма сходится с общей
   численностью журнала.
3. **Править функцию счётчика, а не текст тревоги.** Маркер «НЕ УШЛО» остаётся только
   для настоящих потерь.
4. **Проверить права ДО подготовки передачи:**
   `getfacl -p /home/maksim/infra-ops/autonomy-report.py`.
   С 17.10.2026 у каталога и его файлов стоит `user:tfrole:rwx` (в т.ч. default ACL, так
   что новые файлы наследуют) — агентский сеанс от `tfrole` пишет и коммитит сам.
   16.10 прав не было, и правка ждала команду владельца; правило «правь только патчем»
   устарело. Проверка за пять секунд: `getfacl`, затем append с откатом.
5. **Если прав всё-таки нет** — отдавать одну команду: скрипт в `/var/tmp` (не `/tmp` —
   его чистят), который сам делает резервную копию, `git apply --check`, `git apply`,
   `py_compile` и печатает результат проверки.

## Как проверить (без отправки тревог Максиму)

- Живые данные — только с `HOME=/home/maksim`, см. грабли.
- Настоящая функция на живом журнале: загрузить модуль через `importlib` из
  `/home/maksim/infra-ops/autonomy-report.py` и вызвать `delivery_watch(36)`, `(120)`,
  `(720)`: на окне с настоящими сбоями должны быть видны потери, на текущем окне — «потерь
  нет (доставлено N)».
- Синтетика всех семи форм строки (чистая доставка, повтор-успех, доклад дошёл, доклад
  молчал, доклад не дошёл, своя дорога, неизвестно) — подменив `UNDELIVERED` на временный
  файл. Ожидание: 5 потерь, из них 1 «без предупреждения», повтор-успех не потеря.
- Сквозной прогон `main()` с подменёнными `send`/`send_direct` (чтобы тревога не ушла
  Максиму): на живых данных уровень тревоги по доставке чистый, на подставном журнале с
  потерями поднимается `error` и строка «Доставка уведомлений: часть тревог … не дошла».
- `python3 -m py_compile` после правки.
- Чужие незакоммиченные правки в `~/infra-ops` не трогать: `git add <файл>` точечно,
  без `-A` и `-a`, `reset`/`stash` не делать.

## Грабли

- Модуль из `~/infra-ops` под чужим HOME разворачивает `~` в `/home/tfrole` и молча читает
  несуществующий журнал: счётчик показывает ноль. Живые данные — `HOME=/home/maksim`.
- `main()` реально **отправляет** сводку (n8n, а при отказе — запасную дорогу) и пишет
  строку в журнал. Для проверок подменять `send`/`send_direct`.
- Под чужим сеансом юниты systemd показывают «неизвестно», а проверка базы знаний падает
  «list index out of range» — это артефакт окружения проверки (нет пользовательской
  шины systemd), а не поломка машины. Утренняя сводка от `maksim` в это время писала
  «все 1535 документов видны» и все службы `active`. Не чинить это в рамках задачи.
- Навык не запишется в `~/taskflow/roles/infra_engineer/skills/` — папка закрыта (`0700`
  у maksim). Класть в рабочее дерево задачи и говорить владельцу, куда скопировать.
- Закрывать карточку, пока правка не применена, не стоит: на следующее утро тревога
  вернётся и разбор начнётся заново.
