# Правки ~/infra-ops из агентского сеанса

## Признаки

Сообщение «Отказано в доступе» на запись в `/home/maksim/infra-ops`, в
`sudo -n -l` только четыре служебные команды Mint, `Host key verification
failed` на `git ls-remote gitea`. Сессия Инженера .110 идёт от служебного
пользователя `tfrole`, а домашняя папка и репозиторий принадлежат `maksim`.

## Причина

Агентские сеансы TaskFlow работают не от владельца. Прав на его файлы у них
нет, безпаролевый sudo выдан только служебным командам Mint, ключа на ssh к
Gitea/NAS тоже нет. Это не тупик диагностики, а граница среды: обойти её нельзя.

## Как делать

1. **Не трогай живое дерево.** В `~/infra-ops` регулярно есть незакоммиченные
   правки владельца — сначала `git status`. Никаких `reset`, `stash`, смены
   веток.
2. **Готовь патч, а не правку файла.** Живой файл копируй в `/tmp` под тем же
   именем, патчь копию, снимай diff в файл `.patch`.
3. **Проверяй на копии, до передачи:**
   - `cd ~/infra-ops && git apply --check <путь>.patch` — проверка без записи
     (права на чтение есть, файл не меняется);
   - `python3 -m py_compile <копия>`;
   - прогон изменённой функции на живых данных (HOME=/home/maksim, если скрипт
     читает `~/.claude/...`) и на синтетическом журнале с настоящей потерей —
     правка не должна «замолчать» тревогу.
4. **Положи патч в два места:** рабочее дерево задачи (коммит) и `/var/tmp`.
   `/tmp` чистят при загрузке, `/var/tmp` живёт дольше.
5. **Отдай ровно одну команду** — без аргументов, которые владелец должен
   подставлять сам: `cd ~/infra-ops && git apply /var/tmp/<файл>.patch`.
6. **Не вливай коммит-носитель патча в main.** Если патч лёг в рабочее дерево
   задачи (репозиторий TaskFlow), оставь его в ветке роли и скажи об этом прямо:
   main этого проекта к правке `~/infra-ops` отношения не имеет, а вливать в main
   без владельца нельзя.

## Как проверить

- `git apply --check` проходит на текущем живом файле — конфликтов нет.
- Копия с патчем компилируется и даёт ожидаемый текст на живых данных.
- На синтетике с настоящей потерей тревога по-прежнему поднимается.
- В ленте карточки и в отчёте честно сказано: код в `~/infra-ops` **не
  применён**, SHA main не существует, перенос ждёт одну команду владельца.

## Грабли

- Отчёт «причина найдена, правка внесена» без слов «применена на живой машине»
  вводит владельца в заблуждение: в следующей сводке дефект вернётся.
- Путь `~/<файл>.patch` в команде для владельца может не существовать: патч
  лежит в `/var/tmp` и в рабочем дереве задачи, а не в его домашней папке —
  записать туда сеанс не может.
- Проверка «просто запустил и посмотрел» без синтетики пропускает регрессию:
  правка счётчика легко «чинит» тревогу, одновременно глуша настоящую потерю.

## Смежное

- Если правка требует не файла, а перезапуска юнита, который живёт от
  `maksim` (юниты `systemctl --user` владельца), проверь это заранее:
  `systemctl --user list-units` сеанса `tfrole` покажет не его набор.
## Что изменилось 22.10.2026

- **Права на запись в `~/infra-ops` есть** (с 17.10 стоит ACL `user:tfrole:rwx`),
  и 22.10 правка доставки тревог применена прямо в живой репозиторий: коммит
  `5c39033`, только два своих файла, чужие незакоммиченные правки не тронуты.
- **Инструмент правки файлов** (не bash) пишет только в рабочую копию задачи и
  в `/tmp` — в `~/infra-ops` он отвечает «запись вне рабочей копии запрещено».
  Это ограничение инструмента, а не прав; правка через `git apply` в самом
  репозитории — рабочий путь, его применяли и раньше (18.10).
- Порядок, который сработал: копия файла в `/tmp` → правка копии → `diff -u` в
  патч → `git apply --check` на живом файле → `git apply` → `python3 -m py_compile`
  → прогон изменённой функции на живых данных и на синтетике → `git add` явными
  путями → `git commit` → проверка, что сводка/сторож видят норму по результату.
