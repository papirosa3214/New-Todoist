Карточка: `a2548612-133b-4dc2-964b-b585eb4e2cc9` · репозиторий-правки: `/home/maksim/infra-ops` (ветка `main`)

## Коротко

Тревога «systemd recheck did not drain ghost session records» — не ложная: пустые записи
сеансов действительно копятся, сотнями в час. Но способ, которым сторож их убирал
(`systemctl daemon-reload` и мгновенная проверка результата), сегодня уже не работает:
перечитка systemd не убирает ни одной записи. Правка сделана в стороже: чистка теперь
идёт по ступеням, каждая ступень измеряется, а тревога говорит реальные числа.

Остался один шаг, который агент выполнить не может: поставить новую версию сторожа
в `/usr/local/libexec/session-record-watch.py` — файл под root, у агентского сеанса нет
прав. Ниже одна команда владельца.

снимать файлы состояния бессмысленно (см. доработку ниже).

## Причина

SSH-сеансы к .110, которые обрываются снаружи, на systemd 255.4-1ubuntu8.17 оставляют
в logind запись в состоянии `closing`: cgroup сеанса уже исчез, запись — нет. Это
известная гонка systemd (https://github.com/systemd/systemd/issues/43745), точная
внутренняя причина на 255 не доказана.

Кто рвёт такие сеансы (проверено срезом `ps` за 45 секунд):

- `Codex CLI` по SSH извне — `/bin/bash -l -i -c CODEX_HOME=…`, клиент с 192.168.1.102,
  новый сеанс примерно раз в секунду, живёт меньше секунды;
- MCP-серверы TaskFlow, поднятые по SSH — `python3 server/scripts/mcp_server.py`.

То есть копятся не записи TaskFlow, а следы внешних агентов, которые подключаются к .110
по SSH.

Почему перечитка systemd перестала помогать: 23.10 в 04:11 тот же вызов убрал 8192
записи (это записано в `~/infra-ops/docs/session-record-watch-20261023.md`), а в 08:56 и
09:11 — ноль. Разница не установлена; поэтому сторож больше не считает перечитку
гарантией и проверяет результат каждой ступени отдельно.

## Что изменено

`/home/maksim/infra-ops` → коммит `d5bad96` (ветка `main`), файлы
`session-record-watch.py` и `test_session_record_watch.py`.

Сторож идёт по ступеням, после каждой меряет счётчик и останавливается, как только он
упал ниже порога (64):

1. **перечитка systemd** — `systemctl daemon-reload`, не чаще раза в 10 минут, и
   результат ждём до 35 секунд, а не снимаем мгновенно;
2. **снятие просочившихся файлов состояния** — удаляются файлы `/run/systemd/sessions/<id>`
   только у тех записей, которые и так считаются мусором (closing, cgroup исчезла), затем
   ещё одна перечитка systemd; живыми сеансами не трогаем;
3. **остановка оставшихся scope-юнитов** — если юнит сеанса ещё есть в systemd, его
   останавливают, чтобы logind смог закрыть сеанс;
4. **обычное закрытие** — `loginctl terminate-session` (не больше 200 за проход).

Тревога теперь содержит реальные числа: сколько записей было, сколько осталось и какие
ступени не помогли. В состояние сторожа добавляется поле `attempts` — по нему видно,
какая ступень дала результат. Плюс поле `growth` — на сколько вырос счётчик между
проходами.

| синтаксис (`ast.parse`) | без ошибок |

Чистку на живой машине проверить нельзя: агентский сеанс работает от `tfrole` (uid 997),
`sudo` без пароля даёт только четыре служебные команды Mint, а `systemctl stop` и
`loginctl terminate-session` упираются в polkit («Время ожидания соединения истекло»).
Поэтому живую проверку даёт первый проход нового сторожа — он печатает в
`/var/lib/session-record-watch/state.json`, какая ступень сработала.

## Одна команда владельца

Нужен root: поставить новую версию сторожа и прогнать её один раз.

```bash
sudo install -m 0644 -o root -g root /home/maksim/infra-ops/session-record-watch.py /usr/local/libexec/session-record-watch.py && sudo systemctl daemon-reload && sudo systemctl start session-record-watch.service && sudo cat /var/lib/session-record-watch/state.json
```

Проход занимает до двух минут (юнит ждёт, пока счётчик опустится). Смотреть в выводе
поле `attempts`: ступень, после которой счётчик упал, — это и есть рабочая чистка. Если
`error` остался, в нём будет реальное число оставшихся записей.

Если после установки записи не уходят (то есть ни одна ступень не сработала) — остаётся
разово перезапустить менеджер входов: у пользователя `maksim` включено `Linger=yes`,
поэтому пользовательские службы и TaskFlow при этом остаются, а записи очищаются. Это
действие владельца, и лучше делать его в quiet-окно, когда нет активных попыток ролей:

```bash
sudo systemctl restart systemd-logind
```

## Доработка после вердикта критика (23.10, вердикт changes_requested)

Коммит `2cc9b8f` в `/home/maksim/infra-ops` (ветка `main`, разошён по gitea, github и nas).

1. **Лимит terminate — по остатку бюджета.** Прежние `MAX_TERMINATE=200` при
   последовательных `terminate-session` по 15 с не влезали в `BUDGET=100`
   (`TimeoutStartSec=120`): проход мог быть убит на середине, и `state.json` оставался
   без записи. Теперь потолок по числу — 2000, фактический объём считается из остатка
   времени (минус резерв под финальное ожидание и запись состояния), вызовы идут
   пачками по 8 одновременно, а состояние пишется инкрементально после каждой ступени.
2. **Файлы `/run/systemd/sessions` больше не снимаются.** Выбрана замена — штатный
   `loginctl terminate-session` (плюс остановка scope-юнитов), а не правка внутреннего
   состояния systemd. Причины: правка не покрыта гарантией systemd; на живом проходе
   снятие файлов дало 1576 -> 1609 записей (стало больше) и удалило 24 файла из 117
   существующих; файлы — не то место, где лежит мусор (в памяти logind). На стенде
   (подменённые `loginctl`/`systemctl`) проверено, что полный проход не трогает файлы
   и закрывает сеансы штатной командой.
3. **В `~/infra-ops/docs/session-record-watch-20261023.md` исправлено неверное
   «14/14 PASS»:** набор тестов — 13 тестов, 13/13 PASS (прежняя версия набора — 6).

Живые числа на 10:08 МСК: `loginctl list-sessions` — 1683 записи (1673 closing, 10 active),
живых scope-cgroup — 24, файлов в `/run/systemd/sessions` — 117. Рост продолжается
(09:41 — 1269 closing, 10:08 — 1673). Штатные средства (daemon-reload, terminate-session,
снятие файлов) записи не убирают — нужен рестарт `systemd-logind`, это решение владельца.
