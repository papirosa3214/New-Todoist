# DESIGN.md — живой журнал дизайн-системы TaskFlow

Этот файл — единственный источник истины про то, как что выглядит и почему. Правило проекта
(`~/.claude/CLAUDE.md`): **перед любой визуальной правкой — прочитать этот файл**. После любой
значимой визуальной правки — **дописать сюда**, не оставлять решение только в комментарии кода.

Не дублирует комментарии в коде (там — «почему именно так», конкретные числа с историей правок) —
здесь только «что где и в каком порядке», чтобы не читать десяток файлов, просто чтобы понять
структуру. За точными числами/датами решения — идти в комментарий у самого кода, ссылки даны.

### Модуль отступов

База — **4px**. Всё выводится из него: `gap-1.5`=6, `gap-3`=12 (стандартный зазор иконка↔текст),
`px-4`=16 (стандартный горизонтальный отступ экрана), `mb-4`=16 (межблочный модуль между секциями
формы). Круглые/квадратные отметки состояния — 18px (`w-[18px] h-[18px]`), это конвергентный
размер для ВСЕХ индикаторов состояния задачи/подзадачи в проекте (было раскидано 12/18/22px по
разным экранам, унифицировано 2026-08-13).

Дробных пикселей избегать — если число не целое на реальной ширине экрана, это сигнал, что расчёт
неверный (см. design-by-measurement skill).

## 2. Общие примитивы

- **`Card`** (`TaskFields.tsx`) — `bg-card rounded-2xl overflow-hidden`, дети разделены
  `border-t border-stroke`. Используется для сгруппированных полей (Срок/Проект/Приоритет).
  Список подзадач в форме — **сознательно БЕЗ Card-обёртки** (плоский поток страницы, тем же
  приёмом что обычный текст) — так решено явно, не забыто.
- **`Button`** — `h-12 rounded-xl text-[15px] font-semibold`, три варианта:
  `primary` (`bg-red text-white` — главное действие), `secondary` (`bg-card2` + рамка),
  `outline` (прозрачный + рамка, `text-sub`). Всегда `w-full` внутри своего контейнера.
- **`Avatar`** (`UI.tsx`) — два режима, переключаются по наличию `avatar_url`:
  - **есть картинка** → `<img>`, `rounded-lg` (НЕ круг), `object-fit: contain` (НЕ `cover`).
    Оба решения от 18.08.2026: круглая маска давала «кругляш» вокруг непрозрачного фона исходника,
    `cover` обрезал неквадратные картинки по бокам. Загружаемую картинку-маскота/лого перед
    загрузкой стоит обработать (убрать фон, допаддить до квадрата) — иначе результат будет мелким
    внутри бокса (contain честно показывает исходные пропорции).
  - **нет картинки** → буквенный кружок, `rounded-full`, цвет фона = `avatar_color` пользователя,
    инициалы белым текстом.
  - Размеры по контексту: 18–20px (плотные строки), 24px (списки/доска/форма), 32–36px (крупные
    карточки/уведомления).
- **`ScreenHeader`** — два варианта: `large` (заголовок слева + actions в строку, экраны верхнего
  уровня — Входящие/Сегодня/Обзор) и `compact` (iOS-nav-bar: `leading` слева, по-настоящему
  центрированный заголовок, `actions` справа — детальные/вторичные экраны).
  **Фон — затухание, а не плашка** (19.08.2026, Максим: «верхушку сделать прозрачную, с
  последующим затуханием: вначале нормальная видимость, под шапкой посередине уже мутно, а
  ближе к верху экрана прям исчезает»). Было `bg-bg/90 backdrop-blur-xl border-b` — почти
  непрозрачная полоса с резкой линией внизу. Стало три слоя: два `backdrop-filter: blur`
  (20px и 6px) со сдвинутыми `mask-image`-градиентами + подложка цветом `--color-bg`, тоже
  градиентом. Двух слоёв размытия не избежать: один `backdrop-filter` даёт ОДНУ силу
  размытия на всю высоту, маска умеет только гасить её целиком — переход «чётко → мутно →
  ничего» из одного слоя не собирается. Границы больше нет, она спорила бы с плавностью.
  `-webkit-backdrop-filter` и `-webkit-mask-image` обязательны — владелец смотрит с айфона,
  в WebKit без префикса не работает ни то, ни другое. Подложка построена на `color-mix` от
  токена, поэтому светлая тема работает от того же кода.
- **`Icon`** — обёртка над Lucide, `strokeWidth` фиксирован по проекту (не дефолтный lucide-овский).

## 3. Задача — три представления

Одна и та же задача рисуется тремя разными компонентами. Правку внешнего вида задачи почти всегда
нужно вносить **во все три**, иначе они разъедутся (уже случалось несколько раз за историю проекта):

| Представление   | Компонент                     | Где живёт                                        |
| --------------- | ----------------------------- | ------------------------------------------------ |
| Строка списка   | `TaskRow.tsx`                 | Входящие/Проект/Предстоящее/Сегодня (list-режим) |
| Плитка доски    | `TaskBoard.tsx` → `BoardCard` | те же экраны, board-режим                        |
| Полная карточка | `TaskDetailScreen.tsx`        | открывается тапом по строке/плитке               |

### Строка списка (`TaskRow`)

Порядок слева направо: **[колонка: аватарка исполнителя, если есть, w-24px фиксированной ширины]**
→ **[заголовок + описание одной колонкой]** → **[метаданные строкой под заголовком]**.

Порядок бейджей метаданных (`hasMeta`, вычисляется по фактическим полям задачи):
`приоритет-флажок` → `проект` (цвет проекта, прозрачный фон + текст тем же цветом; выключен на
Inbox — `showProjectBadge={false}`, там задача и так лежит в секции с заголовком-именем проекта,
второй раз то же самое было бы шумом, владелец 19.08.2026 — тот же день, когда бейдж и завёлся) →
`просрочено-пилюля` (красная, только Today) → `метки` → `дата` (пропущена на Today/Upcoming —
избыточна/дублирует группировку) → `счётчик подзадач` («2/5») → `статус агента`.

**Никакого чекбокса завершения задачи в строке нет** (убран 18.08.2026 вместе со свайпом-влево —
«не надо мне эти квадратики, лучше провалиться в саму задачку»). Единственный способ отметить
готово — открыть карточку и нажать кнопку там (см. ниже).

**Свайп-влево вернулся тем же днём, с другим действием** — не завершение, а прямой переход в
форму редактирования (`/task/:id/edit`), минуя карточку-просмотр и её кнопку «Изменить». Тот же
жест 1:1 (`useSpring`, `response: 0.3, damping: 1`, порог 72px/400px·с⁻¹ — физика отпускания не
менялась, уже одобрена), синий фон с карандашом вместо teal-чека. Работает во всех экранах на
`TaskRow` (Today/Inbox/Project/Upcoming) — доска (`BoardCard`) свайпа не имеет, у неё другая
механика взаимодействия (тап открывает карточку, drag&drop двигает между колонками).

**Распознавание — retuned 19.08.2026**, дважды за сессию («миллиметрик — и сразу в изменении»).
Не порог срабатывания (72px/400px·с⁻¹ выше — те остались), а ДО него: ось жеста решалась на 6px
любого направления голым `|dx|>|dy|` — дрожание руки при обычном скролле застревало
«горизонтальным» навсегда (`setPointerCapture`). Плюс отдельная дыра: velocity сама по себе —
мгновенная скорость по двум последним сэмплам, не средняя за жест, и короткое резкое касание в
пару px давало >400px/с при почти нулевом смещении. Две правки в `TaskRow.tsx`: `DIRECTION_LOCK_PX`
6→10 + `DIRECTION_BIAS` 1.4 (dx должен явно преобладать, не только чуть перевесить) — из §10
скилла `apple-design` («hysteresis ~10px» + асимметрия цены ошибки: скролл, принятый за свайp,
просто повторить, а свайп размером с дрожание уводит на другой экран); `SWIPE_VEL_MIN_DX` = 36px
(половина SWIPE_THRESHOLD) — velocity-путь больше не срабатывает сам по себе без реального
смещения.

### Плитка доски (`BoardCard`)

Тот же принцип колонки-аватарки слева (тоже без чекбокса — убран синхронно со строкой списка).
Порядок бейджей в подвале плитки (более сжатый набор, чем строка списка): `дата` → `счётчик
подзадач` → `статус агента` → `метка` (первая) → `бейдж проекта` (только на многоколоночной доске).
Порядок **другой**, чем в TaskRow — сознательно, доска теснее, приоритет отдан дате и подзадачам.

### Детальная карточка (`TaskDetailScreen`)

Сверху вниз: **шапка** (назад слева, красная корзина-удаление справа — три точки убраны
18.08.2026, «Изменить» переехало кнопкой в самый низ, см. ниже) → **заголовок + флажок приоритета**
(заголовок НЕ крашен цветом) → **описание** (если есть) → **карточка метаданных** (срок → приоритет
→ исполнитель → статус агента, каждая своя строка `bg-card rounded-xl`) → **метки** (если есть) →
**подзадачи** (лента, см. §4) → **кнопки действия** → **лента событий/комментариев**.

**Карточка «Приоритет»** в метаданных — 18.08.2026 убрана пилюля «P1» справа, взамен красятся ТОЛЬКО
иконка-флажок и слово «Приоритет» цветом приоритета (не заголовок задачи выше, не что-либо ещё в
строке). P4/без приоритета — остаётся серым (не отличается визуально от «не покрашено»).

**Кнопки действия** (`space-y-2`, под подзадачами): «Закрыть задачу» (`primary`, только когда
статус active и все подзадачи выполнены/их нет) → «Изменить» (`outline`, **видна всегда**, ведёт в
форму редактирования — 18.08.2026 единственный путь туда, раньше был ещё в меню трёх точек).

**Лента** — сортировка **новые сверху** (18.08.2026, было наоборот — «самые актуальные вверху,
чтобы не листать до посинения»).

## 4. Подзадачи

Живут как самостоятельная единица работы (не плоский чек-лист) — своё состояние, своя аренда,
свой итог. Компонент — `SubtaskFeed.tsx`.

**Пять состояний**, форма несёт смысл (`StateMark`):

| Состояние | Как выглядит                                                                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `done`    | залитый зелёный кружок с белой галочкой (единственное состояние с кольцом-заливкой)                                              |
| `running` | `DashedRing` (21×21px, 8 сегментов Lucide `CircleDashed`, дуги укорочены) — три независимых слоя движения одновременно, см. ниже |
| `pending` | тот же `DashedRing`, статичный, без анимации — «running, просто ещё не поехало»                                                  |
| `blocked` | оранжевый треугольник-восклицание (`TriangleAlert`, `text-orange`, 21px) — сразу видно КАКАЯ подзадача блокирует                 |
| `review`  | синий глаз (`Eye`, `text-blue`, 21px) — агент сдал шаг, ждёт решения владельца, см. подраздел ниже                               |

`done`/`running` — оба зелёные (`--color-green`), различаются формой, не цветом (осознанное
решение 18.08.2026, раньше running был teal). Текстовая подпись рядом с заголовком убрана
(18.08.2026) — избыточна, статус виден и по значку, и по строке `AgentStatusRow` наверху карточки.
`blocked` изначально был `text-coral` (красный) — перекрашен в `text-orange` тем же днём, найден
рассинхрон с `AgentStatusRow`, где «заблокировано» уже было оранжевым; coral оставлен только за
«Агент пропал» (более тревожное состояние, молчание, а не осознанная блокировка).

**Пятый заход дизайна running-индикатора (финал, 18.08.2026)** — стоит помнить перед следующей
переделкой:

1. Lucide `Loader2` — не понравился.
2. 12 капель-«комета» с CSS `transform: rotate` на всей группе — «крутилась не как стрелочка на
   своей оси, а ещё и вокруг оси, как ураган неровный, пьяная стрелка».
3. `DashedRing` v1 — волна из ОДНОГО яркого сегмента (12.5% цикла) — технически волна, но при 8
   сегментах в моменте виден один: «не вижу, что там что-то происходит».
4. `DashedRing` v2 — дуга 5/8 сегментов разом (`animation-delay` = индекс path в массиве × шаг) —
   **реальный баг**, не вкусовщина: индекс path в `circle-dashed.mjs` НЕ совпадает с его угловым
   положением на круге (Lucide перечисляет пути в порядке генерации SVG, не по часовой стрелке) —
   дуга зажигалась вразнобой, «в трёх абсолютно разных местах» вместо соседних сегментов.
   **Урок: при анимации по индексу многосегментного stock-SVG-значка — не считать, что порядок
   массива совпадает с геометрией; считать угол каждого сегмента (`atan2` от центра до его
   стартовой точки) явно, скриптом, и строить свою карту позиций.**
5. `DashedRing` v3 (финал) — та же дуга 5/8, но с верной угловой картой
   (`DASH_ANGULAR_POSITION` в `SubtaskFeed.tsx`), плюс ещё два слоя движения поверх, все три
   проверены покадрово через Playwright перед показом:
   - **dash-glow** (цвет, «змейка») — 0.8s, по часовой
   - **dash-spin** (вращение всей обёртки) — 1.6s, **против часовой**, `linear` (не `ease` —
     рывки на симметричной фигуре читались бы как неровность)
   - **dash-pulse** (масштаб) — 1.6s, дышит 18↔23px (`scale(0.8571)`↔`scale(1.0952)` от базы 21px)

   Направления цвета и вращения **намеренно разные** — не рассинхрон, прямая просьба владельца.
   `dash-spin` и `dash-pulse` — на **разных DOM-узлах** (span-обёртка / svg внутри неё), не на
   одном: два CSS `transform`-анимации на одном элементе не складываются, вторая просто
   перезаписывает первую. Физическое вращение здесь безопасно (в отличие от кометы v2) именно
   потому что фигура радиально симметрична — 8 сегментов через строго равные 45° вокруг истинного
   центра обёртки, вращаться с постоянной скоростью ей буквально не в состоянии «пьяно».

   **Вывод: спрашивать точный референс/показывать варианты раньше, чем тратить итерацию на
   самостоятельную интерпретацию — и никогда не переносить геометрический расчёт в компонент
   без проверки скриптом/покадровым скриншотом, «на глаз» тут дважды подряд дало баг.**

**В форме редактирования** подзадач нет ни чекбоксов, ни `DashedRing` — только заголовок текстом +
крестик-удаление + ручка-хват для drag&drop (см. §6). Отмечают выполненными/смотрят статус
только в карточке.

**Вставка «между шагами»** (для агентов) — `after_id` в `POST /api/tasks/:id/subtasks`, вставляет
сразу после указанного шага, сдвигая хвост. **Перестановка** (для человека) — drag&drop в форме
редактирования, тот же паттерн (`@dnd-kit`, ручка-хват слева), что уже двигает карточки на доске.

### Приёмка по шагам (`review`) — 18.08.2026

Пятое состояние подзадачи, симметричное протоколу всей задачи (`AGENT-PROTOCOL.md`), но на уровне
шага: агент сдаёт шаг на проверку и **сразу продолжает следующий**, не дожидаясь решения — владелец
«прощёлкивает» шаги пачкой, когда удобно, не в реальном времени. `review` не протухает по времени
(в отличие от `running`) — молчание тут нормальное ожидание, не брошенная работа.

**Кружок-переключатель отключён у `review`** (был кликабельным как везде — случайный тап по нему
принимал шаг, который на самом деле хотели отклонить). Вместо тап-переключателя — раскрыть шаг и
увидеть две явные кнопки, **`ПРИНЯТЬ` слева / `ВЕРНУТЬ` справа** (`justify-between`, `text-[13px]
uppercase tracking-wider`, тот же паттерн, что uppercase-заголовки в `UI.tsx`). `ВЕРНУТЬ` открывает
форму комментария (`ReplyForm`) — обязателен, с возможностью приложить файл/скриншот.

**Права — по типу пользователя, не по `creator_id`.** Первая версия проверяла `req.userId ===
task.creator_id` — оказалось неверно: агент часто сам и есть создатель задачи (обычный рабочий
паттерн), эта проверка заперла бы решение по review именно на него. Исправлено на `caller.type !==
'ai'` (симметрично уже существующей защите `completed` для задачи в `agent-state.ts`) — выйти из
review может любой человек с доступом к задаче, не обязательно тот, кто её создал.

**`blocked` получил ту же механику** — кнопка `ОТВЕТИТЬ` (оранжевая, тот же uppercase-стиль),
открывает ту же форму `ReplyForm`. Смысл другой: это просто комментарий в общую ленту задачи, не
смена состояния (агент сам снимает блокировку, когда сможет продолжить) — не путать с `ВЕРНУТЬ`.
Прямая просьба: не листать вниз в общую ленту ради ответа на конкретный шаг. `blocked` теперь
раскрывается даже без `result` (агент не обязан передавать его вместе с `blocked`, только `review`
требует на сервере) — иначе форме ответа было бы негде появиться.

### Действия владельца на уровне ЗАДАЧИ (`AgentOwnerActions`, TaskJournal.tsx) — 18.08.2026

Не путать с действиями по шагу выше: тут состояние всей карточки.

| состояние     | кнопки владельца                                                                |
| ------------- | ------------------------------------------------------------------------------- |
| `review`      | «Принять» (primary) · «Вернуть на доработку» (secondary) · «Вернуть в ожидание» |
| `blocked`     | **«Ответить и вернуть в работу»** (primary) · «Вернуть в ожидание»              |
| `in_progress` | «Вернуть в ожидание»                                                            |

**Кнопка `state: null` переименована: было «Снять с агента» → стало «Вернуть в ожидание».** Старое
имя врало: `assignee_id` не трогается, задача остаётся на агенте и он может взяться снова. Из-за
названия владелец не понимал, чем вообще возвращать задачу из `blocked` («как мне тебя вернуть?»,
18.08.2026) — и это была не нехватка функции, а нехватка честного слова на кнопке.

**«Ответить и вернуть в работу»** переиспользует тот же нижний лист, что «Вернуть на доработку»
(`ReturnToWorkSheet`), параметризованный `title`/`hint`/`placeholder` — второй компонент не заводим,
сценарии отличаются только словами.

⚠️ **Порядок в обработчике обязателен: сначала `state: null`, потом комментарий.** Будильник
(`server/scripts/trigger.py`) просыпается по уведомлению о комментарии и тут же перечитывает
задачу; если она в этот момент ещё `blocked`, он пройдёт мимо («заблокирована, ждёт владельца») и
ответ повиснет без движения. Обратный порядок выглядит логичнее для человека и молча не работает.

**Вложения** — не отдельная система: `ReplyForm` переиспользует ту же инфраструктуру, что обычный
комментарий задачи (`useUploadAttachment`/`useAddComment`) — файл грузится сразу при выборе, чипом
висит над полем. При `ВЕРНУТЬ` текст уходит в **оба места**: полноценным комментарием в общую ленту
(с файлами — только там они умеют жить) и в `result` подзадачи (без файла — то, что видно при
раскрытии шага без похода в ленту).

## 7. Известные грабли — держать в голове перед правкой

- **Avatar без `avatar_url` в проп-листе** — молча деградирует до буквенного кружка. Каждый новый
  вызов `<Avatar>` обязан передавать все три (`initials`, `color`, `avatar_url`), даже если кажется,
  что картинки не будет в 99% случаев.
- **SQL для отдачи задачи существует в ДВУХ независимых местах** (`GET /api/tasks/:id` в
  `tasks.ts`, `getFullTask()` в `subtasks.ts`) — правка поля в одном (например добавление
  `avatar_url` в JOIN) не значит, что оно есть в другом. Уже расходились дважды.
- **`CSS` как имя переменной опасно в файлах с `@dnd-kit`** — `import { CSS } from
"@dnd-kit/utilities"` затеняет глобальный `window.CSS`. `window.CSS.escape(...)`, не
  `CSS.escape(...)`, если такой импорт уже есть в файле.
- **Удаляя «мёртвый» компонент — grep вызовов, не только импортов.** `grep "import.*X"` находит
  внешних потребителей; компонент того же файла может звать `X` напрямую без импорта — это не
  подсветится тем же grep'ом и даст `ReferenceError`/белый экран при первом рендере.
- Подробный разбор двух живых крашей из-за этого — `kb/lessons/2026-08-18-taskflow-silent-crash-no-error-boundary.md`.

Apple, выверка кегля окончательна только на устройстве.

Полная картина (что решено, что отвергнуто, чем упирается интеграция) — memory-файл

всех экранах включая доску. В самом веере пункта «Добавить» НЕТ (дублировал бы удержание),
крайним пунктом — «Настройки». Пункт «Настройки» из троеточия «Обзора» убран как дубль.
