## Доставка TaskFlow напрямую в main — решение владельца 05.11.2026

- Pull Request не требуется: не создавать PR и не ждать внешнего ревью. GitHub CI и автослияние остаются отключёнными.
- Штатный путь: актуализировать main → исключительно точечные локальные проверки изменённой логики и файлов → отдельный коммит только своих изменений → прямой push main в GitHub. Коммит прямо в main разрешён. Если работа велась в отдельной ветке/worktree, агент сам локально сливает её в main и пушит main, без PR.
- Публикация и локальное слияние — часть уже порученной работы: владелец не нажимает Merge и не даёт повторное разрешение. Конфликт разрешить с сохранением обеих правок; без force-push и потери чужой работы.
- Только точечные локальные проверки. Полные и глобальные тестовые прогоны, весь test suite, общий регрессионный прогон и тесты несвязанных модулей запрещены. Сервер: явные файлы тестов и --maxWorkers=4. Общий typecheck/сборка не подменяет точечную проверку; штатная сборка сервера при выкладке — отдельный шаг доставки.
- Новая логика — целевой RED → GREEN. Документация и косметика — diff и относящиеся к правке статические проверки, без придуманных тестов. Симулятор, UI-тесты и установка на iPhone — только по отдельному прямому поручению.
- Не коммитить чужие изменения и не использовать git add -A/git commit -a в общем грязном дереве. Основное дерево .110 оставлять на main; изоляция worktree разрешена, но не создаёт обязанности открывать PR.
- Сервер после push: проверить доставку. Перед перезапуском — пустая очередь ролей/чатов и резервная копия БД; затем штатная сборка, health и затронутый API. Push в GitHub ещё не доказывает выкладку.
- Отчёт: SHA опубликованного main, что точечно проверено, что выложено/установлено и что осталось. Удалять только свои уже влитые ветки/worktree. Точечные подсказки при работе/ошибках инструментов сохранять; замена постоянного промпта не является поручением отключать их.

## Как заполнять задачи в Linear (единый порядок, 06.10.2026)

Все, кто заводит задачи в Linear, заполняют их одинаково: владелец потом переносит их в TaskFlow одним импортом. Полная таблица «что импорт читает» — `docs/linear-issue-standard.md`. Коротко:

1. **Описание — четыре раздела по порядку:** «Работа», «Результат», «Критерии приёмки», «Границы» (условия владельца дословно, не выдумывать).
2. **Название** — суть проблемы или результата; без номера, без экранирования.
3. **Приоритет** ставить осознанно (1–4); «без приоритета» при импорте станет 4.
4. **Связи «блокирует» расставлять сразу** — они станут зависимостями. Подзадача — только у куска работы со своим результатом; шаги исполнения (сделать, проверить, принять) подзадачами не оформлять.
5. **Проект** — по итогу работы, **вехи** (3–4 этапа) — только в Linear, каждая задача привязана к вехе. Отменённых задач в импортируемом проекте не держать.

Как карточки живут в TaskFlow после импорта (плоский список под родителем-проектом, план ролей, модели, приёмка) — `docs/task-intake-standard.md`.

## Правило приборов и сторожей (владелец, 10.10.2026)

**Если строишь прибор — ставь на него сторожа. Всегда.**

Прибор — это всё, что работает на метрики и functioning: счётчики, журналы,
индексы, срез данных, синхронизация, расписание. Такое молча портится, и
чем тише, тем дороже потом. Например счётчик обращений к заметкам: сломанный
он незаметен — роль открывает заметку, ничего не пишется, а решение о том,
что удалить, принимается вслепую.

**Обязательный порядок:**

1. В реестр сторожей (`docs/watchers.md`) добавить запись **в той же задаче**,
   что и сам прибор, а не «потом вспомнить».
2. Сторож проверяет **пробным ходом**, а не «таблица существует». Прибор может
   выглядеть целым, пока запись внутри молча падает.
3. Сломался — **уведомление владельцу в «Состояние системы»** (таблица
   `notifications`, свой тип сторожа), **не карточкой**: тревоги сторожей —
   шум для доски (владелец 13.10.2026). В тексте: что сломано, что от этого
   ломается дальше, что делать. Telegram — только если лёг сам сервер.
4. Защита от лавины: не больше одной тревоги в сутки на сторожа, иначе
   поломка забивает «Состояние системы» одинаковыми сообщениями.
5. Инциденты — в тот же реестр: что сломалось, как чинили.

**Это правило для всех агентов** — оркестратора, Codex, Claude Code, любой
роли. Не только для того, кто пишет прибор в этот раз: прибор переживает
задачу, а поломка всплывает через месяц и уже в другой сессии.

**Реестр сторожей — `docs/watchers.md`.** Что смотрим, зачем, где код, как
должно работать, что было (инциденты).

## Роли: где лежат инструкции и как они говорят (20.10.2026)

Один источник. Роли отвечают и сдают только JSON; Markdown — только у владельца
(дневник, заметки, экспорт документа).

| Что                                                                          | Где                                                                                                                   |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Своё у роли (назначение, компетенции, характер)                              | `~/taskflow/roles/<роль>/AGENTS.md` — git `taskflow-roles`                                                            |
| Общее для всех ролей (контракт JSON v1, формат, сдача, координация)          | `server/scripts/role-system-prompt.md` → сервер пишет `SYSTEM.md` в папку роли сам, руками не править                 |
| Список блоков ответа (`text`, `table`, `command`, `link`, `widget`, `html`…) | схема `server/src/lib/roleContractV1.ts` (`STRUCTURED_BLOCK_FIELDS` + `ROLE_BLOCK_GUIDE`), в шаблон подставляется сам |
| Навыки и скрипты роли                                                        | `~/taskflow/roles/<роль>/skills/`, `scripts/`                                                                         |
| Память ролей                                                                 | БД TaskFlow: `taskflow_remember` (`scope`: `role` своя / `team` общая / `project`), `taskflow_recall` ищет везде      |
| Редактор «Инструкция роли» в приложении                                      | пишет прямо в `AGENTS.md` и коммитит                                                                                  |

Больше НЕ источник: `roles.prompt` в БД, `server/scripts/role-prompts/` (убраны 20.10.2026: папка — в Корзину, колонка очищена; копии в `~/.local/state/taskflow-role-prompts-backup-20261020`).

Вызов инструментов: один инструмент `taskflow`, роль пишет только
`{"operation":"…","arguments":{…}}`; action/version/request_id подставляет сервер
(`server/src/runtime/universalTaskflow.ts`). Аргументы проверяются по схеме ДО
выполнения; три неверных вызова подряд — ответ `error.coach` с готовой формой.
Things 3 — 20 операций `things_*`, Todoist — 46 операций `todoist_*` (мост Composio),
почта — `taskflow_mail_*`.

Вызов роли субагентом: инструмент `taskflow_call_role`
(`server/src/runtime/roleSubagentCall.ts`) — зовёшь другую роль и получаешь её
ответ текстом. Права: только Помощник и Оркестратор
(`server/src/lib/roleToolScope.ts`); из роли роль не зовут; не больше 3 вызовов за
ход; ответ обрезается до 16 000 символов; ход субагента — 10 минут.

Вызванная роль работает в **своей комнате-ветке** исходного чата
(`server/src/runtime/subagentRoom.ts`): там видно, как она работает, и лежит её
ответ. Модель субагента (владелец 29.10.2026): **одноразовый** — набирает
контекст, сжимает его в **выжимку**, отдаёт вызывающей роли и исчезает; первичные
источники перебирает он, а не вызывающая роль. Поэтому комната **новая на
каждый вызов**, а промпт субагента и описание инструмента это проговаривают
(`server/src/runtime/roleSubagentCall.ts`).

В списке сессий комнаты **не показываются** — они живут в боковой
панели сессии, по ролям, со статусом:
`GET /api/chats/{id}/subagent-rooms` → комнаты сессии с полями `role_id`,
`role_name`, `state` (`open` / `finished` / `failed`), `question`,
`answer_preview`, `unread_count`. Метка комнаты — `chats.subagent_role_id`,
статус — `chats.subagent_state` (миграция `185_subagent_rooms`). Комната
закрывается сама, как только выжимка из неё попала в главную сессию. Клиентскую
часть (панель роли, шторка со списком комнат, статусы) — по спецификации
`docs/2026-10-29-subagent-rooms-ios.md`. Кнопка «Остановить обращение» на
карточке субагента работает: `server/src/routes/chats.ts`, маршрут
`/api/chats/:id/coordination/:messageId/stop`.
