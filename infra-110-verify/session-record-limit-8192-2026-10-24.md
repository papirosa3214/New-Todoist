# Пустые записи сеансов Linux: 8192 — это предел systemd, а не просто мусор

Дата: 24.10.2026. Карточка df3d2c61, источник тревоги — сводка `autonomy-110` 09:00.

Репозиторий правки: `infra-ops` (`/home/maksim/infra-ops`), ветка `main`,
коммиты `daab963` (правка сводки и тесты) и `1d649fc` (разбор). Оба разошлись
в gitea и github 24.10.2026.

> Навык роли дополнен: `roles/infra_engineer/skills/session-record-ghost-watch/SKILL.md`
> (раздел про предел 8192 и про новую правку сводки).

## Признаки

- Сводка пишет: `Сеансы Linux: 🚨 осталось 8177 пустых записей сеансов Linux (было 8177)`.
- `loginctl list-sessions` — ровно **8192** записи, все пользователя `maksim`
  (uid 1000), состояние `closing`, ни одной `active`.
- 8177 из них пустые (без cgroup и без процесса-владельца), файлов в
  `/run/systemd/sessions` — 6617. Числа не равны: записи живут в памяти logind.
- Каждое утро заводится новая карточка диагностики на одну и ту же поломку.

## Причина (уточнена 24.10.2026)

8192 — это жёсткий предел systemd на число сессий одного пользователя
(`Maximum number of sessions (8192) reached, refusing further sessions`,
systemd 255.4-1ubuntu8.17; настройки в `logind.conf` нет).

Последняя сессия, которую logind согласился создать, — **23.10 14:57**. С тех пор
каждый вход по SSH отклоняется на входе:

```
pam_systemd(sshd:session): Failed to create session: Maximum number of sessions
(8192) reached, refusing further sessions.
```

Отказов за последние 18 часов — 22 046, по 1300–1400 в час; столько же успешных
входов по SSH. То есть **доступ по SSH работает, но сессия в logind не создаётся**,
и в новых сессиях не работает `systemctl --user` («Failed to connect to bus»).

Раньше записи копились из-за оборванных SSH-сеансов (Codex CLI и MCP-серверы
TaskFlow с 192.168.1.102) — дефект systemd 255, issue 43745. Теперь приток
остановился не потому, что починили, а потому, что logind отказывает в новых
сессиях: мусор занял весь лимит. «Число не растёт» больше не означает «всё в порядке».

## Что сделано

`autonomy-report.py`, функция `session_record_watch`:

- строка сводки при **росте** числа записей или при новой ошибке остаётся тревожной,
  как раньше;
- при **неизменной** известной поломке (нужна перезагрузка logind) число
  показывается без тревожного маркера и с прямой припиской «решение владельца» —
  одна поломка больше не заводит новую карточку каждое утро;
- сводка сообщает и про исчерпанный предел сессий (8192) и про то, что новые входы
  по SSH в logind не попадают.

Проверка: `rendezvous._split_state` на новой строке даёт «штатно», тревожных строк
нет; тесты `test_autonomy_report_sessions.py` — 5/5, прежний набор
`test_session_record_watch.py` — 13/13.

## Что осталось за владельцем

Перезагрузка `systemd-logind` — единственный способ очистить записи, и решение
владельца (разлогининит SSH-сеансы; при `Linger=yes` пользовательские службы
остаются). Пока её нет, сводка продолжает честно показывать 8177 зависших записей
и исчерпанный предел сессий, но новую карточку диагностики не заводит.
