# Правка посредника tg-relay: прямой путь в Telegram (24.10.2026)

## Что случилось
Ночью 23→24.10 лежал весь прокси-стек (xray-target-guard: «ни один сервер не пускает
к цели»). Посредник tg-relay ходил в Telegram только через SOCKS xray-bots (10810) —
47 отправок сорвались с «нет ответа, curl вернул код 28», тревоги до владельца не дошли.

## Что сделано
Посредник при отказе прокси идёт в Telegram напрямую из своей сети: из контейнера в
сети n8n-stack_default api.telegram.org виден без прокси (проверено: ответ за 0.17 с).
С сети самого хоста — нет (таймаут 28), поэтому прямой путь и работает только из
контейнера. Порядок попыток: прокси → напрямую → снова прокси; бюджет времени прежний
(≈22 с), чтобы отправитель не успел отвалиться по своему таймауту в 30 с.

## Где применено
Образы `n8n-stack-tg-relay:latest` и `n8n-stack-tg-relay-kb:latest` пересобраны с этой
правкой; в работающие контейнеры файл положен через `docker cp`, контейнеры перезапущены.

## Важно для источника истины
Правка живёт в этом файле (копия `~/n8n-stack/tg-relay/relay.py` с изменением). Каталог
стека `~/n8n-stack` агентскому сеансу не доступен на запись. Кто будет обновлять стек —
перенесите эту правку в `~/n8n-stack/tg-relay/relay.py`, иначе следующая пересборка
образа вернёт посредника к одному маршруту (только прокси).
