# BGE-M3: частые загрузки и падение Ollama при авто-обновлении (25.10.2026)

Карточка 10078308-9d42-4a89-b516-d8a2fa11dedd, тревога `bge-gpu-watch`
«Эмбеддинги BGE-M3: 🚨 частые загрузки BGE-M3: 8 за 5 минут (порог 6)», 04:19 МСК.

## 1. Причина тревоги

Ollama создаёт **отдельный раннер на каждый набор `options`** запроса, а маршрут
`/v1/embeddings` (OpenAI-совместимый) `options` **игнорирует** — он всегда идёт
по ключу модели по умолчанию.

Прокси наблюдения `~/ollama/request-watch/proxy.py` подмешивал в BGE-запросы
`options {num_gpu: 999, use_mmap: true}`. На .110 шли два ключа:

- `/api/embeddings` — TaskFlow `embeddingClient` (модель `bge-m3-embed:latest`),
  RAGFlow (модель `bge-m3-embed`, `keep_alive: -1`);
- `/v1/embeddings` — локальная прокладка `~/infra-ops/minimax_shim.py`
  (модель `bge-m3-embed`, без параметров).

Каждое чередование ключей пересоздавало раннер: в журнале `ollama.service` каждые
20–40 секунд `offloaded 25/25 layers to GPU`, эмбеддинги отвечали 3–6 секунд
вместо 15–30 мс. GPU при этом был свободен, модель целиком в VRAM.

Проверка экспериментом (backend 127.0.0.1:11436): два запроса подряд с разными
`options` → второй грузит модель заново (3 с); одинаковые → 10–20 мс;
`/v1/embeddings` с любыми `options` всегда по ключу по умолчанию.

## 2. Починка

Прокси для BGE-запросов (`/api/embed`, `/api/embeddings`, `/v1/embeddings`;
модель `bge-m3-embed`/`bge-m3-embed-gpu`) убирает из тела `options` и `runner`.
Все потребители работают на ключе модели по умолчанию. GPU-размещение не
теряется: его задаёт Modelfile модели (`num_gpu 999` у `bge-m3-embed:latest`,
`num_gpu -1` у `bge-m3-embed-gpu:latest`), `mmap` — умолчание llama.cpp.

`8e189da` — правка прокси и тестов; `fe02902` — разбор в
`docs/bge-runner-key-20261025.md`; `3010741` — правка авто-обновщика (раздел 3).

## 3. Побочное событие: еженедельный обновщик положил Ollama

В 04:30 воскресенья `ai-stack-update.service` обменял `~/ollama` на новую
версию из архива GitHub, но не перенёс `gpu-policy/` и `request-watch/`.
ExecStartPre (`install.py`) и прокси наблюдения оказались не на месте,
`ollama.service` ушёл в цикл рестартов. Откат не сработал: `systemctl --user
restart ollama` стоял **вне** `try`, исключение уходило наверх, и система
осталась с неполной новой установкой.

Ollama лежала ~13 минут (04:30–04:33): эмбеддинги RAGFlow и TaskFlow не
работали. Возврат: старая установка `~/ollama-0.40.3` цела — переименование
обратно, юнит поднялся сам, прокси продолжил работу. Новая версия (0.40.11)
оставлена рядом в `~/ollama-0.40.11.failed`, на боевой порт не переключалась.

Правка обновщика (`3010741`): живая часть установки переносится в новую версию;
`systemctl restart` и проверка внутри `try`, откат выполняется при любой ошибке;
прежняя копия той же версии уводится в `.prev-<время>`, чтобы не блокировать
переименование.

## 5. Как это делать из агентской сессии (tfrole)

- Журнал пользовательских юнитов `maksim` недоступен (`/var/log/journal/*/user-1000.journal`,
  sudo не выдан) — читается контейнером с `journalctl --directory=/journal
  _SYSTEMD_USER_UNIT=ollama.service`.
- Перезапустить пользовательский юнит из агентской сессии нельзя
  (`systemctl --user` → «Access denied»). Для `ollama-request-watch.service`
  (Restart=always) работает убийство процесса прокси; для `ollama.service` —
  починка файлов, юнит поднимается сам в цикле рестартов.
