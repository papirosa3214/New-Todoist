# Доставка уведомлений: сбой 23→24.10.2026 и что сделано

## Что было
Утренняя сводка 24.10 написала: «у отправителей НЕ УШЛО 7, сорвалось у посредника: 47,
последняя причина — нет ответа, curl вернул код 28, вытянуто повтором: 10».

Живой разбор журналов:
- окно сбоя — 23.10 23:00 … 24.10 00:46;
- в это же время `xray-target-guard` писал «ни один сервер не пускает к цели» — лежал
  весь прокси-стек, а не только Telegram-нога;
- посредник `tg-relay` ходил в Telegram ТОЛЬКО через SOCKS `xray-bots` (10810) — 47
  отправок сорвались с кодом 28 (таймаут);
- n8n и посредник при этом были живы: сломан был путь наружу.

## Почему это плохо
Канал тревог не был охраняем: `infra-vpn-watch` смотрел на `xray-claude` (10813) и про
`xray-bots` (10810) — тот, через который идут тревоги, — не знал вообще. Сбой прокси
был виден как «НЕ УШЛО 7» без причины.

## Что сделано
1. **Посредник ходит в Telegram напрямую, когда прокси лежит.** Из сети контейнера
   `api.telegram.org` виден без прокси (ответ 0.17 с); с самого хоста — таймаут. Порядок
   попыток: прокси → напрямую → снова прокси, бюджет времени прежний (≈22 с).
   Правка: `infra-110-verify/tg-relay-direct-route/relay.py` (источник истины —
   `~/n8n-stack/tg-relay/relay.py`, обновление стеком описано в README рядом).
   Образы `n8n-stack-tg-relay` и `n8n-stack-tg-relay-kb` пересобраны, контейнеры
   перезапущены.
2. **Сторож канала тревог** (`infra-vpn-watch`): проверяет оба пути посредника изнутри
   контейнера; тревога поднимается, когда не работают оба; молчание при недоступном
   docker — не ложная тревога.
3. **Честный счётчик в сводке** (`autonomy-report.py`): «сорвалось у посредника: 47
   отправок» + число разных тревог по журналу посредника, а не число строк журнала.

## Проверки
- при мёртвом SOCKS тестовый посредник доставил сообщение по прямому пути (журнал:
  «recovered», маршрут direct);
- живой посредник `127.0.0.1:8099` — сообщение принято Telegram;
- сквозной путь отправитель → n8n → посредник → Telegram — отправка вернула успех;
- `infra-vpn-watch --dry`: оба пути живы, ложной тревоги нет; на мёртвом прокси
  проверка возвращает «не работает», на недоступном docker — «не смогли проверить»;
- `delivery_watch()` на живых данных: «сорвалось 7 отправок (7 разных тревог)».
