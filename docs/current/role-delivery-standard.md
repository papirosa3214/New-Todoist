# Регламент сдачи работы ролями TaskFlow

Утверждён владельцем 11.10.2026. Действует для всех ролей, работающих по карточкам TaskFlow. Стандарт уточняет отчётность и безопасную работу с Git, сохраняет действующий порядок сдачи этапов и проверки.

## Ответственность и границы

Одна карточка — один комплект изменений — один ответственный за итоговый коммит и интеграцию. Ответственного брать из поля «Ответственный за интеграцию» в карточке; не назначать по собственной догадке. Для работы без изменений репозитория — «Не требуется». Исполнители отвечают за свои части, проверяющий — за обоснованный вердикт, указанный ответственный — за сборку изменений карточки, итоговый коммит и перенос принятого кода в основную ветку.

До правки прочитать карточку, границы, текущую ветку и состояние рабочего дерева. Зафиксировать, какие файлы или участки относятся к своему этапу. Изменения сервера разных карточек изолировать в worktree на карточку; роли одной карточки могут работать в её общем worktree, согласовав участки. Нативный TaskFlow имеет единственный исходный каталог на Mac: соблюдать AGENT-CYCLE.md и реестр границ, пересекающиеся правки выполнять последовательно. Общий каталог не даёт права на чужие файлы и изменения.

## Передача своей части

Каждая роль передаёт: что сделала, какие файлы/участки изменила, на какой ветке и исходном состоянии, какие проверки провела, где доказательства, что осталось и кому передано. Список файлов дополнять описанием участков, если файл меняли несколько участников. Сдавать свой этап предусмотренным инструментом с коротким `result` и `report_markdown`; структурный `artifact` сохранять для передачи следующей роли. Итоговый коммит выполняет указанный ответственный. Отсутствие интеграции ещё не запрещает обычную сдачу разработки и не создаёт нового барьера проверки.

## Человекочитаемый отчёт — сразу при сдаче

Полный отчёт сохранить через `taskflow_doc_write` в документации задачи до сдачи на проверку; в кратком результате дать ссылку. Для исполнения карточки инструмент кладёт документ в папку задачи. `report_markdown` также передать при сдаче этапа (либо `artifact.report_markdown`); критик — вместе с настоящим вердиктом через `taskflow_review`. Короткая сводка в чате и машинный `artifact` не заменяют сохранённый отчёт. Обновлять существующий отчёт по мере доработки; не создавать заново одинаковые документы.

Писать для владельца продукта: понятный итог в первом предложении, затем короткие содержательные разделы:

- **Результат:** что теперь работает и что это меняет для пользователя.
- **Что сделано:** изменения поведения; состав правок своей части.
- **Проверки:** конкретный сценарий, ожидаемый и наблюдаемый результат, точные количества, среда. Различать исходники, тестовую копию, симулятор, физическое устройство и живой сервис. Зелёная сборка не доказывает пользовательский сценарий.
- **Ограничения:** что осталось, не проверено или не применено, точная причина и следующий ответственный. Если ограничений нет — сказать прямо.
- **Материалы:** прямые ссылки на документы, кадры и результаты тестов; репозиторий, ветка, коммит и статус интеграции/выкладки, когда применимо. Полные логи вынести из основного текста.

Точные имена файлов и SHA уместны в Материалах; основной текст должен быть понятен без знания кода. Простая работа требует короткого отчёта; сложная — достаточного объяснения, чтобы не собирать контекст заново. Использовать обычные заголовки `## Результат`, `## Что сделано`, `## Проверки`, `## Ограничения`, `## Материалы`.

## Безопасный итоговый коммит

Указанный ответственный сверяет фактический diff с карточкой и передачами исполнителей. Подготавливает только её изменения: явные пути, а при смешанных изменениях одного файла — только согласованные участки. В общем грязном каталоге запрещены `git add .`, `git add -A` и `git commit -a`. Явное имя файла само по себе не гарантирует безопасность: если в нём смешаны изменения разных карточек, сначала разделить их.

Перед коммитом проверить `git diff --cached`, `git diff --cached --check` и список подготовленных файлов; после — состав и SHA коммита. Чужие изменения не откатывать, не прятать через reset/stash, не включать попутно и не исправлять без поручения. Не переключать грязное или живое дерево. Если состав изменений нельзя однозначно разделить, прекратить Git-операцию, описать конкретный конфликт и согласовать границу с ответственным; не угадывать принадлежность.

После объединения частей проверить именно собранный результат. Перенос принятого кода в main выполняет назначенный участник в действующем порядке. Перед интеграцией/перезапуском сервера проверить отсутствие выполняющихся ходов и очереди. Push, установка и выкладка — в рамках поручения и правил проекта. Не выдавать рабочую ветку за main, main за выкладку, установку за проверку устройства. Карточку за владельца не закрывать.

## Итог всей карточки

Ответственный собирает из отчётов этапов один актуальный итоговый документ: общий результат, проверки совместного результата, ссылки на материалы, точные коммиты и состояние применения. Он обновляет его после интеграции/выкладки и связывает с карточкой. Если работа ещё не перенесена или не применена, прямо указывает причину и ответственного. Владелец и следующая роль должны получить готовый контекст, а не восстанавливать его по переписке.

Это общий рабочий стандарт, а не новый слот, JSON-контракт, `required_fields` или программный запрет сдачи. Действующие права, маршруты сдачи, проверки и окончательное решение владельца сохраняются.
