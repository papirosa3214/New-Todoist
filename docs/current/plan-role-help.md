# Достройка запущенного плана при нехватке роли

Дата: 08.10.2026. Карточка: 120ab80c-5a28-4d68-8e46-507c86adc5a0.

## Что мешало

taskflow_plan_request был доступен в чатах и старом MCP-пути, но отсутствовал в taskflowTools — фактическом наборе инструментов рабочего запуска роли внутри сервера. Стартовая инструкция предлагала недоступный вызов. Общая инструкция роли одновременно предлагала вернуть работу вне своей компетенции или позвать коллегу на совещание; сообщение не создаёт исполнительный узел.

Даже доступный add_step по умолчанию ставил нового исполнителя после текущего. Если результат коллеги нужен до сдачи своего шага, это оставляло ожидание без возможности продолжить.

## Поведение

Один инструмент taskflow_plan_request доступен всем рабочим ролям. Рабочий запуск ограничивает subtask_id своим текущим слотом; схема, вызов API и описание общие для чата и рабочего runtime.

- add_step: автор может сдать свою часть, чужая работа нужна далее. По умолчанию новый шаг ждёт автора. before позволяет поставить его перед следующими неначатыми шагами, которым нужен результат.
- request_help: чужой результат нужен, чтобы закончить собственную работу. Новый помощник наследует предшественников автора (либо явно заданные after), а автор получает зависимость от помощника.
- rework: существующий сценарий QA/критика «доработка → повторная проверка».

Пример рабочего вызова:

    taskflow_plan_request({
      subtask_id: "<текущий id шага>",
      kind: "request_help",
      role: "researcher",
      expected_result: "Проверить совместимость выбранной библиотеки",
      reason: "Без результата исследования реализацию завершить нельзя"
    })

При применённом request_help сервер в той же транзакции:
1. Добавляет узел и обычную подзадачу помощника.
2. Сохраняет технический снимок автора и закрывает его текущую попытку.
3. Оставляет done=0, переводит автора в blocked/dependency.
4. Через существующий unlockReadyPlanSubtasks запускает готового помощника.
5. После сдачи помощника liftDependencyBlocks снимает ожидание и запускает тот же исходный слот. Его сессия сохраняется; результат помощника доступен в сводке предыдущих шагов и карточке.

Роль завершает текущий ход без сдачи своего шага, release и повторной блокировки. Технический блок зависимости отличается от отказа и не требует ручного запуска владельцем.

## Ограничения

Роль достраивает только собственный идущий шаг утверждённого плана. Граф остаётся ациклическим; неизвестная/недоступная роль отклоняется. Чужие и сданные шаги не меняются. Исключение для входящей связи начатого шага действует только при явном request_help.

Прежние лимиты сохраняются: до 12 узлов по инициативе ролей и до 3 добавленных шагов одной роли. Превышение возвращает proposed: граф и состояние автора не меняются, помощник ещё не назначен. Автор фиксирует ожидание решения владельца; при одобрении создаются помощник и зависимость. Нельзя считать proposed исполненным делегированием.

API отклоняет before для request_help: исходный слот он связывает сам. Причина запроса обязательна. Уже подходящего исполнителя в графе не надо дублировать.

Инструкция для рабочего слота явно сильнее общего совета вернуть чужую работу: сначала достройка графа и проверка ответа. Совещание и консультация не заменяют исполнительный узел.

Тесты проверяют закрытие попытки автора, отсутствие преждевременного завершения плана, отказ при фиктивной сдаче, запуск после помощи, чужой слот, цикл, неизвестную роль и предложение сверх лимита с последующим одобрением.

Карточка регистрации работы автоматически попала в существующий конвейер: её Архитектор завершил ход и зафиксировал уже подготовленное изменение в этом worktree. Вливание и перезапуск допустимы после проверки отсутствия идущих запусков. Для будущего опыта: план без необходимого исполнителя → явная потребность другой роли → request_help → результат помощника → продолжение исходной роли → полный итог. Проверить вызов инструмента, граф, ленту и результат, а не только завершение хода модели.
