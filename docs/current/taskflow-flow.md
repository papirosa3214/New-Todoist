## 4. Приём (`applyIntakeToNewTask`)

Вызывается из `POST /api/tasks` без ожидания [код] `routes/tasks.ts:1100`. Решает **настройка владельца** `users.task_intake_mode` — не того, кто создал карточку.

1. Родитель-контейнер (есть дети) сам не исполняется, приём пропускается.
2. Подбор роли: если не выбрана владельцем (`owner_selected_role`) и нет исполнителя — модель выбирает роль, пишется `machine_selected_role`; «личное» → исполнитель владелец, дальше ничего.
3. **Режим `manual`** — приём здесь останавливается: предложенная роль видна, флаг и раздача за владельцем.
4. **Режим `automatic`** (сейчас так [база]) — если у карточки нет черновика плана, сервер ставит `ready_for_pickup=1` и тут же вызывает `dispatchTaskToPi` → **одиночный запуск**.
5. Тумблер «Система» = `task_intake_mode`. Включение «Системы» догоняет и прошлые карточки (`sweepStragglers`).

⚠️ **[вывод] Автоприём обгоняет подготовку плана.** Приём стартует мгновенно, подготовка плана (§5) идёт воркером с вызовом модели. К её приходу карточка уже `ready_for_pickup=1`, поэтому подготовка пропускает её (`protectedTask`). В базе: подготовок `skipped` — 40, `ready` — 4, `superseded` — 13 [база]. То есть в автоматическом режиме командный план почти не появляется сам — работа уходит одной роли. Это объясняет находки А6/Е1 («14 задач ушли одной ролью без проверки»).

## 5. Подготовка (автоподготовка плана)

`runtime/autoPreparation.ts`, воркер раз в секунду (`TASKFLOW_AUTO_PREPARATION=0` отключает) [код].

- Берёт задачу из очереди, спрашивает модель: достаточно ли постановки, кто участники, какие зависимости.
- Результат: **черновик плана** (`task_collaboration_plans`, status `draft`) **или** вопрос владельцу (`needs_clarification`) **или** предложение разбить на дочерние карточки (`structure_review`, согласует владелец через `/preparation/approve-structure`).
- Не трогает: задачи без проекта, с флагом готовности, с исполнителем-выбором владельца, с утверждённым планом, с идущей работой, с планом, составленным вручную.
- В конце — уведомление владельцу `preparation_ready`.

## 6. Выбор схемы: две дороги, взаимно исключающие друг друга

| | **План команды** | **Одиночный запуск** |
|---|---|---|
| Как возникает | `POST /collaboration-plans` (вручную/оркестратор) или `/propose`, либо черновик подготовки; **утверждает** владелец или оркестратор | флаг готовности (владелец или автоприём) → `dispatchTaskToPi`, либо кнопка «Запустить» `POST /api/tasks/:id/run` |
| Что получается | подзадачи-**узлы** (`subtasks.collaboration_plan_id`, `plan_node_key`), граф зависимостей, свои роли, ветка git | одна роль на задачу целиком, задание в `role_run_jobs` |

| Другую схему | блокирует: одиночный запуск → 409 «выбран план» | блокирует: план → 409 «выбран одиночный запуск» |

[код] `dispatch.ts:dispatchTaskToPi`, `task-collaboration-plans.ts:approve`, `taskExecutionState`. Поднятие флага владельцем при `draft`-плане гасит этот черновик (`superseded`).

## 7. Исполнение: план команды

1. **Утверждение** (`POST …/approve`): владелец/оркестратор. В одной транзакции узлы плана становятся подзадачами; прежние утверждённые планы → `superseded`. Для ветки (родитель + дети) план утверждается на родителе одним действием (`approveBranch`).
2. **Автостарт**: узлы без входящих рёбер запускаются сразу (`startPlanSubtaskRun`); остальные открываются по мере того, как предшественники сданы (`unlockReadyPlanSubtasks`).
3. **Условие открытия узла** (`canPlanSubtaskBecomeReady`): не осталось невыполненных зависимостей задачи, не осталось незавершённых дочерних, все предшественники `done=1` (для узлов с артефактом — версия артефакта в нужном статусе).
4. **Запуск узла**: заводится попытка (`attempts`), `subtasks.agent_state='in_progress'`, роль запускается внутри процесса сервера (`runRoleInProcess`) — **напрямую, не через очередь `role_run_jobs`**.
5. Правило узла: ИИ может взять и закрыть только узел **своей** роли и только после открытия предшественников (`planNodeAgentRefusal`).
6. Максимум узлов в плане — 16, доработок — 2 круга (`MAX_PLAN_NODES`, `MAX_REWORK_ROUNDS`).

## 8. Исполнение: одиночный запуск и очередь

`role_run_jobs` — надёжная очередь в SQLite: постановка в той же транзакции, дедупликация, атомарный захват, аренда с пульсом, повтор с задержкой, статусы `dead/skipped/cancelled` [код] `roleRunQueue.ts`.

- **Воркер**: по умолчанию **3 полосы** одновременно (`ROLE_RUN_CONCURRENCY`, решение владельца 05.10) — `roleRunWorker.ts`. Одна карточка — не больше одного запуска сразу.
- **Что кладётся в очередь**: назначение (`assigned`), комментарий владельца роли (`commented`), сдача на проверку (`review`), продолжение после захода (`after_run`).
- **Разбор причины** (`kickRoleTaskStrict`): «Система» выключена и запуск не ручной → откладывается на 30 с; карточка в `review` → Критик (если автопроверка включена и вердикта нет); `blocked` → ждёт владельца; нет состояния → выполнить; `in_progress` после захода → продолжить, но не больше 3 звеньев подряд (`MAX_CHAIN`) и только если был прогресс.
- ⚠️ **[код] Узлы плана в очередь не попадают**, поэтому ограничитель «3 полосы» их не держит. Глобального предела одновременных запусков узлов в прочитанном коде я не нашёл. [вывод] при нескольких одновременно открытых узлах нагрузка на модель/машину ничем не ограничена.

## 9. Что происходит внутри одного захода роли

`runRoleInProcess` [код] `runtime/inProcessRun.ts`:

1. **Модель** — из `role-routing.yaml` по роли. Нет модели → ошибка запуска.
2. **Рабочая папка**: чужой проект — как есть; **репозиторий самого сервера — отдельный git worktree на карточку** `~/.local/state/taskflow-runs/worktrees/<task_id>`, ветка `roles/<task_id>`. Все роли одной карточки работают в одной копии (`roleWorkspace.ts`).
3. **Контекст**: зависимости (`buildDependencyContext`), контекст плана для узла (предшественники и артефакты), сводка через `task_context_bridge.py` (карточка, KB, Mnemosyne), память проекта (`roleProjectContext`), снимок прошлой попытки узла (`slotWorkSnapshot`), накопленные сообщения темы.
4. **Системный промпт** = слой `role.prompt` (БД/файл `role-prompts/<key>.md`) + `local_policy` («ты уже на .110, по SSH на себя не ходи»); снимок записывается в `tasks.composed_prompt_snapshot`.
5. **Инструменты**: встроенные `read/bash/edit/write/grep/find/ls` + `taskflow_*` (внутренние вызовы сервера от имени роли, без постоянного ключа) + Composio/Xcode при необходимости.
6. **Сессия**: ключ `задача+роль` (+ узел) на диске; повторный заход продолжает тот же разговор.
7. **Пульс**: каждые 90 с сервер сам продлевает аренду (`HEARTBEAT_MS`); аренда живёт 5 минут.
8. **Конец захода**: для узла — снимок остановки (роль кратко отвечает «сделано/осталось/блок», иначе пишет сервер); сессия закрывается. Сбой запуска → задача `blocked` «Запуск прервался: …».

⚠️ **[код] Для узла плана после захода нет автоматического продолжения.** `continueOrHandOff` вызывается только когда `subtaskId` пуст (`inProcessRun.ts:~984`). Если роль закончила ход, не сдав узел (пустой ответ модели, лимит провайдера), узел остаётся `in_progress` без живого запуска — пока не сработает восстановление при перезапуске сервера или рука оркестратора. Это очень похоже на причину находок А10/А21 («повисший шаг»).

## 10. Сдача и проверка

**Сдача шага**: `subtask_done` с `result` (обязателен, ≤400 символов; без него 400). Закрытие узла сразу открывает следующие по графу.

**Сдача задачи (план)** `finishPlanIfComplete` [код]: все узлы плана `done=1` → создаётся версия результата, задача `agent_state='review'`, уведомление автору, проверка родителя (`admitParentAfterChildren`).

**Сдача задачи (обычная)** `routes/subtasks.ts`: последний шаг закрыт и задача у агента `in_progress` → `review`.

**Критик/автоприёмщик.** Два независимых включателя:
- `users.reviewer_first_default` (владелец) — **сейчас 0** [база];
- `tasks.requires_reviewer_review` (карточка) — по умолчанию 0 [код].

Оба должны быть «да», чтобы сервер **сам** добавил итоговую проверку (`ensurePlanFinalReviewer`). Сейчас автоматического Критика нет нигде. Критик появляется, только если **оркестратор поставил его последним узлом плана** [решено 05.10]: терминальный узел критика сервер превращает в итоговую проверку (`queuePlanFinalReview` → задание `review` в очередь → заход критика в режиме `review`).

**Вердикт** `POST /api/reviews` [код] `routes/reviews.ts`: только владелец или Reviewer (критик). Нужна актуальная версия результата и хэш артефакта. Вердикты: `approved`, `changes_requested`, `blocked`.
- `changes_requested` с `rework_steps` (ключ первого неверного этапа): сервер клонирует затронутую цепочку узлов, добавляет повторную проверку, задача возвращается в `in_progress`. Лимит — 2 круга; дальше `blocked` «требуется решение владельца».
- Критик одобрил дочернюю карточку ветки → она сама `completed`; корневая — ждёт владельца.
- Вердикт пишется комментарием и уведомлением владельцу; дубль в 60 с отсекается.

⚠️ **[код/вывод] Вердикт «не готово» у QA — не то же самое, что `changes_requested` Критика.** Доработку запускает только вердикт через `/api/reviews` с `rework_steps`. Если QA нашла дефекты, а Критик «одобрил вердикт QA» вместо `changes_requested`, план просто закончится (находка А20).

## 11. Приёмка

- Задачу закрывает **только владелец** (`PATCH status` → 403 всем остальным). Оркестратор не закрывает и не удаляет.
- Итог по карточке пишется заметкой в документацию проекта (`writeOutcomeNote`, `lib/taskOutcome.ts`): вердикт, результаты узлов, документы, ветка с коммитом.
- Объёмная задача (дети или ≥5 шагов): исполнитель кладёт **отчёт по задаче** в документацию проекта до сдачи в `review` (`AGENT-PROTOCOL.md`, «Отчёт по задаче»).

## 12. Вливание кода

**Автоматического вливания нет.** Правки лежат в ветке `roles/<task_id>`; в живой `main` их переносит человек или оркестратор: `git merge --no-ff roles/<id>` [код] `roleWorkspace.ts`, комментарий в шапке; `taskOutcome.ts` только показывает, сколько коммитов опережает ветка.

- Роли часто **не коммитят** — результат лежит в worktree незакоммиченным (находка А18); нужно проверить перед вливанием.
- Живой сервер запущен как `tsx watch` из этого же дерева: **любое вливание в серверную часть перезапускает сервер и рвёт идущие запуски**. Поэтому серверный код вливают только при пустой очереди [решено].
- Сейчас: 53 worktree, 51 ветка `roles/*` [база/git] — остатки, никем не чистятся.

## 13. Дети, родители, зависимости

- **Родитель-контейнер** не исполняется; его работа — сборка итога детей. Когда все дети на `review`/`completed` и у родителя есть свои невыполненные пункты, родитель получает флаг и раздаётся тем же путём (`admitParentAfterChildren`, только в `automatic`).
- **Зависимости** (`task_dependencies`, policy `completed`): незавершённая зависимость не даёт узлу открыться; воркер подготовки раз в секунду перепроверяет `unlockDependencyPlans`.
- **Ветка** (родитель с детьми): план утверждается одним действием на родителе; дочерние ссылаются на него (`branch_plan_members`). Дочерняя карточка отдельного плана на себя не утверждает (409, ссылка на родителя).
- **Очерёдность дочерних** при одиночных запусках: `releaseQueuedSuccessors`, когда предыдущая завершена.

## 14. Аренда, молчание, сбои и восстановление

| Что | Как | Где |
|---|---|---|
| Аренда задачи/шага | 5 минут от последнего сигнала; истекла → «агент пропал» (вычисляется при чтении, не хранится) | `agentState.ts`, `AGENT-PROTOCOL.md` |
| Аренда задания очереди | пульс, при смерти процесса — `recoverExpiredRoleRunJobs` при старте воркера | `roleRunQueue.ts` |
| Узел плана «в работе» при старте сервера | попытка закрывается `interrupted`, роль пишет в ленту «ход оборвался», продолжает тот же разговор; второй обрыв за 30 мин → `blocked` | `recoverInterruptedPlanSubtasks` |
| Узел плана в `todo`/`blocked` после падения | **не поднимается** (только `in_progress`) → ручной сброс | находка А10 [код подтверждает] |
| Технические блокировки | планировщик: повтор до 3 раз, потом `dead` | `scheduler.ts` ветка 1 |
| «Не моя роль» | роль вызывает `release`, переподбор, нет кандидатов → `dead` | `release.ts`, ветка 2 |

## 16. Чаты, память, интеграции

- **Чат задачи / тема плана** (`projectTopics`, `slotConversation`): обсуждение этапа ролью только на чтение и обсуждение, работа не возобновляется; сообщение доставляется работающему узлу или разговорному ходу. Оркестратор состоит во всех темах.
- **Чат координации агентов** (`chat_messages`): два канала — `agents` (рабочий) и `owner` (окно постановки Секретаря). Агенты владельцу напрямую не пишут; ответ владельцу разрешён на личное обращение, сутки. Подробно — `AGENT-PROTOCOL.md`.
- **Роль-чат** (`routes/chats.ts` → `PiRuntimeAdapter.startChatRun`): память «чат+роль», последние 20 сообщений, краткий промпт. С задачей напрямую не связан (кроме слот-обсуждения).
- **Память/знания**: `taskflow_kb_search`, Mnemosyne, документация проекта (`taskflow_doc_*`), итог задачи.
- **Внешние агенты**: MCP `taskflow` и HTTP-API (`AGENT-API.md`), `claim` / `heartbeat` / `state`; взять командную карточку нельзя («назначения выполняет сервер»).
- **Linear/Composio**: роли подключают через `composioRuntime`; отметки оркестратора в Linear — через коннектор владельца.
- **Уведомления**: действия задач владельцу в уведомления не дублируются (лента активности); остаются комментарии, вердикты, сдача, сводки.

**Уведомления без дублей ленты.** Действия задач (assigned, commented, reviewed, agent_state) не дублируются в уведомлениях владельца (миграции 068/069, независимо от писателя); `GET /api/notifications` скрывает старые дубли без удаления записей, WebSocket не шлёт владельцу `notification:new` для подавленной записи. Лента, комментарии, вердикты, уведомления о завершении, служебные уведомления и адресные сигналы исполнителям сохраняются.

## Вырезание одиночного запуска: карта (по коду, 05.10.2026)

**Идея.** Всё, что сегодня зовёт `dispatchTaskToPi` или ставит задание `assigned`, вместо этого создаёт план из одного узла (`single_executor`, роль из подбора), сразу утверждает его и стартует узел (`startPlanSubtaskRun`). Появляется одна внутренняя функция «план из одного шага по задаче»; все точки входа зовут её.

**Точки входа, которые переводятся на неё** [код]:

| Где | Что сейчас |
|---|---|
| `routes/dispatch.ts:applyIntakeToNewTask` (строка ~654) | автоприём: флаг + раздача |
| `routes/dispatch.ts` `/api/tasks/:id/dispatch` | ручная раздача владельцем |
| `routes/dispatch.ts:admitParentAfterChildren`, `releaseQueuedSuccessors` | родитель после детей, следующая в очереди |
| `routes/tasks.ts` PATCH `ready_for_pickup` (строки ~1490–1510) | флаг владельца: задание или раздача |
| `routes/manual-run.ts` `POST /api/tasks/:id/run` | кнопка «Запустить исполнителя» |
| `lib/ownerDraft.ts` (строки ~486, 601, 606) | допуск дерева Секретаря, «✓ Идёт» |
| `lib/diagnosticDispatch.ts` | карточки инфра-тревог |
| `routes/agent-state.ts` (~1184–1193) | раздача после перехода состояния |
| `runtime/scheduler.ts:launchRole` | запуск по расписанию (ветка 4, и так не работала) |

**Решение Максима 05.10.2026: девять входов сводятся к трём, все три остаются.**
1. **Действие владельца** — флаг готовности, `/dispatch`, `/run`, «✓ Идёт» объединяются в одно «Запустить»; работает и при выключенной «Системе».
2. **Допуск системой** — автоприём, родитель после детей, следующая в очереди, допуск дерева Секретаря, диагностические карточки идут через одну функцию допуска, которая сама проверяет «Систему».
3. **Расписание** — **не удаляется**: ветка 4 планировщика (`launchScheduled`/`launchRole`) остаётся, только запускает через ту же функцию «план из одного шага»; включение (взять `run_at` из `due_date`+`start_time`) — на этапе наращивания.

Вход в `agent-state.ts` (~1184) — выяснить, нужен ли он, до переключения.

**Что уходит или сильно меняется:**
- `runtime/taskExecutionState.ts` — исчезает различие `scheme: single | team`; `can_launch` / `can_use_plan` / `can_change_executor` пересчитываются (409 «выбран одиночный запуск» исчезает).
- Задания очереди `assigned` и `commented` для задач-одиночек; `kickRoleTaskStrict` остаётся для итоговой проверки (`review`) и ответа роли владельцу; цепочка `after_run` (`MAX_CHAIN`) нужна только пока не будет автопродолжения узла (пункт 9 части II) — **выкинуть нельзя, пока этот пункт не сделан**.
- Правка ролей `release` / `repick-role` / ветки планировщика 2–3 («не моя роль»): в плане роль задана узлом, смена — через `planMutations` (`update_step`), не через переподбор по задаче.
- Поле `role_run_jobs.manual_start` и проверка «владелец запустил при выключенной Системе» — переосмыслить (см. ниже).
- Клиенты: веб `TaskDetailScreen.tsx`, `TaskRow.tsx`, `TaskBoard.tsx`, `src/api/tasks.ts`; iOS-клиент (поле `execution.scheme`, кнопка «Запустить») — отдельный репозиторий, править отдельной карточкой.
- Тесты: затронуто около 30 файлов `server/test` (`readyDispatchBridge`, `dispatchRoleChoice`, `taskExecutionState`, `collaborationPlanVsExecutor`, `readyFlag`, `parentAdmission`, `ownerDictation`, `manualRolePick`, `diagnosticDispatch`, `serverSystemControl` и др.).

**Новая находка при составлении карты [код].** Тумблер «Система» сейчас гасит только запуски через очередь (`kickRoleTaskStrict`). Узлы плана (`startPlanSubtaskRun`, `unlockReadyPlanSubtasks`) его **не проверяют**: утверждённый план идёт дальше при выключенной «Системе». Когда всё станет планом, этот разрыв превратится в дыру — **в новую внутреннюю функцию нужно сразу заложить правило**: при `manual` запускает только явное действие владельца (утверждение плана или кнопка), автоматические продолжения цепочки не стартуют. Какое поведение нужно для уже утверждённого плана при выключении «Системы» — решить отдельно.

**Порядок (чтобы не уронить работающее):**
1. Узлы получают автопродолжение и общий предел параллельности (пункты 8–9), иначе после вырезания «обрыв» превращается в вечное зависание.
2. Новая функция «план из одного шага» + тесты на ней.
3. Переключение точек входа по одной, каждая — отдельный коммит.
4. Удаление `dispatchTaskToPi`-пути, заданий `assigned`, схемы `single` в `taskExecutionState`, клиентов, затем тестов.
5. Влить серверную часть только при пустой очереди (правило из §12).
