# Сессии владельца: снимок и лента событий — где граница согласованности

14.11.2026. Относится к серверным сессиям разговора владельца
(`server/src/routes/owner-sessions.ts`, `runtime/ownerSessionRuntime.ts`,
`runtime/ownerSessionEvents.ts`). Чатов ролей и веб-клиента не касается.

## Задача

Клиент восстанавливается после обрыва так: берёт снимок сессии
(`GET /api/sessions/:id`) и дальше доигрывает события. Снимок курсора не
содержал, поэтому клиент выбирал точку сам и платил за это либо повтором
уже показанного текста (снимок + те же события), либо потерей головы
ответа, который в момент снимка ещё стримился. Простое «вернуть рядом со
снимком текущий курсор» без гарантии атомарности — ложный контракт: между
чтением записей и чтением курсора может пройти событие, которого в снимке нет.

## Что доказано про порядок Pi (1.5.0)

`server/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js`,
`_handleAgentEvent`:

1. `await this._emitExtensionEvent(event)` — расширения (нас не касается).
2. `this._emit(event)` — **синхронный** обход слушателей; возвращаемые промисы
   не ожидаются. Здесь событие попадает в `OwnerSessionEventBuffer.push`.
3. `sessionManager.appendMessage(event.message)` →
   `_appendEntry` → `appendFileSync` — **синхронно, в том же продолжении**,
   без единого `await` между пунктами 2 и 3.

`entry_appended` для остальных записей (`_commitBoundaryDrafts`,
`_appendCustomMessage`, `appendContextEdit`, virtual-model state) выдаётся
**после** записи; `message_end` — единственный, кто идёт впереди записи, и
только внутри одного синхронного блока.

Отсюда: однопоточный Node не может выполнить обработчик HTTP в промежутке
между `_emit` и `appendMessage`. Значит курсор, прочитанный обработчиком,
всегда либо раньше события, либо уже после записи — промежуточного
состояния «событие отдано, записи нет» не наблюдает никто.

## Контракт (обратно совместимый: только новые поля)

`GET /api/sessions/:id` → `session` дополнительно несёт:

| Поле              | Смысл                                                              |
| ----------------- | ------------------------------------------------------------------ |
| `eventCursor`     | точка в ленте на мгновение снимка, строка `<epoch>:<seq>`          |
| `eventCursorEpoch`| та же эпоха ленты отдельно (эпоха меняется при перезапуске сервера) |
| `eventCursorSeq`  | тот же номер отдельно: сравнение чисел, без разбора строки          |

Гарантия: **всё, что в ленте не новее `eventCursor`, уже есть в
`session.entries`**. Обратное неверно намеренно: событие, которое успело
уйти вперёд записи, окажется новее точки и придёт событиями ещё раз —
потерять текст нельзя, повторить можно.

Источник точки — `OwnerSessionEventBuffer.boundary()`. Она читается
**первой** в том же синхронном блоке, что и записи
(`OwnerSessionRuntime.snapshotWithBoundary`, `readSnapshot`). Порядок
«сначала точка» — защита на будущее: если в блок когда-нибудь попадёт
`await`, худший исход — повтор события, а не пропавший текст.

Каждое событие тоже несёт `epoch` и `seq` рядом с `cursor`.

### Правило клиента (iOS)

1. Снимок — основа. `session.entries` рисуются как есть.
2. Дальше применяются только события с `seq > eventCursorSeq` **при
   совпадении `epoch`**. Событие с другой эпохой или меньшим `seq` —
   уже показано, пропускается.
3. `epoch` не совпал → перечитать снимок.
4. Догон после обрыва: `GET /api/sessions/:id/events?after=<eventCursor>`.
   Ответ — ровно стык, без повторов.

`GET /api/sessions/:id/events`:

- `resetRequired: false` — `events` новее переданного курсора;
- `resetRequired: true` — курсор вытеснен из буфера (512 событий) или из
  другой эпохи: приходит `snapshot` (с его `eventCursor`), а `events`
  содержит **только** то, что новее точки снимка. Раньше здесь отдавались
  все удержанные события, включая уже вошедшие в снимок, — текст задваивался;
- курсор `<epoch>:0` (начало эпохи) сбросом не считается.

`GET /api/sessions/:id` подключает ленту (`ensureForwarding`) **до** чтения
снимка: иначе события между снимком и подпиской не попали бы ни в снимок,
ни в буфер.

## Что осталось ограничением (не выдаётся за решение)

- Лента живёт в памяти: перезапуск сервера — новая эпоха, клиент перечитывает
  снимок. Курсоры между эпохами не сравниваются, это и есть смысл `epoch`.
- События дальше 512 в прошлое не достаются — только снимок.
- Частичный ответ, который в момент снимка ещё стримится, в снимок не входит
  (Pi пишет только на `message_end`). Такой ответ приходит событием целиком
  (`message_end` приносит полный `text` и блоки), поэтому текста не теряется;
  визуально он может «достроиться» с начала.
