# Живой хвост снимка сессии владельца: `session.live` из состояния Pi

14.11.2026. Относится к серверным сессиям разговора владельца
(`server/src/routes/owner-sessions.ts`, `runtime/ownerSessionRuntime.ts`).
Чатов ролей, замороженного веб-клиента и iPhone в этой работе не касается:
клиентская часть — отдельное поручение.

## Задача

Клиент восстанавливался после обрыва так: снимок (`GET /api/sessions/:id`) плюс
доигрывание ленты событий. Незавершённый ответ в транскрипт ещё не записан
(Pi пишет сообщение только на `message_end`), поэтому в снимке его нет, и
голову ответа клиент собирал сам по своей очереди событий — со всей её ценой:
ожидание первого куска, потеря середины при вытеснении окна (`eventsLost`),
свой разбор текста на телефоне.

Готовое состояние установленного Pi SDK содержит тот же текст целиком. Серверу
не нужно ничего восстанавливать по событиям: он читает состояние агента и
отдаёт **текущий ответ** рядом с записями, уже размеченным. Это убирает
зависимость показа ответа от полноты очереди событий у клиента, но **не
заменяет** события: шаги хода по-прежнему приходят ими.

## Что доказано про установленную версию (1.5.0)

`server/node_modules/@earendil-works/pi-coding-agent` 1.5.0 +
`@earendil-works/pi-agent-core`:

| Факт | Где |
| --- | --- |
| `AgentSession.state` — это `agent.state` (не копия) | `pi-coding-agent/dist/core/agent-session.js:1052` |
| `message_start`/`message_update` кладут сообщение в `state.streamingMessage` | `pi-agent-core/dist/agent.js:402-406` |
| `message_end` очищает `streamingMessage` и дописывает сообщение в `state.messages` | `pi-agent-core/dist/agent.js:408-410` |
| `tool_execution_start`/`tool_execution_end` ведут `state.pendingToolCalls` | `pi-agent-core/dist/agent.js:412-421` |
| `agent_end`/`finishRun` очищают `streamingMessage` | `pi-agent-core/dist/agent.js:240,356,387,429` |
| «Стоп» тоже даёт `message_end` с частичным текстом (`stopReason: "aborted"`) | `pi-agent-core/dist/agent-loop.js:325,338,376` |
| Состояние меняется **до** вызова слушателей (тех, кто пишет ленту событий) | там же: `processEvents` сначала `switch`, потом `for (const listener of this.listeners)` |

Отсюда: в любой момент, когда обработчик HTTP получает управление, состояние
агента **не старее** последнего отданного события. Читая точку ленты и
состояние в одном синхронном блоке, сервер получает непротиворечивую пару.

## Контракт (только новые поля)

`GET /api/sessions/:id` → `session` дополнительно может нести `live`:

```json
{
  "live": {
    "streaming": true,
    "coverage": "current_response_only",
    "displayText": "Готово: маршрут проверен.",
    "textBlocks": [{ "type": "doc", "doc": { "…": "…" }, "chars": 27, "source": "…" }],
    "thinkingBlocks": [{ "text": "сначала проверю маршрут", "blocks": ["…"] }],
    "toolCalls": [{ "id": "call-1", "name": "bash" }],
    "pendingToolCalls": ["call-1"]
  }
}
```

| Поле | Смысл |
| --- | --- |
| `streaming` | ответ идёт прямо сейчас |
| `coverage` | **явная граница покрытия**: `current_response_only` — снимок знает только текущий ответ ассистента |
| `displayText` | текст ответа для показа: служебный конверт v1 разобран, сырого JSON нет; пробелы не срезаны |
| `textBlocks` | готовая серверная разметка `displayText` (правило «тонкий клиент без нагрева») |
| `thinkingBlocks` | размышление этой части ответа с готовой разметкой |
| `toolCalls` | вызовы инструментов **этого сообщения**: `id` и `name`. Аргументов нет |
| `pendingToolCalls` | идентификаторы инструментов, которые выполняются сейчас (`state.pendingToolCalls`) |
| `envelopeHeld` | ответ пишется конвертом v1 и ещё не дописан: в чат его не отдают (то же правило, что `held: "envelope"` у живых кусков) |

Правила:

- `live` **отсутствует** — незавершённого ответа нет (или сборка Pi состояния
  не отдаёт). Тогда снимок работает ровно как раньше.
- `live` — только `role: "assistant"`: `message_start` Pi отдаёт и для
  результатов инструментов, их снимок живым хвостом не считает.
- `live` исчезает на `message_end`: сообщение к этому моменту уже лежит в
  `entries`, и показывать его дважды нельзя. Так же и на «Стоп»: Pi отдаёт
  `message_end` с частичным текстом (`stopReason: "aborted"`), текст остаётся
  записью ветки, хвост пропадает.
- Пробелы не срезаются: `displayText` — это текст Pi как есть (отступы в
  начале ответа и хвост строки кода значимы). Пустота проверяется по `trim()`,
  но сам текст им не портится.

## Чего `live` не покрывает — и почему точка событий не сдвинута

`live` — это **одно** сообщение ассистента, которое сейчас печатается. В нём
нет:

- предыдущих шагов текущего хода: завершённые сообщения и результаты
  инструментов приходят записями ветки и событиями `message_end` /
  `entry_appended`;
- аргументов инструментов и их результатов: это события `tool_start` /
  `tool_update` / `tool_end`;
- хода незавершённого инструмента: `pendingToolCalls` — только идентификаторы,
  частичный вывод снимок не восстанавливает.

Поэтому **точка снимка не двигается**. Верхнеуровневый `session.eventCursor`
остаётся прежним — с откатом к началу окна стримящегося ответа (см.
`owner-session-snapshot-events.md`). Клиент доигрывает события от неё, как и
раньше. Обещания «всё до конца ленты уже есть в снимке» здесь нет и не будет:
живой хвост его не выполняет, а пропуск событий по такой границе потерял бы
шаги хода.

Порядок чтения — точка, состояние, записи, всё в одном синхронном блоке. Если
в блок когда-нибудь попадёт `await`, худший исход — повтор события (снимок его
уже содержит), а не пропавший текст.

## Правило клиента (для отдельной задачи по iPhone)

1. События применять от `session.eventCursor` — как раньше. Пропускать окно по
   `live` нельзя: в нём нет шагов хода.
2. `session.live` есть → применить его **последним**, поверх собранного из
   событий: он снят в тот же момент и описывает текущий ответ целиком.
   `displayText` / `textBlocks` — ответ, `thinkingBlocks` — размышление,
   `toolCalls` + `pendingToolCalls` — какие инструменты в этом сообщении и что
   ждём.
3. Живые куски несут **весь** текст части (`text`, `blocks`), поэтому
   «заменить, а не дописать» — повтор куска ничего не задваивает.
4. `envelopeHeld: true` → пузырь ответа не начинать: конверт показывают только
   готовой разметкой после `message_end`.
5. `live` нет → прежний путь: снимок + окно событий.

## Чего в SDK нет (не выдаётся за решение)

- **Полной истории шагов в состоянии агента нет.** `state.messages` —
  линейный транскрипт агента (первым идёт системное сообщение), а не дерево
  записей сессии: связи «сообщение → `entryId`» в нём нет, ветвление и
  компакция в нём не видны так, как в `SessionManager`. Поэтому снимок
  дополняется только живым хвостом, а история остаётся из `entries`.
- **Аргументов и результатов инструментов в `live` нет** — они есть
  событиями (`tool_start` / `tool_update` / `tool_end`) и записями ветки.
- **Окно ответа по-прежнему доигрывается** старому клиенту. Это осознанно:
  сдвигать `eventCursor` значило бы обещать покрытие, которого хвост не даёт, и
  терять шаги у клиента, который про `live` не знает.
- **`eventsLost` больше не означает потерю головы**, если `live` пришёл: текст
  текущего ответа есть в хвосте. Шаги, вытесненные из буфера **до** снимка,
  хвост не возвращает — там только текущее сообщение.

## Сопоставление `todo`: официальный пример Pi и установленный rpiv-todo

Два расширения с одним именем инструмента и **разной** формой `details`:

| | Официальный пример Pi (`examples/extensions/todo.ts`) | Установленный `@juicesharp/rpiv-todo` 2.10.0 |
| --- | --- | --- |
| Инструмент | `todo` | `todo` (имя закреплено: «DO NOT rename», `tool/types.ts`) |
| Действия | `list` / `add` / `toggle` / `clear` | `create` / `update` / `list` / `get` / `delete` / `clear` |
| Задача | `{ id, text, done }` | `{ id, subject, status, activeForm, blockedBy, owner, metadata }`, статусы `pending/in_progress/completed/deleted` |
| `details` | `{ action, todos, nextId }` | `{ action, params, tasks, nextId }` |
| Где живёт список | в `details` результата, переигрывание ветки | память процесса по номеру сессии (`state/store.ts`) + `details` как снимок для переигрывания (`state/replay.ts`) |
| Проверка формы | — | `isTaskDetails`: `Array.isArray(tasks) && typeof nextId === "number"` |

Сервер читает **форму rpiv** (`runtime/ownerSessionTodos.ts` →
`isOwnerSessionTodoDetails`, те же ключи, что у `isTaskDetails`). Поэтому:

- **Автоматической подмены нет и не будет**: если однажды в сессию попадёт
  официальный пример, его `details` не совпадёт по форме, список честно
  ответит `available: false` — не пустым списком и не падением. Это тихое
  «списка нет», и его видно по `available`, а не по ошибке.
- Ставить один вместо другого — решение владельца, а не следствие правки
  кода. Оба расширения регистрируют имя `todo`, поэтому одновременно их
  подключать нельзя.
- `~/.pi/agent/extensions/taskflow-todo-mirror.ts` в сессиях владельца не
  грузится: это зеркало карточек в обратную сторону, не источник списка.
