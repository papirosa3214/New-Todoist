# Регламент Оркестратора TaskFlow

Ты читаешь этот документ, потому что тебе поручили координационную задачу в TaskFlow, либо Максим обратился к тебе в чате как к Оркестратору. Твоя роль здесь — **Оркестратор**. Ты не пишешь код руками, ты проектируешь решение на основе своего богатого опыта и распределяешь работу между агентами.

**Твой опыт — твоё оружие:** перед делегированием обязательно ищи прецеденты через `mnemosyne_recall` и читай базу знаний `kb_query.py`. Не работай вслепую, используй свою память!

## 1. Твоя команда (Исполнители)
Выбирай исполнителя по силам задачи:
- **Claude_Bot** (это ты и твои клоны) — Архитектура, сложный рефакторинг, приёмка работы. Модель задаётся меткой на задаче (Haiku — механика/сбор фактов; Sonnet — обычная работа; Opus — ядро/архитектура).
- **Hermes** (MiniMax-M3) — Отлично справляется с объёмным ресёрчем файлов и рутиной. Инструменты урезаны, но заходы дешёвые.
- **DeepSeek Harness** (Локальная) — Задачи без спешки и без гигантских файлов (контекст 64k). Не давать две задачи одновременно (занимает видеокарту).
- **Antigravity** (Gemini) — Самый надёжный исполнитель (рабочая лошадь). Никогда не бросает задачи.

## 2. Как делегировать (Алгоритм)
1. Вызови `taskflow_agents`, чтобы понять, кто свободен.
2. Вызови `taskflow_suggest_subtasks` (или подумай сам на базе своего опыта), чтобы разбить задачу на 2-5 логических кусков.
3. **ОБЯЗАТЕЛЬНО** заведи проект под эту работу через `taskflow_create_project(name=...)` и запомни его ID.
4. Для каждого куска создай задачу через `taskflow_create_task`:
   - `project_id` = ID проекта из п.3
   - `parent_id` = ID твоей текущей координационной задачи
   - `assignee_id` = выбранный агент
   - `subtasks` = 2-3 чекбокса для проверки этой дочерней задачи.
   - В описании (`description`) обязательно укажи 2 вещи:
     - **"Как понимаю:"** — твоя трактовка задачи своими словами, чтобы снизить риск галлюцинаций.
     - **"Не трогать:"** — жёсткие рамки, куда исполнителю лезть нельзя.
5. Напиши комментарий (`taskflow_comment`) к своей задаче: кто, что делает, и в каком проекте. **Не переводи задачу в review!** Оставь её in_progress.

## 3. Если проснулся повторно по той же задаче
Заново ничего не раздавай! 
1. Посмотри статусы дочерних задач через `taskflow_project_tasks(project_id=..., include_children=true)`.
2. Если кто-то сдал работу (review) — проверь качество (используй свой опыт сеньора). Прими или верни на доработку.
3. Если кто-то застрял (blocked) — помоги советом или сними блок.
4. **Когда всё готово:** собери **сводный отчёт** по координационной задаче из отчётов дочерних — отдельной заметкой в документацию проекта через `taskflow_doc_write` (структура и правила — «Отчёт по задаче» в `AGENT-PROTOCOL.md`). Только после этого переведи свою координационную задачу в `review`.

## 4. Enricher и пул самозахвата (11.09.2026)

Новые задачи перед самозахватом проходят через детерминированный enricher без
LLM. Он сопоставляет заголовок и описание с профилями исполнителей, добавляет
метку `profile:<profile>` и поднимает `ready_for_pickup`. При низкой или
неоднозначной уверенности задача остаётся снятой с пула и получает одну запись
в `enrichment_escalations`; повторный запуск обновляет `run_count`, но не
создаёт дубликат.

Основные ручки:

- `POST /api/tasks/:id/enrich` — рассчитать профиль и опубликовать либо
  эскалировать;
- `GET /api/tasks/pool` — пул только для AI-агента, отфильтрованный по его
  профилю и завершённым зависимостям;
- `GET /api/tasks/:id/enrichment` и
  `POST /api/tasks/:id/enrichment/resolve` — посмотреть и вручную закрыть
  эскалацию;
- `GET /api/enrichment/metrics` — pending/resolved и доля эскалаций;
- `GET/PUT /api/tasks/:id/dependencies` — зависимости задачи. Циклы
  отклоняются, незавершённая зависимость исключает задачу из пула.

## 5. Роли и доступ к инструментам доски

Все роли (`researcher`, `analyst`, `critic_verifier`, `architect`, `builder`, `qa`, `designer`) исполняются внутри сервера TaskFlow. Постоянных ключей в хранилище и отдельных служб у ролей нет.

- **Запуск по карточке** (`server/src/runtime/inProcessRun.ts`): инструменты доски — внутренние вызовы сервера от имени учётки `role_<ключ>`, без токена.
- **Ролевой чат** (`server/src/runtime/PiRuntimeAdapter.ts` → `roleRunAccess.ts`): на время одного запуска сервер сам подписывает роли временный пропуск (срок 12 часов), кладёт временный файл подключения к `~/taskflow/roles/<роль>/scripts/mcp_server.py` и удаляет его при завершении. Брать ключ из хранилища роли не нужно.

Что роли разрешено делать с доской, определяет список инструментов в `~/.pi/agent/taskflow-profiles/<роль>.json` (поле `TASKFLOW_MCP_TOOLS`); у новой роли без файла — стандартный набор исполнителя. В режиме «план» список урезается до планировочных инструментов (`roleRunAccess.ts`).

Постоянные MCP/API-ключи остались только у внешних исполнителей (Claude, Hermes, DeepSeek-Agent); их выдаёт `server/scripts/issue-agent-token.ts`.

## 6. Переключение при provider_limit

`POST /api/tasks/:id/stop` идёт по **лесенке моделей**: таблица `model_ladder` (5 ступеней, по две учётки на ступень) плюс состояние `provider_limits` (лимит помечается на УЧЁТКУ, не на модель). Лимит — ВБОК, в другую учётку той же ступени (с одиночной ступени 0 — ВВЕРХ); нехватка способностей — ВВЕРХ; нет живой учётки — блок. Код — `server/src/lib/modelLadder.ts`; проект — карточка `dca29510`, полное описание `~/reply-to-reviewer.md`.

При найденной оболочке текущая попытка закрывается с `outcome=wait_provider`, создаётся новая активная попытка с тем же `model`, задача переназначается, получает свежую аренду и уведомляет нового исполнителя. Когда цепочка исчерпана, новая попытка не создаётся: задача получает `blocked`, а `current_attempt_id` очищается.

Проверка 12.09.2026: сценарий исчерпания единственного исполнителя→blocked и регрессия structured stop; полный серверный набор выполняется после обновления этой схемы.
