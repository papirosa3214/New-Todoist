# Единый цикл результата: карточки и работа из чата

Дата: 22.10.2026. Владелец одобрил схему в чате; последующее уточнение добавляет работу, порученную через обычную коммуникацию. Это согласованное направление, не отчёт о внедрении.

## Назначение

Независимые работы выполняются параллельно. Зависимости этапов и перенос в общий main имеют свои ограничения; неопределённое «в очереди» не скрывает их. Результаты документов не превращаются в Git-изменения автоматически.

## Входы

1. Карточка задачи: постановка, план и версии результата.
2. Поручение в чате после явного разрешения выполнить работу. Обычное обсуждение не является завершённой работой и не запускает автокритика на каждую реплику. Поручение может уточняться сообщениями во время выполнения. Создавать карточку только ради технического оформления чата не требуется.

Для чата нужно сохранить адрес исходного сообщения/разговора, поручение и границы, текущий результат и его версию. Это внутренний учёт результата, а не новая обязательная карточка. Итог и состояние возвращаются в исходный разговор. Обычное продолжение беседы не получает окно межагентной координации. Вопрос коллеге вне комнаты сохраняет существующую карточку координации.

## Тип работы

- Документы и анализ: пользовательские записки, исследования и отчёты сохраняются в документах TaskFlow; Git-интеграции нет.
- Действия в системе: изменения настроек/сервисов/данных в пределах поручения; Git-интеграции нет, если репозиторий не менялся.
- Изменение репозитория: код, конфигурация и техническая документация в репозитории; интеграция требуется.

Тип отражается в постановке и контексте участников. Для первых двух типов поле ответственности за Git-интеграцию не отображается. Если объём меняется и требуется изменение репозитория, это явно фиксируется в пределах авторизации владельца. Самовольное сохранение документа в рабочей копии не делает Git необходимым.

## Проверка

Каждый завершённый результат проходит финальную проверку. Если последний критик уже принял именно текущую версию результата, повторный запуск не нужен. Промежуточные критики по решению владельца остаются самостоятельными этапами. Новые изменения после принятия требуют проверки новой версии.

Для документов критик сопоставляет поручение, критерии и предоставленный результат. Он не повторяет всё исследование и не запускает не относящиеся к результату тесты. Для кода использует изменения и доказательства, дополнительная проверка имеет конкретную причину.

Возврат, по 2-3 предложения на проблему:

Проблема: что не работает и где.
Исправить: кому и что изменить.
Ожидается: проверяемый результат.

Одобрение: «Принято: результат соответствует задаче. Интеграция: не требуется / разрешена для указанных коммитов». Контракт report_markdown также принимает этот компактный формат и не требует отдельного длинного отчёта. Публичный вердикт краткий, без дублирования большого отчёта в ленте, шагах и карточке. Содержательные доказательства при необходимости хранятся отдельно.

## Интеграция

По умолчанию автоинтегратор — архитектор. Он подключается независимо от состава исходной команды; его отсутствие в одиночной задаче не является причиной пропустить этап. Недоступность показывается конкретным ожиданием, автор карточки не становится незаметным запасным интегратором. Для репозитория после критика он получает принятую версию и точные коммиты, проверяет совместимость и доводит разрешение конфликтов. Детерминированный обработчик выполняет Git-механику после разрешения; не дублирует решение ролью и не делает ручное слияние одновременно с ней.

В очередь принимается конкретный разрешённый набор изменений. Поиск неслитых веток только обнаруживает хвост и сообщает, но не авторизует интеграцию. Изменение принятых коммитов не покрывается старым разрешением. Документ/операционная работа без репозитория после критика возвращается владельцу без архитектора и Git-очереди.

## Наблюдаемость

У каждого поручения видно фактическое состояние: выполняется, проверяется, возвращено на исправление, интегрируется, результат готов. Для ожидания — причина, начало ожидания, конкретная зависимость/адресат; для готовой к исполнению очереди — её размер и позиция. Это не обещание точного времени завершения. Очереди сообщений, слотов и Git различаются.

## Устойчивость автоинтеграции

Выделенный обработчик не задерживает общий планировщик. Блокировка проверяет владельца/живость и не отбирается у работающего процесса только по возрасту. После падения восстанавливается конкретное обязательство, повторная доставка не создаёт второго слияния. Ошибка отдельной карточки не останавливает независимые готовые результаты.

## Проверка реализации

Только логические unit/integration проверки, без UI-тестов, симулятора и iPhone — прямое указание владельца. RED на прежнем поведении, GREEN после. Фикстуры: одиночный секретарь без кода; документ; операции; репозиторий; промежуточный критик; последний критик с актуальной/устаревшей версией; approved/rework; архитектурный интегратор; неразрешённая ветка; несколько параллельных поручений; работа из личного и группового чата; обсуждение без поручения; уточнение во время действия; сбой/повторная доставка; возврат в исходный чат. Живые пользовательские задачи для проверки не создавать.
