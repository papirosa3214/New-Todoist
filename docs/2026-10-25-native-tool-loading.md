# Нативные инструменты Pi: отдельные операции и загрузка по требованию

25.10.2026. Сервер: `/home/maksim/Проекты/New-Todoist` (`server/`).

## Что было

Роли работают на Pi SDK 0.84.4 (`@earendil-works/pi-coding-agent`). Операции TaskFlow
зарегистрированы отдельными инструментами, но модели показывался только общий шлюз
`taskflow` с произвольным полем `arguments`. Штатные механизмы Pi были закрыты обёрткой:

- собственный JSON Schema на инструмент не доходил до модели — аргументы приходили
  произвольным словарём, и модель угадывала поля;
- в каждый запрос уходили описания всех операций: **30 КБ на builder, 54 КБ на
  secretary** (57–113 инструментов), тогда как роль регулярно зовёт 11–17 из них.

## Что стало

### 1. Отдельные инструменты с точными схемами

`buildRoleToolCatalog` отдаёт модели каждую операцию своим именем с её JSON Schema
(`server/src/runtime/roleToolCatalog.ts`). Общий шлюз `taskflow` остаётся зарегистрирован,
но модели не виден: он нужен истории и голосовому пути (`secretaryVoiceTools`).

Права, контекст, идемпотентность и учёт не изменились: нативный инструмент — это тот же
вызов шлюза (`universal.execute` → `operationRestriction` → аудит).

### 2. Загрузка по требованию

Pi умеет держать в реестре все инструменты, но отдавать модели только активные и
расширять набор между запросами (`session.setActiveToolsByName`). Реализовано штатно:

- в реестре сессии — все операции, которые роль имеет право вызывать;
- **активно ядро** (ориентировка, слот, план, комментарий, сдача шага) + загрузчик;
- `taskflow_tools` показывает индекс доступных операций и подключает нужные по именам
  или по смыслу запроса (`server/src/runtime/nativeToolLoader.ts`).

Индекс выдаётся один раз за сессию и дальше живёт в истории — платим за него не каждый
запрос.

| роль | операций | было | стало |
|---|---|---|---|
| builder | 57 | 30.1 КБ | 11.5 КБ (38%) |
| researcher | 61 | 30.9 КБ | 11.1 КБ (36%) |
| secretary | 113 | 54.4 КБ | 12.3 КБ (23%) |
| critic_verifier | 50 | 27.2 КБ | 9.1 КБ (34%) |

Ядро отобрано по частоте за 14 дней (`role_tool_audit`) и по обязательности шага.

### Важная деталь SDK

`tools` в `createAgentSession` — это allowlist, и он **выбрасывает** инструменты из
реестра: не попавшие в список нельзя активировать позже («Only tools in the registry can
be enabled»). Поэтому allowlist содержит все операции, а активный набор сужается
`setActiveToolsByName` сразу после создания сессии (`installNativeToolCore`).

## Чего это не делает

- Права не расширяются: загрузчик отдаёт только то, что роль и так имеет право
  вызывать; проверка остаётся в шлюзе на момент вызова.
- Строгая генерация аргументов на стороне MiniMax — отдельный вопрос, смена способа
  подключения её не гарантирует.
- Нативная отложенная загрузка схем (`defer_loading`) в Pi есть только для Anthropic
  Sonnet/Opus 4.5+ и OpenAI gpt-5.4+. У нас MiniMax и deepseek — работает штатный
  fallback: в следующем запросе Pi просто отдаёт текущий активный набор.

## Что уходит на проводе (роль builder, замерено реальной сессией Pi)

| | инструментов в запросе | payload запроса |
|---|---|---|
| было (весь каталог) | 57 | 58.2 КБ |
| стало (ядро) | 24 | 36.2 КБ |

Разница payload'а — 22 КБ на каждый запрос; сами схемы операций — 30.1 → 11.5 КБ.

Сквозной сценарий (модель скриптованная, mock-провайдер): первый ход зовёт
`taskflow_tools` с именем операции, второй запрос уже несёт подключённую
операцию — модель зовёт её по имени. Общий шлюз `taskflow` модели не виден ни в
одном запросе.

## Порядок выкладки

Живой API на .110 — `node dist/index.js` под `taskflow-server.service` (юзер-юнит
systemd). Перезапуск рвёт идущие ходы ролей, поэтому:

1. `npm run build` в `server/` (tsc → `dist/`), код в `dist/` меняется без остановки
   процесса;
2. `systemctl --user restart taskflow-server.service` — только когда очередь пуста;
3. проверка: новый ход роли вызывает native-операции по имени (в JSONL сессии
   `toolCall.name` = `taskflow_*`, а не `taskflow`), а подключение операции идёт через
   `taskflow_tools`.
