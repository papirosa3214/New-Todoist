# Сводный результат проекта «TaskFlow — связь агентов: ни один шаг не заканчивается молча»

## Цель проекта
Любой запуск шага агента должен кончаться исходом с кодом, этот исход возвращается серверу, и сервер сам решает, что делать (повтор, смена модели, блок). Ни один шаг не заканчивается молча.

## Итоги четырёх дочерних карточек
1. MAK-96 / 3ae8923a — **Исход каждого запуска шага возвращается серверу**. Закрытый словарь 12 кодов причин сбоя, единый классификатор текста ошибки, одно типизированное событие `step_outcome` на каждое завершение хода (сдан, блок, сбой, обрыв). Статус: completed, ревью approved (коммит dc3bc45).
2. MAK-98 / 813ac8ec — **Типизированный blocked**. Тип блока обязателен, вопрос роли ограничен сроком жизни (возврат исходом «срок истёк»), недоступный адресат получает быстрый отказ, признак «меняет результат» разводит сигналы владельцу и оркестратору, `dependency` снимается сам при готовности зависимости. Статус: completed, approved (коммит e2b7c182).
3. MAK-97 / d606326b — **Сервер сам реагирует на исход**. По коду причины: временные сбои повторяются ограниченно, `context_overflow` сжимается и продолжается, квота/лимит уходят на запасную модель цепочки (блок — только когда цепочка исчерпана), доступ/конфиг/нет модели блокируют сразу. Событие «шаг брошен» с хвостом журнала и снимком git. Статус: completed, approved (коммит 43f650d7).
4. MAK-99 / e2c07775 — **Протокол ролей**. Роли видят список коллег и протокол прямо в инструкции, токен молчания глушит пустые «принял», системные сбои идут только в ленту карточки, владельцу доходят лишь сигналы, требующие его решения. Статус: completed, approved (коммит ff1d0e70).

## Проверка ключевого инварианта: исход возвращается серверу, реагирует сервер, а не оркестратор
- **Запись исхода — серверная.** `logStepOutcome` вызывается из серверных путей (`routes/subtasks.ts`, `runtime/planSubtaskAdmission.ts`, `runtime/inProcessRun.ts`, `routes/task-collaboration-plans.ts`), а не из ответа модели. Единая точка — `runtime/stepOutcome.ts`, событие `step_outcome` в журнале карточки.
- **Распознавание — серверное.** `runtime/failureReasons.ts`: один классификатор по тексту, закрытый список из 12 кодов. Свободный текст больше не является решением.
- **Реакция — серверная.** `runtime/failurePolicy.ts` — таблица «код → retry / retry_then_switch / switch_model / compress_continue / block»; исполняет её `planSubtaskAdmission.settleStalledPlanNode` и цепочка failover в `inProcessRun`. Живой сессии оркестратора для этого не требуется; застой ловит серверный таймер `stalledStepWatcher`.
- **Маршрутизация сигналов — серверная.** `runtime/blockSignals.ts` сам выбирает адресата (`owner` / `orchestrator`) по типу блока и признаку «меняет результат».
- **Вывод:** исход каждого шага возвращается серверу, а сервер реагирует сам. Оркестратор не является звеном реакции — он получает сигнал только тогда, когда этого требует тип блока.

## Открытые хвосты
- Классификатор по-прежнему уводит в `unknown` часть редких реальных текстов (не блокер, контракт не сломан). При повторе темы — расширять реестр правил.
- Карточки собраны как проект Linear; приёмка велась в режиме владельца.
