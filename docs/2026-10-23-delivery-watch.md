# Сторож доставок: уточняющий вопрос не остаётся без ответа

23.10.2026 · реестр: `LOCK-DELIVERY-WATCH-20261023` · сервер: `~/Проекты/New-Todoist`

## Задача

Владелец 22.10.2026: «У нас, когда идёт сообщение в личку, кто-то инициировал —
кому-то написал. Ответное письмо, точнее ответ на это сообщение — он как-то
дойдёт до первичного отправителя или нет, [если] держать открытые каналы личных
сообщений, участников? Например, помощник написал оркестратору, чек ушёл,
отключился. А оркестратор вопрос ему уточняющий написал. И уже никто не
ответит».

Разбор (22.10.2026, прод-база .110) показал: **канал у лички в порядке, дыра
в доставке**. Личные комнаты ролей вечны и открыты — 23 комнаты, закрытых нет,
участники не теряются; ответ доходит даже если сессия инициатора закрыта.

Разобрано на живых данных:

| Проверка | Факт |
| --- | --- |
| Личка роль↔роль | 184 доставки `done`, `pending` — **0**; ответ доходит, сервер поднимает новый ход получателю, если его сессия закрыта |
| Помощник ↔ оркестратор (22.10, 21:14–21:17) | вопрос в 21:16:43 → ответ в 21:17:17, сессия помощника закрылась в 21:14 |
| Упавшие ходы в личке | **21** `failed` — Pi-сбой/таймаут, ответ не дан |

Дыры, которые и закрывает этот сторож:

1. **Ход роли упал → вопрос навсегда без ответа.** Сбой Pi закрывает доставку
   в `failed`; recovery на старте сервера берёт только `pending`, автоповтора
   не было нигде. Живой пример: архитектор спросил оркестратора в 06:49 →
   «Не смог ответить: Request timed out» в 06:50 → архитектор спросил снова
   в 06:56 → ответ в 07:06. Ответ вытащил только новый вопрос инициатора.
2. **Вопрос в слоте, где роль не работает → тишина до TTL.** Доставка лежит в
   `pending`, затем сервер закрывает её в `failed` по TTL (60 минут) — без
   уведомления кому-либо. Сейчас висят: архитектор — 2 сообщения (20:59,
   21:00), разработчик — 2 (21:10, 21:11), карточка c14e6335 «рутины»: слоты
   этих ролей уже `done`, работать некому.

## Что сделано

### 1. Автоповтор упавшего хода

`server/src/runtime/chatDeliveryWatch.ts` (новый) — `sweepFailedDeliveries()`:
поднимает упавшую доставку тем же путём, что и живое сообщение
(`recoverAgentDelivery` → Pi-вызов → ответ в чат). Попытки ограничены
(`TASKFLOW_CHAT_DELIVERY_MAX_ATTEMPTS`, по умолчанию 3), пауза перед повтором
(`TASKFLOW_CHAT_DELIVERY_RETRY_MIN`, 5 минут), счётчик — в `payload_json.retryCount`.

Отделены от «истёкших по TTL» доставок: `expireStaleDeliveries()` теперь
помечает их ключом `expired` в payload, и такие доставки не поднимаются —
вопрос по ним неактуален.

### 2. Пинг по висящему вопросу

`server/src/runtime/chatDeliveryWatch.ts` — `sweepStalledDeliveries()`: если
доставка лежит в `pending` дольше порога (`TASKFLOW_CHAT_DELIVERY_STALL_MIN`,
20 минут), а роль-получатель **не работает** по этой карточке (нет слота
`in_progress`/`review` и нет задания в `role_run_jobs`), владельцу уходит
уведомление в «Состояние системы» — тем же способом, что сторожа формата
ответов и сторожа поиска по базе знаний.

Не пинается: свежий вопрос; роль, которая работает по карточке; вопрос без
карточки (личная переписка — там доставку поднимает живой маршрут).

### 3. Подключение

`server/src/runtime/chatQueueRecovery.ts`:
- периодический проход (`scheduleChatQueueRecovery`, раз в 10 минут) теперь
  делает три шага: пинг висящих вопросов → просрочка → подъём `pending` →
  повтор упавших ходов;
- на старте сервера упавшие ходы прошлой сессии тоже поднимаются заново.

Пинг стоит **до** просрочки: истёкшую доставку уже не поднять, а сказать
владельцу надо.

## Ограничения

- **Живой сервер не перезапускался.** API на .110 работает из `dist/`, выкладка
  идёт сторожем `deploy-when-idle.py` (systemd-таймер, раз в 2 минуты): ждёт
  простоя очереди, пересобирает, перезапускает, проверяет `/api/health`. То
  есть после коммита в `main` изменение доедет само, когда очередь опустеет.
- Повтор поднимает **ход роли**, а не гарантирует ответ: если роль падает
  снова три раза, владелец получает уведомление — дальше вопрос закрывает он.
- Пинг не поднимает роль: он сообщает, что вопрос ждёт. Запустить роль по
  этой карточке должен владелец (или оркестратор через существующий механизм
  `wakeOrchestratorStalled` — если понадобится, сделаем отдельной строкой).

### Дыра 1: повтор без ограничения по возрасту

`sweepFailedDeliveries` поднимал **все** `failed`-доставки без метки
`expired`. В боевой БД их 75, и 73 из них старше суток (12–21.10.2026).
Повтор каждые 10 минут по 20 штук поднял бы 73 доставки недельной давности:
роль отвечает на вопросы, которые уже никому не нужны, и съедает реальный
ресурс на каждом.

**Что сделано:** `chatDeliveryRetryMaxAgeMinutes()` — окно повтора, по
умолчанию **6 часов** (`TASKFLOW_CHAT_DELIVERY_RETRY_MAX_AGE_MIN`). Сбой
старше окна не поднимается. Окно выбрано не на глаз: в боевых данных в него
попадает ровно 2 доставки — те самые вопросы владельца, — и не попадает ни

### Дыра 2: пинг пропускал вопросы в чатах без карточки

`findStalledDeliveries` отбрасывал доставки, у которых нет карточки
(`if (!taskId) continue;`). А личная переписка роль↔роль — это ровно тот

считается, если роль не занята этой перепиской — тем же признаком живого
хода (`roleIsBusyNow`), которым уже пользуется просрочка доставок. Одно
понятие «роль занята» на оба случая.

`roleIsBusyNow` переехал из `chatQueueRecovery.ts` в `chatDeliveryWatch.ts`
(иначе цикл импортов: сторож уже импортируется из recovery-модуля); из
`chatQueueRecovery.ts` оставлен реэкспорт.
