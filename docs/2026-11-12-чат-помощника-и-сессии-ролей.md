Рядом — уже принятые схемы: `docs/2026-11-12-оркестрация-миссии-каркасы.md` (main `a35e7d40`)

## 1. Решение в двух абзацах

Вместо трёх параллельных представлений «где сейчас роль» — комнат субагентов
(`chats.subagent_role_id`/`subagent_state`, миграция `185`), связки «личная комната → дочерняя
сессия» (`chat_child_sessions`, миграция `203`) и карты `activeRuns` в памяти процесса
(`runtime/inProcessRun.ts:1226`) — заводим **одну сущность: сессия роли** (`role_sessions`).
Сессия — это один запуск роли: повод (слот карточки, вызов из чата, вход миссии), файл
Pi-сессии, состояние, черновое и итоговое название, итог. Она же — строка журнала в сессии
Помощника, потому что журнал и есть список сессий этой роли, отфильтрованный по «откуда
позвали». Отдельной таблицы журнала нет: второе хранилище одной и той же записи разошлось бы
с первым.

Комнат у ролей нет. Роль работает в файле Pi-сессии и отдаёт результат через существующие
ворота: допуск слота (`runtime/planSubtaskAdmission.ts:545`), квитанция сдачи, аренда слота
(`acquireSlotSession`, `runtime/slotSession.ts:29`). Владелец видит работу роли живым ходом
(существующий поток `chats:live`, `runtime/chatLiveDelta.ts`) и итогом в журнале; ответ на
`@роль` из чата Помощника приходит в этот же чат сообщением от роли, **без запуска хода
Помощника** — двойной цены нет.

## 3. Сущность «сессия роли»

### 3.1. Таблица `role_sessions` (миграция `219_role_sessions`)

Последняя существующая миграция — `218_chat_queued_messages` (`server/src/migrations.ts:6470`),
поэтому нумерация начинается с 219.

| Поле | Тип / смысл |
| --- | --- |
| `id` | Идентификатор сессии (это то, что приложение и инструменты получают как `session_id`) |
| `role_key` | Ключ роли (`architect`, `builder`, …) |
| `origin_kind` | `task` — по слоту карточки; `call` — вызов из чата; `task_comment` — `@роль` или ответ роли в ленте карточки (§9.3.2); `mission` — вход оркестратора миссии |
| `origin_chat_id` | Сессия Помощника, откуда позвали; NULL для `task` и `task_comment` |
| `origin_message_id` | Сообщение-повод: `chat_messages.id` при `call`, `comments.id` при `task_comment` (поле TEXT без внешнего ключа — как и `origin_chat_id`) |
| `origin_task_id` | Карточка, из ленты которой позвали (`task_comment`); NULL в остальных случаях. Дублем к `task_id` не считается: у `task_comment` без слота `subtask_id` пуст, а `task_id` нужен для аренды карточки |
| `parent_session_id` | Сессия роли, которая вызвала (сейчас вложенность запрещена, поле — на будущее) |
| `task_id`, `subtask_id`, `attempt_id` | Привязка к карточке, слоту, попытке; NULL для `call` |
| `session_file`, `session_id`, `cwd` | Файл Pi-сессии, id сессии у Pi, рабочая папка |
| `state` | `running / waiting_owner / waiting_role / closed / failed / stopped` |
| `title_draft`, `title_final` | Черновое название (по первой фразе) и итоговое (DeepSeek 9B при закрытии) |
| `title_embedding`, `title_embed_model` | Вектор итогового названия для поиска по смыслу |
| `last_step`, `last_activity_at`, `heartbeat_at` | Последний инструмент и живость |
| `result_summary`, `result_ref` | Итог одной фразой и ссылка на артефакт (документ, коммит) |
| `close_reason` | `done / failed / stopped / stale` (сторож тишины) |
| `created_at`, `closed_at`, `archived_at` | Времена; `archived_at` — убрано с глаз, файлы живы |

Индексы: `(role_key, state)`, `(origin_chat_id, created_at DESC)`, `(task_id, subtask_id)`,
`(state, heartbeat_at)`.

Внешних ключей на `chats` у `role_sessions` нет — только `origin_chat_id` как TEXT. Это
сознательно: сессия Помощника может быть архивирована (`chats.archived_at`), а запись журнала
обязана остаться.

### 3.2. Файлы сессий

Каталог: `~/.local/state/taskflow-runs/sessions/<session_id>/` (корень уже настраивается
`TASKFLOW_RUNS_DIR`, см. `runtime/slotSession.ts:59`). Файл не удаляется никогда — «ничего не
должно теряться» (пункт 4 концепции); удаление — только `archived_at` в строке.

Слотовые сессии переиспользуют нынешний каталог `${taskId}-${role}-${subtaskId}`
(`slotSessionDirectory`, `runtime/slotSession.ts:59`) и таблицу `slot_sessions`
(миграция `097`, поля `session_file`, `cwd`, `session_id`). Бэкфилл этапа 1 просто переносит
эти три поля в `role_sessions` — файлы не переезжают, поэтому уже накопленные истории шагов
остаются читаемыми.

### 3.3. Жизненный цикл

```
открыта (running) ──роль ждёт владельца──► waiting_owner ──ответ──► running
        │                └──роль ждёт коллегу──► waiting_role ──пришёл──► running
        ├──сдала итог──► closed (close_reason=done)
        ├──ошибка/CAPABILITY──► failed
        ├──остановка владельцем или сторожем тишины──► stopped
        └──closed/failed/stopped + 30 дней──► archived_at (строка и файл остаются)
```

Правила перехода живут в одном месте — новом `runtime/roleSessions.ts`; всё остальное читает
состояние оттуда. Сторож тишины (`sweepStaleInProcessRuns`, `runtime/inProcessRun.ts:1243`)
вместо прерывания «в никуда» ставит `stopped` и пишет `last_step`, чтобы в журнале было видно,
чем кончилось.

Живость: `heartbeat_at` обновляется на каждом инструментальном шаге. После перезапуска сервера
сессия в состоянии `running` без свежего heartbeat получает `stopped` при первой же проверке —
именно этот случай сейчас показывает владельцу «занята», хотя роль ничего не делает.

## 4. Почему не «комната без комнаты»: адресация и роли

Сегодня роль адресуется через комнату: `chats` + `chat_members`, сообщение лежит в
`chat_messages`, живой ход — по `chat_id`. Если убрать комнату, адресом становится
`role_sessions.id`; сообщения и живой ход остаются в существующих таблицах:

- **сообщение владельца** → `chat_messages` в сессии Помощника (как сейчас), плюс
  `role_session_id` в очереди доставки;
- **ответ роли** → `chat_messages` в сессии Помощника от имени роли (`from_user_id` роли), без
  запуска хода Помощника;
- **живой ход** (шаги, инструменты) → существующий поток дельт по ключу сессии
  (`chatLiveDelta.ts`, снимки — `task_live_turn_snapshots`, миграция `192`, `server/src/migrations.ts:5536`);
- **вложения и документы** — там же, где сейчас.

То есть комнаты убираются как *контейнер переписки*, а не как механизм доставки: таблицы
`chat_messages` и очередь `chat_message_queue` (миграция `123_chat_message_queue_and_generation`, `server/src/migrations.ts:4016`)
остаются и работают.

## 5. Судьба `role_runs` — явный ответ на вопрос Оркестратора

**Выбран вариант 1: взять как основу «сессии роли»** — с четырьмя правками, без которых он не
годится.

1. `room_id` **удаляется** (комнат нет). Вместо него `session_file` + `session_id` + `cwd` —
   то, что уже лежит в `slot_sessions` (`migrations.ts:3253`) и `chat_sessions`
   (`migrations.ts:2310`).
2. Таблица называется `role_sessions`, а не `role_runs`: «запуск» — слово исполнителя, а
   владельцу и приложению продаётся «сессия». Это то же самое, но название задаёт смысл
   (наборы полей совпадают на 80%).
3. Добавляются поля, которых в проекте 11.11 не было и без которых концепция не выполняется:
   `origin_kind`, `title_draft`, `title_final`, `title_embedding`, `heartbeat_at`,
   `archived_at`, `close_reason`.
4. Три нынешних места состояния становятся **производными**:

| Сейчас | Становится |
| --- | --- |
| `chats.subagent_role_id`, `chats.subagent_state` (`migrations.ts:5409`) | Удаляются вместе с комнатами; чтение заменяется на `role_sessions` |
| `chat_child_sessions.status` (`migrations.ts:6037`) | Удаляется; связь «слот ↔ сессия» — `role_sessions.subtask_id` |
| `activeRuns` в памяти (`inProcessRun.ts:1226`) | Остаётся кэшем исполнителя; истина — `role_sessions.state` |
| `subtasks.agent_state` | Остаётся (состояние работы), но приводится из `role_sessions` при старте/закрытии сессии |

Почему не вариант 3 (отказаться от таблицы): «кто сейчас работает» после перезапуска сервера
без своей строки в БД восстановить нечем — `activeRuns` пуст, `subtasks.agent_state` не знает
ни файла сессии, ни повода вызова, ни названия. Название и эмбеддинг вообще некуда положить.
Вариант 2 (расширять `chat_child_sessions`) отпадает по той же причине, по которой он и был
придуман: эта таблица привязана к двум комнатам (`parent_chat_id`, `talk_chat_id`), а комнат не
остаётся.

Что от `role_runs` **не** берём: `result_message_id` (итог живёт в `result_summary`/`result_ref`
и в сообщении сессии Помощника), `room_id`, состояния `done/failed` в прежнем смысле —
`done` заменяется на `closed` + `close_reason`.

## 6. `@роль` из сессии Помощника

### 6.1. Разбор и маршрут

1. Владелец пишет `@разработчик поправь сборку` в сессии Помощника. Разбор упоминаний уже есть:
   `parseRoleMentions` (`server/src/routes/chats.ts:2284`), список ролей чата — `chatMemberRoles`.
2. Если в сообщении есть `@роль` (или тап по кружку роли) — **ход Помощника не запускается**.
   Сообщение уходит роли напрямую (пункт 3 концепции).
3. Сервер выбирает сессию роли (§6.2) и доставляет сообщение:
   - сессия `running` → подмешивание в идущий ход на ближайшей границе действия — тот же путь,
     что `deliverChatToWork` (`inProcessRun.ts:1197`) и `slot_topic_inbox` (`migrations.ts:3260`),
     но ключ не `(очередь сообщений, слот)`, а `(очередь сообщений, role_sessions.id)`;
   - сессия `waiting_owner`/`waiting_role`/`closed`/`failed` → **продолжение той же сессии**
     (у Pi есть `--session-id`, `runtime/PiRuntimeAdapter.ts:1420`): роль получает «у тебя была
     задача такая-то, сделал то-то — ответь в этом контексте»;
   - открытых сессий нет → открывается временная: `origin_kind='call'`,
     `origin_chat_id` = сессия Помощника, `origin_message_id` = сообщение.

### 6.2. Если у роли несколько сессий

Правило по умолчанию, без вопроса владельцу: 1) если в тексте названа карточка — сессия по этой
карточке; 2) иначе последняя активная; 3) если активных больше одной и выбор неочевиден, в
журнал пишется строка «доставлено в последнюю активную; открыто ещё N», а приложение
показывает список (пункт 6 концепции — тап по активной роли даёт список с подписью повода).
Молчаливой потери нет: сообщение всегда попадает в конкретную сессию и это видно.

### 6.3. Ответ в сессию Помощника

Итог сессии кладётся сообщением в `origin_chat_id` от имени роли (`chat_messages`,
`from_user_id` = роль). Ход Помощника не поднимается. Помощник увидит ответ в своей истории на
следующем своём ходе — если посчитает нужным. Это отличается от нынешнего `taskflow_call_role`,
которое будит вызывающего через очередь (`deliverDigest`, `runtime/roleSubagentCall.ts:424`, через `recoverAgentDelivery` `:451`): там вызывала роль,
здесь — владелец, и он читает ответ сам.

### 6.4. Что видно, пока роль думает

Строка журнала сразу получает `state='running'` и `last_step` (обновляется на каждом шаге),
живые шаги идут дельтами (`chats:live`). «Принято» и «роль ответила» — два разных состояния,
как и требует раздел 2.4 проекта 11.11.

## 7. Журнал вызовов

**Где хранится:** нигде отдельно — это выборка из `role_sessions`
`WHERE origin_chat_id = <сессия Помощника> ORDER BY created_at DESC`. Отдельной таблицы нет
сознательно: журнал и сессия — одна запись, разъехаться не могут.

**Что в строке:** роль, повод (`origin_kind`), первые ~120 знаков поручения (из
`chat_messages.text` по `origin_message_id`), время начала, состояние, итог
(`result_summary`), ссылка на артефакт, ссылка на сессию (`role_sessions.id` → экран сессии).

**Как провалиться:** `GET /api/role-sessions/:id` + подписка на дельты по тому же ключу.
Ничего не суммируется (пункт 4 концепции): файлы сессий хранятся, строка указывает на сессию.

**Отдельно:** журнал не входит в контекст модели Помощника целиком. В промпт попадают только
строки, которые Помощник сам запросил инструментом; иначе сессия Помощника распухнет от
чужих работ (`history-isolation.md`).

## 8. Название при закрытии и поиск по смыслу

- **Черновое название** (`title_draft`) ставится при открытии: первая фраза поручения,
  обрезанная до 80 знаков. Это то, что видно в приложении, пока сессия идёт.
- **Итоговое название** (`title_final`) даёт локальная модель при закрытии — она уже работает:
  `LOCAL_DEFAULT_MODEL = "eriktonon/deepseek-v4.1-flash-1017:9b"` (`server/src/lib/localModels.ts:4`).
  Промпт: «дай название 5–8 слов по смыслу: с кем, о чём, чем кончилось». Вызов через `aiClient`
  (`lib/aiClient.ts:122` — та же модель, `num_ctx` 81920), то есть новых зависимостей нет.
- **Эмбеддинг** — `LOCAL_EMBED_MODEL = "bge-m3-embed:latest"` (`lib/localModels.ts:5`), клиент
  `getEmbeddings` (`lib/embeddingClient.ts:106`). Вектор кладём в `role_sessions.title_embedding`
  (BLOB), тип — как у `role_embeddings`/`memories`, где вектор уже так хранится
  (`migrations.ts:1358`, поле `embedding BLOB`).
- **Поиск** — косинус по векторам, функция уже написана: `cosine` (`lib/semanticEnrich.ts:32`).
  Ищем по закрытым сессиям владельца и по сессиям конкретной роли. Запрос «о чём говорили с
  Разработчиком про сборку» находит по названию, не по тексту переписки. Достаточно векторной
  таблицы в 100-тысячном масштабе; отдельный индекс (sqlite-vec) не нужен, пока сессий меньше
  нескольких тысяч.

**Если модель недоступна** — сессия всё равно закрывается, `title_final` остаётся NULL,
черновое название сохраняется, задача на переименование ставится в фон (одна повторная
попытка). Закрытие сессии не должно ждать модель: это же правило уже действует для
`thinkingTranslation` (`lib/thinkingTranslation.ts:62`).

### 9.2. Уборка уже существующих комнат (пункт 7 концепции)

Порядок, чтобы не потерять переписку:

1. Резервная копия БД (`cp db.sqlite db.sqlite.bak-<дата>` либо `sqlite3 .backup`) — обязательна,
   выполняется скриптом, а не руками.
2. Скрипт `server/scripts/archive-role-rooms.ts` с предпросмотром: печатает, сколько комнат
   попадает в архив по видам — `subagent_role_id IS NOT NULL`, `room_kind IN
   ('personal','dm','common','wake','handoff')` и отдельной строкой **комнаты задач
   `room_kind='task'`** — и сколько сообщений в каждой группе. Ничего не меняет без флага
   `--confirm` — образец поведения уже есть у уборки чатов (`chats_cleanup_preview`).
   Комнаты задач идут в тот же архив, но **не раньше, чем их переписка перенесена в `comments`
   и счётчики сошлись** (§9.3.2, шаг 12 плана). Создание и маршрутизация убираются по §9.1 —
   держать их в списке чатов после переключения нечем и незачем; без архива они остались бы
   единственным видом комнат, у которого механизм убран, а строка живёт. Отдельного решения
   владельца по ним не требуется: это тот же пункт 7 концепции.
3. Подтверждение владельца в этот момент (не заранее).
4. Запись `chats.archived_at = now()`; строки и сообщения остаются, список их больше не
   показывает (маршрут `GET /api/chats` уже отсекает комнаты субагентов, `routes/chats.ts:541`,
   — условие расширяется на `archived_at`).
5. Колонки `subagent_role_id`/`subagent_state` и таблица `chat_child_sessions` физически удаляются
   отдельной миграцией **после** переключения чтения, не в том же релизе.

### 9.3. Переписка по задаче — в ленте активности карточки (владелец 12.11.2026)

Решение владельца: групповых чатов задач (`room_kind='task'`, «Переписка по задаче») больше
нет. Разговор по задаче идёт в ленте активности карточки, где уже есть поле ввода
(`POST /api/tasks/:taskId/comments`; таблица `comments`, `db.ts:146`) и раздел «Лента
активности» в iOS. Второй ленты не заводим.

**Что уже есть.** Лента карточки уже склеена из двух источников: `comments` и сообщений чатов,
привязанных к задаче (`routes/tasks.ts:1278-1310`: `chat_messages WHERE task_id=? AND
channel='chat'`, пометка `source='chat'`). То есть переписка по задаче и сегодня видна в ленте,
но приходит она из комнаты задачи, а комнату мы убираем. Значит менять надо не ленту, а
источник: сообщения ролей по задаче пишутся в `comments`, а `chatComments` (вместе с
`room_kind='task'`) уходит вместе с §9.1. Один источник — одна лента.

**Чего в `comments` нет, а решению нужно:**

1. **Ответ на сообщение.** `comments.reply_to_id TEXT REFERENCES comments(id)`; сервер отдаёт
   его в элементе ленты, клиент рисует цитату. Без этого «ответ роли именно на сообщение
   владельца» невыполним и пришлось бы вернуть комнаты.
2. **Служебное свёрнуто.** `comments.visibility IN ('public','service')`; `service` по умолчанию
   свёрнуто, разворачивается одним тапом. Признак ставит **сервер**, а не клиент — иначе два
   экрана разложат одно сообщение по-разному. Правила: сообщение владельца — `public`; ответ
   роли на сообщение владельца — `public`; сообщение роли не в ответ владельцу, отметка шага,
   запись `logEvent` (`agentState.ts:355`) — `service`.
3. **Кто автор.** Новых колонок не нужно: `user_id` уже ссылается на `users`, а `GET /api/tasks/:id`
   джойнит автора (`routes/tasks.ts:1247`); отдаём добавкой `role_key`.

**Маршруты.** `GET /api/tasks/:id` — в элементах ленты `reply_to_id`, `visibility`, `role_key`.
Запись ответа идёт существующим маршрутом комментариев с телом `{text, reply_to_id?}`; им же
пользуются ответы ролей и голос Помощника, `taskflow_comment` пишет туда же. Отдельного API для
«переписки по задаче» нет — это и есть смысл решения.

**Живое обновление.** Лента уже обновляется событием `tasks:live` (`inProcessRun.ts:1708`),
отдельный поток не нужен: новый комментарий и ответ роли добавляются в ту же порцию дельт.

**Стыковка с сессиями ролей и доставкой `@роль`.** Нового механизма нет: комментарий с
`@роль` разбирается тем же `parseRoleMentions` (`routes/chats.ts:2284`), что и сообщение в
сессии Помощника (§6.1), и попадает в ту же сессию роли — в работающую через `deliverChatToWork`
(`inProcessRun.ts:1197`), иначе открывается временная сессия с `origin_kind='task_comment'`,
`origin_task_id = <карточка>` и `origin_message_id = <id комментария>`. Признак того, что
разговор идёт по карточке, добавляется в подсказку сессии («задача такая-то»). В реестре
`role_sessions` такой запуск виден как обычная сессия с поводом «вызов из ленты карточки» —
отдельного поля `role_runs` не нужно (§5).

Сегодня маршрут комментариев роли не вызывает (`routes/subtasks.ts:1194`): упоминание
разбирается только будильником «владелец написал — подними назначенного» (`:1256`,
`enqueueRoleRunJob` с поводом `commented`, список поводов — `runtime/roleRunQueue.ts:5`).
Правка одна: после вставки комментария владельца сервер ставит задание на каждую названную
роль (`dedupeKey = comment:<id>:<role>`), дальше — обычная дорога запуска: сессия, аренда
карточки, ворота допуска. Отдельного «ленточного» исполнителя нет.

**Как роль отвечает в ленту.** Тот же `taskflow_comment`, но с `reply_to_id` сообщения
владельца; иначе — комментарий без привязки и `visibility='service'`. Ответ на сообщение
владельца получает `visibility='public'` автоматически (правило §9.3) — роли не надо решать,
что считать служебным.

**Этап и проверка** — шаг 12 плана §13. Сценарий: владелец пишет комментарий с `@роль` — роль
поднимается без хода Помощника и отвечает привязанным ответом; отметки шагов видны свёрнутыми
и разворачиваются; в живом списке чатов `room_kind='task'` не появляется; переписка прежних
комнат задач после переноса читается в ленте.

### 9.3.1. `slot_topic_inbox` и маршруты `routes/chats.ts` для комнаты задачи

`slot_topic_inbox` (`migrations.ts:3260`) — не «входящие темы», а очередь «сообщение ещё не
дошло до работающего слота»: `(message_id, subtask_id, delivered_at)`. Читает её запуск роли
(`inProcessRun.ts:1884`), пишут — доставка в занятую сессию (`:1188`, `:1203`, `:1210`), маршрут
комнаты задачи (`routes/chats.ts:1230`), квитанция (`:2818`) и `slotConversation.ts:103`.
Ленте она нужна не как хранилище, а как транспорт «сообщение → работающий слот».

- **Остаётся, но меняет источник.** Ссылаться на `comments` внешним ключом нельзя без второй
  колонки: добавляем `comment_id TEXT REFERENCES comments(id)` и `CHECK` на ровно один
  источник — либо `message_id`, либо `comment_id`. Так доставка в занятую роль работает для
  ленты тем же механизмом, что и для чата, и не приходится возвращать комнату.
- **Из комнаты задачи не пишется.** Строка `routes/chats.ts:1230` уходит вместе с комнатой;
  новых строк с `message_id` из тем больше не появляется.
- **Накопленное чистится** в уборке §9.2: у комнат задач недоставленные строки удаляются
  вместе с их архивом — тот же приём, что уже есть у архивной комнаты
  (`lib/taskRoomArchive.ts:19,142`).
- **Отметки шагов сюда не идут и раньше не шли** (`runtime/stepTopicProgress.ts:20` — сказано
  прямо), поэтому отметки переносятся в ленту мимо этой таблицы.
- Таблицу целиком (как `chat_child_sessions`) **не удаляем**: она остаётся транспортом для
  сессий, меняется только состав ссылок.

Маршруты `routes/chats.ts` для комнаты задачи, по одному:

| Что | Строка | Судьба |
| --- | --- | --- |
| Выбор темы и слота, доставка в работу | `:3614` (вход) и `:3361` (`deliverTopicToWork`, только для темы) | Удаляется; доставка в ленте — `deliverChatToWork` (`inProcessRun.ts:1197`) по сессии |
| Старт «разговора со слотом» для темы | `:3783` и `:3821` (`startSlotConversation`) | Удаляется целиком (§9.1) |
| Постановка в очередь из маршрута комнаты | `:1230` | Удаляется |
| Список чатов | `:541` | Остаётся, условие дополняется `archived_at`, комнаты задач больше не попадают |

`GET /api/tasks/:id` перестаёт склеивать `chat_messages` комнат задач (`routes/tasks.ts:1305`):
второго источника у ленты не остаётся — только `comments`.

### 9.3.2. Что происходит с существующими комнатами задач при переключении

Четыре шага, в этом порядке; между шагами ничего не теряется, откат возможен до шага 4.

1. **Миграция полей** — `comments.reply_to_id`, `comments.visibility` (обе NULL допустимы).
2. **Перенос переписки** — скрипт `server/scripts/migrate-task-rooms-to-comments.ts`:
   `chat_messages WHERE task_id=? AND channel='chat'` → `comments` (автор `from_user_id`,
   `created_at` сохраняется, `visibility='public'`, `reply_to_id` — из `reply_to_id` сообщения,
   если он тоже перенесён, иначе NULL). Идемпотентность — отдельная таблица соответствий
   `comment_id`/`message_id` либо колонка `comments.legacy_message_id TEXT UNIQUE`; повторный
   прогон добавляет ноль строк. Предпросмотр и `--confirm` — как в §9.2.
3. **Сверка счётчиков** — по каждой комнате: сообщений в комнате = добавлено в `comments`.
   Расхождение — стоп, архив не запускается.
4. **Только после этого** — шаг 10 плана (архив комнат по §9.2) и удаление чтения
   `chat_messages` из `routes/tasks.ts:1305`. Между шагами 2 и 4 лента читает оба источника и
   схлопывает дубли по `legacy_message_id` — иначе на время перехода переписка задвоится.

Вложения сообщений комнат (`attachments.chat_message_id`) переносятся на `comment_id`; если
перенос вложений не сделан, шаг 4 не выполняется — картинки в ленте иначе пропадут.

Что не входит: голосовые сообщения в ленте карточки, редактирование и удаление комментариев —
отдельные решения владельца, этой схемой не покрыты.

## 11. Стыковка со схемой миссии

Схема миссии (`docs/2026-11-12-оркестрация-миссии-каркасы.md`) не переделывается:

- **слот = сессия роли** с `origin_kind='task'`: у каждого исполнения узла своя сессия, шаг
  остаётся чекпоинтом (база уже чекпоинт);
- **вход оркестратора = сессия роли** с `origin_kind='mission'` и `task_id` миссии, без слота.
  Каждый вход — новая сессия (свежий контекст, «оркестратор не держит сессию между входами»);
  карточка миссии показывает их списком «вход 1..N», а не одной бесконечной историей;
- **журнал миссии остаётся `mission_events`** — это про «что решено», сессии — про «кто где
  работал». Дублирования нет: `mission_events` пишет предметные события, `role_sessions` — факт
  запуска и его итог;
- **навыки миссии** (`mission_skills`) и отбор JEV (`lib/memorySkillsJev.ts:185`,
  `runtime/instructionResources.ts:187`) — не меняются. Для `call`-сессий отбор навыков идёт по
  тексту поручения, а не по карточке (это и было отмечено в постановке карточки).

## 12. Где схема отступает от концепции владельца (прямо и с причиной)

1. **Параллельность без лимита — да, вложенность «роль зовёт роль» — пока нет.**
   Лимит «3 запуска за ход» (`runtime/roleSubagentCall.ts:11, 479`) снимается: он считается
   внутри хода и мешает ровно тому, что владелец назвал лишним. Но цепочка «роль вызвала роль,
   та ещё одну» остаётся запрещённой: в карточках уже был разбор пинг-понга между ролями.
   Если нужно иначе — это отдельное решение владельца, не следствие этой схемы.
2. **Одна пишущая сессия на карточку.** Параллельных сессий сколько угодно, но писать в рабочий
   каталог карточки (`roleWorkspace`, `runtime/roleWorkspace.ts:197`) может одна — иначе две роли
   одновременно правят один worktree и ветку `roles/<task_id>`. Остальные в это время либо
   читают, либо работают в своей папке роли (`~/taskflow/roles/<key>/workspace`). Аренда уже
   есть — `acquireSlotSession` (`runtime/slotSession.ts:29`); расширяем её с шага на карточку.
3. **Ответ роли приходит в сессию Помощника сообщением, а не поднимает ход Помощника.**
   Владелец сказал «ответ приходит в сессию Помощника»; буквальное пробуждение Помощника стоило
   бы токенов на каждое «спасибо, принято». Помощник видит ответ на следующем ходе.
4. **`role_sessions` вместо `role_runs`** — переименование с обоснованием в §5.

## 14. Риски и что не ломать

- **Квитанция сдачи, аренда, пульс, попытка слота, утверждение плана, очередь в main** — не
  трогаются. Новый путь входит через те же ворота допуска.
- **Один worktree на карточку**: без правила §12.2 две параллельные сессии затрут друг друга.
  Это главный технический риск схемы; проверяется на этапе 8.
- **Перезапуск сервера**: сессии обязаны переживать его (состояние в БД + `heartbeat_at`);
  проверка перед выкладкой — пустая очередь ролей.
- **Два состояния на время перехода**: зеркало одностороннее (исполнитель → `role_sessions`),
  иначе расходятся.
- **Контекст Помощника**: журнал не заливается в промпт целиком (§7).
- **Архив комнат**: без резервной копии и без предпросмотра не запускать — это необратимое по
  смыслу действие, хотя строки и остаются.
- **Один источник переписки на время перехода**: пока `chat_messages` комнат задач читаются в
  ленте карточки (`routes/tasks.ts:1278`), перенос делать целиком (шаг 12), а не выдёргиванием
  `channel='chat'` — иначе часть переписки пропадёт из карточки.
- **Изоляция истории**: шаги сессии роли не попадают в контекст Помощника, только итог.

- Код сервера не менялся, база не читалась и не менялась; всё в §13 — предложение.
