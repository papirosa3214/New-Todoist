# Дочерние сессии личной комнаты: назначение слота

Дата: 08.11.2026. Спецификация `docs/2026-11-08-role-slot-chat-branches-spec.md`
§1–2, §4–6. Решение владельца: «сессии из личных комнат создаются дочерние
сессии, которые работают у каждой роли в одной этой групповой комнате в рамках
задачи».

## Что было

Слот уже существовал как подзадача плана (`subtasks` + `slot_sessions` с файлом
сессии), но:

- связи «личная комната роли → ребёнок-слот» в базе не было: ни родителя сессии,
  ни попытки, ни поколения контекста в одном месте;
- карточки назначения в личной комнате роли не было вовсе — владелец не видел,
  что роль получила работу, из своей комнаты;
- отличить назначение от обычного обращения было нечем.

## Что стало

**Миграция `203_chat_child_sessions`.** Таблица `chat_child_sessions`:

| поле | смысл |
| --- | --- |
| `kind` | `branch` (личная ветка) или `assignment` (назначение слота) |
| `parent_chat_id` | родитель сессии — личная комната роли |
| `talk_chat_id` | где идёт разговор: общая комната задачи |
| `role_id` | роль, которой выдан слот |
| `task_id`, `slot_id` | задача и конкретный слот (`subtasks.id`) |
| `attempt_no` | попытка слота: продолжает ту же связь, а не создаёт новую |
| `context_generation` | поколение контекста ребёнка |
| `status` | `assigned` / `delivered` / `answered` / `waiting` / `failed` |

`UNIQUE(kind, slot_id)` — повтор назначения, рестарт и повторная доставка не
создают вторую дочернюю сессию и второй запуск. У ветки `slot_id` пустой, а
NULL в SQLite уникальностью не считается — ветки друг другу не мешают.

**`lib/chatChildren.ts`.** `ensureSlotAssignment()` находит личную комнату роли
и комнату задачи, создаёт карточку идемпотентно; повтор увеличивает
`attempt_no`/`context_generation` и переводит статус в `delivered`.
`markAssignmentAnswered()` ставит «ответ получен» при закрытии узла вердиктом,
`assignmentsOf()` отдаёт карточки комнаты.

**Где вызывается.**

- `runtime/planSubtaskAdmission.ts:startPlanSubtaskRun` — сразу после того, как
  узел плана закреплён за ролью (claim + attempt). Ошибка карточки работу не
  срывает: пишем в журнал, слот идёт дальше.
- `closeNodeWithVerdict` — подтверждение «ответ получен» по факту вердикта, а не
  по факту доставки.

**Маршрут.** `GET /api/chats/:id/children` — карточки назначений комнаты: ID,
слот, роль, задача, комната разговора, статус, номер попытки. Права — как на
сам чат.

## Изоляция (главное)

Карточка назначения **не является сообщением** `chat_messages`. Отображаемая
карточка отделена от входа модели структурно: она физически не лежит в истории,
поэтому не может попасть в контекст ни через историю, ни через выжимку, ни
через кеш. Спецификация §5 прямо предупреждает, что одной проверки
`message_type='system'` недостаточно, — здесь проверять нечего.

## Проверки

`server/test/chatChildSessions.test.ts` (5 проверок, RED → GREEN):

1. назначение создаёт одну карточку, родитель — личная комната, разговор — комната задачи;
2. повтор назначения продолжает связь, второй карточки нет, попытка и поколение растут;
3. у роли с двумя слотами две карточки, у чужой комнаты — ни одной;
4. карточка не появляется в переписке личной комнаты (`chat_messages` не растёт);
5. `GET /api/chats/:id/children` отдаёт карточки, `answered` ставится один раз.

RED: на коде до правки — `no such table: chat_child_sessions`, 5 из 5. GREEN: 5/5.
Соседние: `planSubtaskAdmissionCycle` 4/4, `planNodeContinuation` 5/5,
`tsc --noEmit` чисто. `planSubtaskRecovery` — 3 проверки падают и на коде до
правки (проверено откатом), к этой работе не относятся.
