# Личные задачи владельца и задачи агентов: модель конфиденциальности (черновик)

> Статус: черновик для решения владельца, 19.10.2026. Код не менялся.
> Повод: в десктопном макете (`docs/mockups/desktop-workspace.html`) «Входящие / Сегодня / Предстоящее» показывают
> личные задачи Максима вместе с рабочими задачами агентов. Нужно, чтобы агенты и серверный агентский контур
> **не видели личное вообще**.

## 1. Что есть сейчас

### 1.1. Уже существующий механизм: приватный проект

В `projects` есть флаг `is_private` (задача 9d583c58…). Правило в `server/src/access.ts`:

- `privateProjectHides()` (`access.ts:204`) — приватный проект и его задачи скрыты от всех, кроме `role='owner'`,
  включая оркестратора и агентов; ответ 404, как будто проекта нет;
- `getTaskForRead / ForWrite / ForReview` проверяют приватность **до** «видит всё» (`access.ts:386`);
- `visibleProjectScope()` (`access.ts:345`) режет приватные проекты из списков;
- `getProjectForFiling()` (`access.ts:585`) не даёт агенту подать задачу в приватный проект;
- списки задач (`routes/tasks.ts:560`, `:686`) и поиск (`routes/search.ts:58`, `:110`) фильтруют `p.is_private`.

Живая база (`server/taskflow.db`, 19.10.2026): 5 проектов, приватный один — «Apple Напоминания» (0 задач);
«Учёт личных финансов» **не** приватный (4 задачи). Пользователи: владелец, оркестратор, 11 агентов (`type='ai'`), «Система».

### 1.2. Главная дыра: задачи без проекта («Входящие»)

Фильтр приватности везде записан как

```sql
(p.id IS NULL OR (p.is_private = 0 ...))
```

`p.id IS NULL` — это задача без проекта, то есть **«Входящие»**. Такие задачи считаются открытыми, а
`seesEveryTask()` (`access.ts:184`) даёт агентам, оркестратору и «Системе» «видно всё». Значит, всё, что владелец
надиктовал во Входящие, агент читает. Сейчас таких задач 15 из 107.

Личных задач с датой, но без проекта, это касается так же: «Сегодня» и «Предстоящее» — срезы по дате, а не отдельное
хранилище.

(б) половина серверного агентского контура (runtime, контекст ролей, память, секретарь) читает `tasks` в обход ворот.
Каждый новый путь — это новая точка, где надо не забыть фильтр.

## 2. Что значит «агент личного не видит»

Предлагаемое определение, его стоит утвердить отдельно:

1. Личная задача не попадает ни в один ответ API, MCP, инструмент роли/оркестратора, контекст, промпт, поиск,
   эмбеддинг-индекс, уведомление или вебхук для учётки, у которой `role != 'owner'`.
2. Агент не может узнать, что она существует: 404, а не 403; в счётчиках её нет.
3. Агент не может создать задачу в личном пространстве и не может сделать личную задачу ребёнком рабочей
   (и наоборот) — граница не пересекается деревом.
4. Перевод задачи из личного в рабочее делает только владелец, явно («отдать агентам»). Обратный перевод снимает
   задачу у агента и останавливает его заходы.
5. Владелец видит обе стороны вместе — это уже чисто клиентская склейка (макет desktop-workspace).

## 3. Варианты

### Вариант А. Флаг на задаче + «закрыто по умолчанию» в воротах

`tasks.visibility` (`'personal' | 'agents'`), по умолчанию для задач владельца — `personal`; Входящие владельца
становятся личными. Ворота `access.ts` получают одну функцию `personalTaskHides()` рядом с
`privateProjectHides()`, а SQL-шаблон `p.id IS NULL OR …` заменяется общим `visibleTaskScope()`.

- ➕ Минимум переделок, одна база, одна модель данных, склейка в UI бесплатна.
- ➕ Повторяет уже работающий механизм приватного проекта.
- ➖ Безопасность держится на дисциплине: каждый прямой `SELECT FROM tasks` в runtime (п. 6, 7, 8, 13, 14 — их
  десятки) надо пройти и закрыть. Новый код снова может забыть.
- ➖ Агентский процесс и личные данные лежат в одном файле SQLite: любой агент с доступом к shell на .110
  (роли работают в worktree на той же машине) может открыть `taskflow.db` напрямую. Флаг от этого не защищает.

### Вариант Б. Личное пространство = приватный проект (без нового поля)

«Личное» — это один или несколько проектов с `is_private=1`; Входящие владельца по умолчанию кладутся в личный
проект «Входящие», а не в `project_id = NULL`. Дыра п. 1.2 закрывается тем, что задач без проекта у владельца
больше нет, плюс `p.id IS NULL` для агентов меняется на «скрыто».

- ➕ Почти без схемы: механизм приватного проекта уже покрыт тестами (`server/test/projects.test.ts` и др.).
- ➕ Наглядно для владельца: «Личное» — это проект(ы).
- ➖ Всё то же, что у А: прямой SQL в runtime и общий файл базы.
- ➖ Задача бывает личной по смыслу, но лежит в рабочем проекте (например «позвонить подрядчику» в «Учёт финансов»).
  Тогда нужен ещё и флаг — то есть вариант А.

### Вариант В. Отдельная база для личного (физическая изоляция)

Личные задачи живут в отдельном файле SQLite (`personal.db`), который открывает **только** код владельца:
отдельный модуль/роуты `/api/personal/*`, доступные лишь сессии `role='owner'`. Агентский контур (runtime,
MCP, роли, оркестратор, память, поиск агентов) этот файл не импортирует вообще. Клиент склеивает два списка
в «Входящие / Сегодня / Предстоящее».

- ➕ Сильнейшая гарантия: новый код в runtime физически не может «забыть фильтр» — данных просто нет в его базе.
  Этого и просил владелец: «что видит сервер вообще и контур агентский, какие задачи, а какие он даже не
  обращает внимания».
- ➕ Можно дать файлу другие права ОС (отдельный пользователь, или шифрование), и тогда роли с shell на .110
  тоже не дотянутся. Без этого шага изоляция только логическая.
- ➖ Самая большая работа: дублировать CRUD задач, повторы, напоминания, метки, вложения, поиск, Apple
  Напоминания, iOS-клиент; всё общее (метки, проекты) придётся либо копировать, либо делать ссылками.
- ➖ Перевод «личное → агентам» становится переносом между базами (новый id, история остаётся в личной).
- ➖ Тот же процесс `tsx` держит обе базы — от уязвимости в самом сервере изоляции нет; полную даёт только
  отдельный процесс/пользователь ОС.

### Сводка

|                                  | А: флаг                      | Б: приватный проект | В: отдельная база           |
| -------------------------------- | ---------------------------- | ------------------- | --------------------------- |
| Объём работы                     | средний (аудит ~40 мест SQL) | малый–средний       | большой                     |
| Гарантия от «забыли фильтр»      | нет, нужен страж             | нет, нужен страж    | да, по устройству           |
| Защита от агента с shell на .110 | нет                          | нет                 | да, если права ОС разделены |
| Склейка в UI                     | бесплатно                    | бесплатно           | клиент мержит два источника |
| Личная задача в рабочем проекте  | да                           | нет                 | нет (только перенос)        |

## 4. Рекомендация

**Сначала А+Б, при этом держать курс на В.**

1. **Сейчас (дёшево, закрывает главную дыру):** «закрыто по умолчанию». Задача владельца без проекта и любая
   задача с `visibility='personal'` агентам не видна. Одна функция в `access.ts` вместо разбросанного
   `p.id IS NULL OR …`; переделать на неё `routes/tasks.ts`, `routes/search.ts`; запретить пересечение
   границы через `parent_id`. Новые задачи владельца во Входящих — личные; агентам задача уходит, когда владелец
   явно её назначил агенту или положил в рабочий проект.
2. **Сразу за этим — закрыть обходы ворот:** контекст ролей (`roleProjectContext.ts`), `taskflow_children`,
   runtime-чтения, секретарь, эмбеддинги, память/KB. Минимальное правило: в `server/src/runtime/**` и `lib/**`
   нельзя читать `FROM tasks` без `visibleTaskScope`. Проверять это тестом-линтером (grep в тесте), иначе через
   месяц снова протечёт. По правилу приборов — запись в `docs/watchers.md` и сторож, который **пробным ходом**
   создаёт личную задачу-маяк и проверяет, что её не отдают API агента, MCP `my_tasks`, поиск и контекст роли.
3. **MCP `taskflow`** (`mcp_server.py:279`): перестать тянуть весь `/api/tasks` и фильтровать у себя — просить
   у сервера только своё (`?assignee=me`).
4. **Отдельная база (В)** — когда/если владелец решит, что угроза «агент с shell читает файл базы» реальна.
   Тогда в ней сразу и отдельный пользователь ОС. Шаги 1–3 переносу не мешают: тот же `visibleTaskScope`
   становится границей, по которой режется база.

## 5. Вопросы владельцу

1. Задача во Входящих по умолчанию **личная** (агентам не видна, пока не отдашь) — так?
2. Задача, назначенная агенту, автоматически становится рабочей, или «отдать агентам» — отдельное действие?
3. Нужна ли защита от агентов, у которых есть shell на .110 (они могут открыть файл базы)? От ответа зависит,
   нужен ли вариант В.
4. «Учёт личных финансов» — это личное (тогда проект надо сделать приватным) или работа для агентов?
5. Секретарь (голосовой) — свой для владельца и личное ему видно, или он тоже агент и личного не видит?
