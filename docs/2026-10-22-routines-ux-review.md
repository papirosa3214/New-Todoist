# Экран «Мои рутины» — разбор живого кода и правки (UX-ревью)

Дата: 22.10.2026. Автор: Дизайнер. Карточка: `c14e6335-6157-4691-ab54-b922b643ef17`, этап «design».
Полная спека (экраны, state matrix, доступность, открытые вопросы): заметка TaskFlow `note://5916da80-1d61-44fb-994a-e4b05b6a0f1a`.
Макеты и словарь — `docs/2026-10-22-routines-screen-design.md` (дизайн, 22.10.2026).
Контракт — заметка «Рутины и расписание TaskFlow — архитектурный план» (`3616b9d8-0254-4237-8634-78b0af86985b`).

Экран и API уже реализованы (`src/screens/RoutinesScreen.tsx`, `src/api/schedules.ts`, `server/src/routes/schedules.ts`, `server/src/runtime/schedules/`). Ниже — что в коде расходится с макетом и что править. Ничего из этого не правилось в этом коммите: коммит содержит только документ.

## 1. Критично

**Д1. «Еженедельно» и «Ежемесячно» без выбора дня; показанный следующий запуск может не совпадать с фактическим.**

Форма предлагает правила, но день не выбирается: `src/screens/RoutinesScreen.tsx:250`.
Сервер берёт якорь от даты создания рутины (`server/src/runtime/schedules/store.ts:277`, `anchorFromCreatedAt`), а при создании первый `next_run_at` считается с фиксированным якорем `1970-01-01` (`server/src/routes/schedules.ts`, блок `const anchor = { year: 1970, month: 1, day: 1 }`) — это четверг и 1-е число месяца.

Итог: рутина, созданная в пятницу, сразу после создания показывает «Следующий запуск: <четверг>», а фактически сработает в пятницу (после пересчёта тиком, `server/src/runtime/schedules/tick.ts:94`).

Что сделать:
- в форму добавить выбор дня недели для «Еженедельно» и дня месяца для «Ежемесячно»;
- в то же время считать первый `next_run_at` с тем же якорем, что и тик (либо с явным днём из правила — тогда якорь не нужен).

**Д2. «Запустить сейчас» не даёт обратной связи, если задача не создана.**

Клиент берёт только `run.task_id` (`src/screens/RoutinesScreen.tsx:449`), а при пропуске (прошлый экземпляр не закрыт) или ошибке её нет — баннер не рисуется, пользователь жмёт кнопку и не видит ничего. Сервер статус отдаёт: `run.status` в ответе `POST /api/schedules/:id/run-now` (`server/src/routes/schedules.ts`).

Что сделать: разбирать `run.status`:
- `created` → «Запуск создан» + ссылка «Открыть задачу»;
- `skipped` → «Пропущено: прошлый запуск ещё не закрыт» + ссылка на открытую карточку (`current_task_id`);
- `failed` / `error` → «Не удалось запустить: <причина>».

## 2. Средняя серьёзность

**Д3. В истории смешаны языки и теряется причина.** При наличии `task_id` и статусе не «created» показывается латинское `failed`/`error` (`src/screens/RoutinesScreen.tsx:101`), без `task_id` — «не создана» вместо «ошибка» (`:111`). Причина (`run.detail`) не показывается, хотя сервер её пишет (`server/src/runtime/schedules/tick.ts:149, 177, 202, 239`).

Словарь: created → «задача создана», skipped → «пропущено», failed → «не создана», error → «ошибка»; ниже — `detail` строкой 13 px.

**Д4. Интервал показан техническими значениями.** «5m», «15m», «1h» (`src/screens/RoutinesScreen.tsx:57, 319`) вместо «Каждые 5 минут», «Каждые 1 час». Сервер уже умеет человеческие подписи (`server/src/runtime/schedules/rules.ts:350`, `ruleLabel`).

**Д5. Выбор правила — не группа радиокнопок.** Кнопки с декоративным кружком `aria-hidden` (`src/screens/RoutinesScreen.tsx:255-266`): скринридер слышит «Ежедневно» без «выбрано», стрелками правило не переключается. Нужно `role="radiogroup"` / `role="radio"` + `aria-checked` (или скрытые `input[type=radio]`), имя группы — «Правило».

## 3. Мелкая серьёзность

- **Д6.** У дней недели нет имени группы: связать с подписью «Дни недели» (`src/screens/RoutinesScreen.tsx:280-300`).
- **Д7.** Радиусы вне шкалы: карточки и строки — `rounded-xl` (12 px), поля — `rounded-xl`; в дизайн-системе карточка 16 px (`r-surface`), поле 8 px (`r-control-md`). Файлы: `RoutinesScreen.tsx:63, 503, 247, 336, 354`.
- **Д8.** «Следующий запуск» абсолютной датой («26 окт., 09:00»). Для ближайших семи дней — «сегодня в 09:00», «завтра в 09:00», «в понедельник в 09:00» (`src/screens/routinesFormat.ts:9`).
- **Д9.** Приостановленная рутина без запусков: «Последний запуск: —» → «Запусков ещё не было» (`RoutinesScreen.tsx:519`).
- **Д10.** В форме нет «Отмены»; кнопка «+» одновременно открывает и закрывает форму, и по виду это не видно (`:225, 236`).
- **Д11.** После создания нет подтверждения: ожидался тост «Рутина создана» (`:196-205`).
- **Д12.** История обрезается до 10 записей без «показать все» (`:96`).

## 4. Что нужно от сервера

Из запрошенного ранее половина уже сделана: `rule_label` отдаётся (`rules.ts:350`, `routes/schedules.ts:57, 134`), `next_run_at` + `timezone`, `status`, `last_run_at`, `current_task_id` — в ответе, ручка `GET /api/schedules/:id/runs` и превью `GET /api/schedules/preview` есть.

Осталось:
1. якорей при создании и при срабатывании должен быть один (см. Д1);
2. `detail` в истории — клиенту нужно лишь показать, дополнительных полей API не требуется.

## 5. Критерии приёмки для delivery и QA

Веб:
1. `/routines` открывается, вход с «Обзора» и из «Настроек»; на 375, 768, 1280 px нет горизонтальной прокрутки, на 1280 ширина колонки 880.
2. Строка показывает название, правило, время, роль и следующий запуск; время — в зоне самой рутины.
3. Для «Еженедельно» выбирается день недели, для «Ежемесячно» — день месяца; показанный следующий запуск совпадает с фактическим днём срабатывания.
4. Пустой список: заголовок, пояснение, кнопка «Создать рутину» с тап-зоной не меньше 44.
5. Загрузка — скелет из трёх строк без скачка высоты; ошибка — `ErrorBanner` с «Повторить».
6. Шесть правил в форме; для «Конкретные дни» — выбор дней; для «Каждые N минут» — варианты от 5 минут с подписями по-русски.
7. Превью пересчитывается на каждое изменение; при ошибке расчёта — «Не удалось посчитать ближайший запуск», а не пустой блок.
8. Пауза, возобновить и «Запустить сейчас» меняют строку без перезагрузки страницы; «Запустить сейчас» во всех трёх исходах даёт понятную подпись, при создании — ссылку на карточку.
9. История: дата, результат по-русски, причина для пропуска и ошибки, для созданной карточки — переход в неё.
10. Доступность: сценарий проходится с клавиатуры; выбор правила — радиогруппа с `aria-checked`; у иконочных кнопок есть подписи; мелкие подписи не ниже 4.5:1; фокус виден.
11. Ни одного нового цвета, радиуса, отступа и кегля вне шкалы `src/index.css`.

iOS (карточка iOS):
12. «Мои рутины» — строка в «Обзоре» и отдельный экран; состав вкладок не меняется; словарь совпадает со спекой.
13. Строка: название 20/600, подпись 13, следующий запуск 12, тап-зона не меньше 44; «+» 44×44; форма — отдельный экран с прокруткой; «Создать рутину» 48 на всю ширину.
14. Свайп по строке даёт паузу, запуск сейчас, историю и удаление; удаление спрашивает подтверждение.
15. Для пустого списка, ошибки и загрузки есть свои состояния, с «Повторить» там, где список не пришёл.
16. VoiceOver читает строку как «название, правило, следующий запуск», у кнопок есть подписи; Dynamic Type до XL не обрезает название.

Сквозное:
17. Слово «повтор» применительно к рутине не используется ни в одном клиенте.
18. Оба клиента читают одни и те же поля ответа `/api/schedules`, текст правила приходит с сервера.
19. Пустая рутина без выбранного правила невозможна: сервер и клиент проверяют одинаково.

## 6. Открытые вопросы (владельцу)

1. День для «Еженедельно» и «Ежемесячно» — предлагаю явный выбор в форме.
2. Название экрана: «Мои рутины» или «Рутины» (в коде «Мои рутины»).
3. Минимальный интервал: сервер разрешает от 5 минут — это 288 карточек в сутки.
4. Часовой пояс: сейчас свободный ввод — опечатка уедет в зону, которую сервер не примет.
5. Правила с указанием дня — общий список или отдельный раздел «Обзора».
6. cron сервер умеет (`rules.ts`, `parseCron`), в форме его нет и решение владельца не зафиксировано — пока не показываем.
7. iOS: форма рутины отдельным экраном (предлагается) или шторкой.

## 7. Что не проверено

- Клиент на телефоне не смотрел (iOS — отдельная карточка).
- Живой прогон не делал: модуля рутин на боевом сервере ещё нет, выкладка — отдельный шаг.
- В браузере экран не открывал: проверка чтением кода и тестами `src/screens/RoutinesScreen.test.ts` (4 теста).
- Аудит на 375/768/1280 px и с клавиатуры — после правок, отдельной проверкой QA.
