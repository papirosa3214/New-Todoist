# Уточнения в чатах и память ролей
Дата: 21 октября 2026. Сервер: New-Todoist, отдельная ветка `codex/chat-live-clarifications`.
Рабочее дерево: `/tmp/taskflow-chat-live-clarifications`.
Статус: исходники и профильные проверки готовы; в main не влито, сервисы не перезапускались.

## Что изменено
- Сообщение владельца в уже работающий обычный чат роли передаётся через SDK steer, без отмены текущего поручения. Секретарь использует тот же путь.
- Сообщения разных чатов и ролей изолированы. Обычная адресация групп сохраняется: уточнение направляется выбранным получателям.
- Передача в SDK не считается успешной доставкой. Нужно событие потребления пользовательского ввода и сохранённый успешный ответ.
- Непотреблённое уточнение выполняется обычной очередью. Его место резервируется до ожидания SDK/CLI, поэтому более позднее сообщение не обгоняет его.
- Исходные записи durable queue, дедупликация и проверка поколения сессии сохраняются. Вложения передаются тем же описанием, что в обычном ходе.
- Для внешнего Claude CLI replay stdin отделён от результата: подтверждение приходит после соответствующего result, ввод закрывается после результатов всех принятых сообщений.
- Рабочие сессии задач/тематических комнат сохраняют существующий механизм доставки; новый канал добавлен к обычным чат-сессиям.

## Почему Разработчик обходил память
Проверены реальные сохранённые steps личного чата «Разработчик», а не только его ответ.
В длинном ходе по Apple Calendar/Reminders он искал по исходникам без taskflow_recall/taskflow_kb_search.
В следующем ходе успешно вызвал taskflow_remember для общей памяти, затем прочитал MEMORY.md личного Claude и записал туда feedback-search-memory-first.md.
Роль builder работает через Pi, а не через внешний Claude CLI. Это выбор роли при доступном файловом инструменте, а не обязательное устройство её памяти.

Общая инструкция уже требовала сначала память и библиотеку; память темы уже автоматически добавлялась через roleProjectContext. Одного правила оказалось недостаточно.
Добавлено:
1. Поиск по библиотеке TaskFlow перед запуском хода: до 3 выдержек по 700 символов с id документа и датой.
2. Явное правило во входном контексте и системном каноне: память роли — taskflow_recall/taskflow_remember, документы — библиотека TaskFlow; личная память Claude/Codex для знаний роли не используется и не дублируется.
3. Ошибка поиска библиотеки не выдаётся за отсутствие знаний.
4. Выравнен список PLANNING_TOOLS: recall — чтение, remember — запись. Через универсальный инструмент recall уже был разрешён: исходное предположение о полном запрете в Планировании не подтвердилось.

Автопоиск использует тот же локальный searchNotes, что taskflow_kb_search; это не новый сетевой поиск по всем внешним датасетам RAGFlow. Существующие чужие файлы памяти и живые записи не удалялись и не переносились.

## Границы результата
- SDK применяет уточнение на ближайшей поддерживаемой границе, обычно между обращениями к модели/инструментами. Уже начавшийся внешний вызов не отменяется.
- Пока чат ещё создаёт сессию, сообщение может пойти обычной очередью; новый канал относится к уже активной сессии.
- Для CLI соответствие одного result одному stdin user turn проверено на протокольных фикстурах; живой CLI с моделью не запускался.
- Память направляется системной инструкцией и автоматическим контекстом. Это не файловая песочница, запрещающая любой произвольный write в .claude.
- iOS-клиент не менялся и не собирался. Приёмка владельцем в реальном чате после отдельного развёртывания ещё нужна.

## Сценарий приёмки после развёртывания
В личном чате Разработчика дать длинное поручение, затем во время инструмента отправить уточнение. Проверить, что оно учтено в том же ходе без повторного запуска поручения.
Повторить у Секретаря. Отдельно проверить быстрые сообщения B/C при окончании A.
По новой теме с существующим документом проверить сохранённые toolCall/toolResult и входные выдержки: сначала известные знания, затем адресное чтение кода; запись новых знаний через TaskFlow.
