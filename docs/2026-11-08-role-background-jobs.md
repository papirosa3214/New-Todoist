# Фоновые команды ролей — дизайн

Дата: 08.11.2026. Автор: агент по поручению владельца. Статус: на согласовании.
Репозиторий: `New-Todoist/server` (авторитетное дерево — на `.110`).

## Зачем

Долгая команда роли (сборка iOS, тесты сервера, выкладка) сейчас держит ход
целиком: пока команда идёт, роль не принимает новое сообщение владельца.
Прецедент 16.10.2026: указание дошло до роли-разработчика только после
семиминутной сборки. Цель — длинная команда идёт отдельно от хода, результат
приходит в переписку сам, роль продолжает работу.

Не цель: заменять синхронный bash, поддерживать интерактивные процессы,
запускать фоновые процессы на `.110` (там сервер, а не сборочные машины).

## Что есть сейчас (проверено по коду)

- `taskflow_host_bash` — инструмент pi поверх `hostBashOperations(machineId, cwd)`
  (`src/runtime/hostOperations.ts:80`), предел команды `BASH_DEFAULT_TIMEOUT_MS = 40 * 60_000`.
  Команда идёт демоном `taskflow-host` на маке, поток — кадрами `op_chunk`
  (`src/host/protocol.ts`).
- `runOperation(machine, op, args, { signal, onChunk, timeoutMs })`
  (`src/host/gateway.ts:177`) уже отдаёт поток по кадрам → фон строится **без
  правок хоста и без новой версии протокола**.
- Вызов держится за ход: `hostCall` проносит `AbortSignal` хода через
  `AsyncLocalStorage` (`src/runtime/hostOperations.ts:33-38`), а обрыв сокета
  reject'ит все висящие вызовы машины (`src/host/gateway.ts:271`).
- Сторож тишины: `touchRunActivity(runId)` (`src/runtime/inProcessRun.ts:1141`),
  `sweepStaleInProcessRuns()` (`:1230`), порог `STALE_RUN_MINUTES` = 30
  (`:1133`), тик — `src/runtime/roleRunWorker.ts:129`. Функция `markActivity`,
  которую я называл раньше, не существует. Карточный ход отмечается только на
  `tool_execution_start` (`:1834`) — поэтому **уже сейчас** 40-минутная
  команда обрывается 30-минутной зачисткой.
- Чатовые ходы живут не в `activeRuns`, а арендой доставки:
  `startDeliveryHeartbeat` (`src/runtime/chatQueue.ts:286-304`) →
  `heartbeatMessageDelivery` (`:252`), пока `modelActive || tools.size > 0`.
- Разбудить роль сообщением можно только связкой `enqueueMessageDelivery`
  (`src/runtime/chatQueue.ts:41`) + `recoverAgentDelivery({chatId, roleId, queueRowId})`
  (`src/routes/chats.ts:2338`); прецедент — `deliverDigest`
  (`src/runtime/roleSubagentCall.ts:423-461`), он сознательно пишет сообщение
  **без** `message_type`.
- `message_type='system'` в историю модели не попадает
  (`src/lib/chatHistoryModel.ts:16`, `src/lib/serviceNoise.ts:30`) — системной
  строкой роль не разбудить по существу, она получит текст один раз и без
  контекста.
- Контекст инструмента: `CatalogContext` уже несёт `chatId, messageId, runId`
  (`src/runtime/roleToolCatalog.ts:82,101`), но `Context` в
  `src/runtime/roleHostAccess.ts:16` — только `{ role, taskId? }`; `machineId`
  вычисляется внутри `executeRoleHostTool` (`:53-55`).
- У синхронного bash **нет** проверки `cwd` по корням; корни машины доступны как
  `machine.allowed_roots` (`src/runtime/roleHostAccess.ts:67`).
- `roleBashKillError` (`src/runtime/roleBashGuard.ts:77,102`) сторожит только
  локальный bash роли; на хост-операции не распространяется.

## Решения

### Р1. Реестр в сервере, поверх существующего вызова хоста

Новый модуль `server/src/runtime/backgroundJobs.ts`. Старт — это
`runOperation(..., { onChunk, timeoutMs })`, чей промис никто не ждёт: сервер
складывает кадры в буфер задачи, состояние выводит по завершении.

Жёстко и явно:
- сигнал хода **не передаём** (`signal` не пробрасывается), иначе отмена хода
  убивает фоновую команду;
- любые отказы шлюза — это состояния задачи, а не исключения:
  `failPendingOps` (`gateway.ts:271` — связь потеряна) → `lost`,
  таймаут (`gateway.ts:201-208`) → `timeout`, `cancelOperation` (`:253`) → `stopped`;
- реестр живёт в памяти: при перезапуске сервера задачи помечаются `lost` и
  роли сообщается, что команду надо перепроверить и перезапустить. Таблица в БД
  не нужна: `role_run_jobs` — про ходы ролей, а не про процессы.

### Р2. Один инструмент `taskflow_host_bg`

| действие | аргументы | ответ |
| --- | --- | --- |
| `start` | `command`, `cwd?`, `project_id?`, `task_id?`, `timeout` (сек, ≤ 40 мин) | `jobId`, `machine`, `startedAt`, `state: "running"` |
| `status` | `jobId` | `state`, `exitCode`, `durationMs`, `bytes`, `tail` (2 КБ) |
| `output` | `jobId`, `offset?` | до 64 КБ вывода за вызов |
| `stop` | `jobId` | `state: "stopped"` |
| `list` | — | свои задачи: `jobId`, `command` (200 символов), `state`, `startedAt` |

Описание инструмента говорит прямо: «сборка, тесты, выкладка и всё дольше
нескольких секунд — здесь; `taskflow_host_bash` — только для коротких команд».

Регистрация — через `roleHostAccessTools` в `src/runtime/roleHostAccess.ts`;
`src/runtime/roleToolCatalog.ts` трогать не надо: он подхватит инструмент сам
(`:101`), сделает активным (`staysActive`, `:63`) и запишет аудит (`:114-121`),
`roleToolScope.ts:6-8` его пропустит. В `Context` добавляется `chatId` — без него
задачу некуда вернуть.

### Р3. Завершение — сообщением роли, а не системной строкой

По завершении (код 0, ошибка, таймаут, остановка, потеря связи):

1. `logServerEvent` (`scope: "host"`, `kind: "bg_job_end"`);
2. в переписку пишется обычное сообщение **без** `message_type` (как
   `deliverDigest`): «Фон завершён: `xcodebuild …`, код 0, 3 мин 12 с» + хвост
   лога 4 КБ — так оно попадает в историю модели;
3. будим роль связкой `enqueueMessageDelivery` + `recoverAgentDelivery({chatId,
   roleId, queueRowId})` (`src/routes/chats.ts:2338`, прецедент
   `roleSubagentCall.ts:423-461`).

Если чат карточки без слота (`src/routes/chats.ts:3411` — `slotChoiceNotice` и
`return null`), пробуждение не делаем: сообщение и итог остаются в переписке,
роль увидит их следующим ходом, и это отмечается в журнале. Владельцу в этом
случае приходит отдельная строка «фон завершён, роль не разбужена — в комнате
нет слота».

### Р4. Тишина не считается молчанием

Задача регистрирует активность в тех же механизмах, что и обычный ход:
- карточный ход — `touchRunActivity(runId)` (`inProcessRun.ts:1141`) и
  `touchTaskActivity(taskId)` (`:1152`) при старте и на каждом кадре;
- чатовый ход — продление аренды доставки (`chatQueue.ts:295-297`), пока у роли
  есть незавершённая задача.

Попутно закрывается сегодняшняя дырка: 40-минутная синхронная команда в
карточном ходе перестаёт обрываться 30-минутной зачисткой — активность
отмечается и на `tool_execution_start`/кадрах, а не только на старте.

### Р5. Пределы и честные отказы

- не больше 3 задач на роль и 6 на карточку;
- предел времени 40 минут; по истечении — `op_cancel` и состояние `timeout`;
- вывод: 4 МБ держит шлюз (`deliverChunk`, `gateway.ts:356-380`,
  `HOST_MAX_OUTPUT_BYTES`, `protocol.ts:40`), сервер хранит хвост до 4 МБ и
  отдаёт его страницами; лог-файлов на маке не заводим — некому их убирать;
- **одно рабочее дерево — одна команда**: синхронный bash и фон работают в одном
  worktree (ключ `taskId` в `roleHostAccess.ts:57-61`), поэтому `start` в занятое
  дерево отказывает прямо: «в этом дереве уже идёт команда `<jobId>`»;
- записи о завершённых задачах живут час;
- при архивации карточки её задачи гасятся — рядом с существующей остановкой
  `role_run_jobs` (`src/lib/taskArchive.ts:209,219`).

### Р6. Безопасность

- `start` проходит собственный сторож хостовых команд: те же запреты, что в
  `roleBashKillError` (`roleBashGuard.ts:77,102`), вынесенные в общий модуль для
  хост-операций — сейчас на хосте гарда нет вообще;
- `cwd` проверяется по `machine.allowed_roots` (`roleHostAccess.ts:67`);
  проверку пишем с нуля — у синхронного bash её нет;
- команда по-прежнему исполняется демоном на маке в песочнице проекта: сервер
  новых прав не получает.

## Как проверяем

Только точечные проверки: без симулятора, без полного прогона. Явные файлы,
`--maxWorkers=4`:

- `server/test/background-jobs.test.ts` — модуль на подменённом `runOperation`:
  старт не блокирует; `status`/`output`/`stop`; код выхода; таймаут; потеря
  связи → `lost`; пределы на роль и карточку; отказ при занятом дереве;
- `server/test/background-jobs-tool.test.ts` — поверхность инструмента: схема,
  отказ сторожем, аудит, права роли;
- точечный тест на активность: незавершённая задача не даёт ходу считаться
  молчащим, а 40-минутная синхронная команда не обрывается зачисткой.

RED → GREEN: тесты пишутся до кода и обязаны падать на текущем дереве.

- стриминг вывода в чат в реальном времени (сейчас — хвост по запросу и итог);

## Что учтено после проверки кода

Расхождения первой редакции, найденные по коду: несуществующая функция
`markActivity`; чатовые ходы живут на аренде доставки, а не в `activeRuns`;
`enqueueMessageDelivery` сам не будит — нужен `recoverAgentDelivery`; системные
сообщения не попадают в историю модели; у bash нет проверки `cwd`; сторож
`roleBashGuard` не покрывает хост; обрыв сокета и сигнал хода убивают висящий
вызов; каталог инструментов не требует правок.
