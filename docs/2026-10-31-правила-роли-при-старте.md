## 2. Короткий вывод на 31.10

1. **Правил «одного набора» по-прежнему нет.** Инструкция роли приходит тремя разными путями: системный промпт, задание пользовательским текстом и слои из редактора. Одно правило может прийти в двух путях с разными формулировками, другое — не прийти ни в одном.
2. **Утечки правил карточки в чат больше нет** — это главная поправка к карте от 28.10.
3. **Слой правил, который роль получает, равен коду.** Переопределение из базы его сейчас не затеняет, но и механизм приоритета не чинили: включите переопределение — код снова перестанет действовать.
4. **Правила среды `.110` потеряны по-настоящему** (работать локально и не по SSH, не запускать `find /`, переспрашивать при неоднозначной просьбе, брать свою историю из `taskflow_my_stats`). Их нет нигде; решение — за владельцем.
5. **Правила карточки не доходят до модели в трёх режимах карточки: ревью, ответ в ленте, продолжение работы.** Они доходят только в «карточка без слота» и «слот плана». Это новый непокрытый случай — по нему работает сам ревьюер.
6. **Блок «требуется подтверждение правил» не доходит никуда** — механизм «применил правило = подтвердил» на уровне модели не работает.

## 7. Что не доходит никуда

1. **Правила среды `.110` (`local_policy`) — потеряны, свершилось.** Слой удалён из кода целиком: в слитом `main` нет ни `LAYER_CATALOG`, ни `META`, ни `readOriginal`, ни подстановки `{localPolicy}` в `chat.wrapper`; в живой сборке (`server/dist`) — 0 совпадений. В канон (`server/scripts/role-system-prompt.md`, 347 строк) эти правила не перенесены: 0 совпадений по «taskflow_my_stats», «Не запускай find», «по SSH», «локально на .110», «Среда выполнения». Ни одна роль их не получает — ни в чате, ни в карточке, ни субагентом. Что именно потеряли (текст слоя в `cc49fb59`, `instructionDefaults.ts:122-137`):
   - «Работай исключительно локально на этой машине; не подключайся к .110 по SSH и не ищи sshpass/expect»;
   - «Не запускай find / и не обходи системные каталоги или NAS без отдельного явного поручения владельца»;
   - «Если просьба владельца неоднозначна … — сначала коротко переспроси … а не уходи в широкое исследование вслепую»;
   - «Если владелец спрашивает про твою же историю работы … — используй taskflow_my_stats … не выдумывай ответ».
2. **Правила карточки в трёх режимах карточки: ревью, ответ в ленте, продолжение работы** (§5.1). Правила вычисляются, но в шаблон не вставлены, а список плейсхолдеров их не содержит.
3. **Блок «требуется подтверждение правил»** (`rules.pending_acknowledgement`, `roleContextResolver.ts:405-426`). Попадает только в манифест снимка и в API состава правил. Ни в один промпт не вставляется: механизм «применил правило = подтвердил» на уровне модели не работает — роль не видит, что от неё ждут подтверждения.
4. **Правка слоя `role.prompt` из редактора** в карточном ходе: `AGENTS.md` подмешивается файлом (`roleHome.ts:283`), а не через `composeLayer`. В чате правка доходит (`instructionResources.ts:243`). В карточке — не проверено вживую (§12).

## 10. Решение, которое нужно от владельцу

Правила среды `.110` вычеркнуты из кода и не перенесены никуда (§7, п. 1). Сегодня ни одна роль не получает: работать локально на этой машине, не подключаться по SSH, не запускать `find /`, переспрашивать при неоднозначной просьбе, брать свою историю из `taskflow_my_stats`.

Два варианта:

- **вернуть в канон** (`server/scripts/role-system-prompt.md`) — правила станут общими для чата, карточки и субагента, с одного места; цена — канон растёт и его правка требует рестарта сервера (правило кэша канона);
- **восстановить слой** `local_policy` в коде — правила снова будут отдельным слоем, редактируемым из редактора слоёв; цена — снова отдельный слой, который надо возить в каждом режиме (именно это и сломалось при слиянии).

Рекомендация Аналитика: **вернуть в канон** — слой `local_policy` уже показал, что удаление слоя без переноса текста ломает правила тихо.

Правки в коде по этому пункту в карточке не делались: карточка — только анализ (границы задачи), решение за владельцем.

## 12. Ограничения

- База TaskFlow не читалась: ни файл БД, ни таблицы. Вопрос «кто сейчас затеняет слой `rules`» закрыт косвенно, но надёжно: штатный инструмент `taskflow_rules` вернул текст, дословно совпадающий с кодом, — значит активного переопределения для правил нет. - Правка слоя `role.prompt` из редактора в карточном ходе и работа `noContextFiles` в загрузчике Pi проверены по коду, но не вживую.
- Внешний путь запуска роли через отдельный процесс Pi (`PiRuntimeAdapter.ts:1894`) не разбирался детально: там собирается `role.prompt`; слой `local_policy` в слитом `main` уже не упоминается (остался только комментарий на `PiRuntimeAdapter.ts:916`).

- Состояние PR на GitHub не смотрелось: доступа по ssh у роли нет; слияние подтверждено по `main` (коммит `4ad29d89`).
- Канон ролей кэшируется в процессе сервера: правка `role-system-prompt.md` не доедет до ролей до рестарта сервера — это важно для варианта «вернуть в канон» (§10).
