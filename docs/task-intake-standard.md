# Единый порядок заведения работы (стандарт, 06.10.2026)

> Как заполнять сами задачи в Linear — отдельный документ `docs/linear-issue-standard.md`. Здесь — что происходит дальше в TaskFlow.

Собран из: правил MCP TaskFlow (формат описания), решений владельца 05–06.10.2026 и практики этих двух дней. Менять только с ведома владельца.

## 1. Где начинается работа: Linear, потом карточки

1. **Проект в Linear.** Метка «Сейчас» — делаем; «Задумка на будущее» — только записано, не берём. Название проекта — что получится в итоге.
2. **Вехи проекта** (3–4 этапа, нумерованные: «1. Основа», «2. Компоненты», «3. Приёмка») — **только в Linear**, для обзора прогресса. В TaskFlow этапов нет: решение владельца 06.10.2026. Импорт вехи не переносит.
3. **Задачи** в проекте, каждая привязана к вехе. Связи «блокирует / заблокирована» ставятся сразу: порядок работы задаёт граф, а не нумерация. Подзадачи Linear — только если у куска работы свой самостоятельный результат; шаги ролей в Linear не заводят.
4. **Карточки в TaskFlow:** сейчас их заводит оркестратор (импорт из Linear, `lib/linearImport.ts`, умеет подзадачи любой глубины, связи и черновики планов, но пока не использовался — таблица импорта пуста). Руками параллельно с импортом не заводить, чтобы не задвоить.

## 2. Описание каждой задачи — четыре раздела, всегда в этом порядке

```
## Работа
Что сделать и исходный контекст.
## Результат
Что должно получиться: документ, изменение, проверяемый эффект.
## Критерии приёмки
Как проверить. Сборка или HTTP 200 сами по себе приёмкой не считаются.
## Границы
Что входит, что исключено, ограничения владельца. Не названы — «Дополнительные ограничения не указаны».
```

Название задачи — суть проблемы или результат, не ярлык. Условия владельца сохраняются дословно. Без сведений работу сделать нельзя — задать конкретный вопрос, а не подставить догадку.

## 3. Карточки в TaskFlow

- **Структура плоская, два уровня:** родитель-проект → дочерние карточки задач (внуков нет). Этапы-вехи в TaskFlow не заводятся.
- **Родительская (проект)** — собирает дочерние, сама не исполняется. Исполнителем на ней стоит **Оркестратор Claude** (из-за этого видна его аватарка в списках). Прогресс считается по дочерним.
- **Дочерняя** — одна задача проекта. Исполнителя на самой карточке не ставят: работают роли через план. Если задача линейная, внутри неё шаги-подзадачи; сложная (4+ шагов, разные компетенции) — дочерние карточки через `parent_id`.
- **План ролей** у каждой карточки: исполнитель → QA → Критик **последним**. Планы утверждает оркестратор.
- Карточку, созданную повторно (`tf_recreate.py`), старую переименовывать «🗑 УДАЛИТЬ — дубль · …»: удалить может только владелец.

## 4. Модели

- Основная у всех ролей — MiniMax-M3. Запасные цепочки (при лимите переключается само) — в `server/scripts/role-routing.yaml`: Критик и QA → `opencode-go/minimax-m3` → `opencode/space-bunny-free`; остальные → `opencode-go/deepseek-v4.1-flash` → `opencode/space-bunny-free`.
- Совсем механическую работу (сверка кадров, сбор скриншотов, правка текста) оркестратор ставит на `opencode/space-bunny-free` до запуска шага: `PUT /api/subtasks/:id/model`, потом `POST /api/subtasks/:id/run`. Проверяющих (QA, Критик) до бесплатной модели не опускать.

## 5. Запуск и параллельность

- Карточки, которые правят одни и те же файлы (общие `DESIGN.md`, `index.css`, `UI.tsx`), можно запускать параллельно, но конфликты слияния разбирает оркестратор. По умолчанию — по одной.
- Серверный код выкладывать (`tsc` + перезапуск) только когда нет идущих шагов.

## 6. Приёмка и закрытие

1. Критик вынес `approved`, ветка `roles/<id>` закоммичена.
2. Оркестратор вливает `git merge --no-ff roles/<id>`, прогоняет проверку типов и тесты области, разбирает конфликты.
3. В Linear задача — Done. **В TaskFlow карточку закрывает владелец**; сервер сам закрывает только дочерние карточки внутри плана-ветки при одобрении Критика (`branch_card_accepted`).
4. Каждое полномочие в обход API (правка БД, ручной перезапуск) — в «Г» файла `docs/2026-10-05-orchestrator-findings.md`.

## 7. Документы по задаче

Итоги и отчёты складываются в папку проекта → подпапка задачи (создаётся сервером сама). Отчёт пишется один раз, при сдаче на проверку, и только для объёмной задачи (есть дочерние или 5+ шагов).
