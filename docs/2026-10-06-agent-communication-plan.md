# Коммуникация агентов: диагноз и план (06.10.2026, вторая редакция)

Запрос владельца: агенты молчат — отваливаются, втыкают, блокируют без слова, чаты забиты флудом. Хочет, как у Гермеса: «где-то что-то завтык — всегда даст знать, в тишине не остаётся». Первая редакция (уровни нюансов, сводки, границы) отвергнута владельцем как имитация: нужно не надстройка, а устройство.

Основания: `docs/2026-10-06-hermes-communication-study.md` (код Гермеса на .110) и `docs/2026-10-06-hermes-official-docs-research.md` (официальная документация, по пересказам поиска).

## Диагноз (проверено по базе и коду 06.10)
- В инструкции ролей «зови коллегу» уже есть (`server/scripts/role-system-prompt.md`, «Командная работа») и не держится: Критик и Разработчик гоняют «принял, отвечу по message_id…» по 500–1800 знаков.
- Канал `agents` мёртв: 4 сообщения за всё время, последнее 05.10 14:08. Сообщение без адресата по задаче никого не будит (`routes/chat.ts`).
- Сбои (`plan_subtask_autostart_failed` ~16 за сутки, `plan_subtask_stalled_blocked`, `model_failover`) пишутся только в `task_events` свободным текстом, получателя нет. Упавший агент сказать не может, сервер за него не говорит.
- 141 уведомление за двое суток, прочитано 0; триггер `notifications_owner_no_activity` глушит владельцу `agent_state`.

## Главное отличие Гермеса
У него ничего не отпускается без исхода. Любое действие (личка коллеге, делегация, шаг воркера) заканчивается событием, которое ПОЛУЧАЕТ тот, кто его запустил, новым ходом: результат либо код причины сбоя. Агенту не нужно «помнить про коммуникацию»: тишина невозможна по устройству. У нас исход шага пишется в журнал и ждёт, пока оркестратор сам спросит (сторож `tf_watch.py`).

## План (по убыванию важности)
1. **Закрытый словарь причин сбоя** вместо свободного текста. Коды (по образцу Гермеса, под наши случаи): `provider_quota_limit`, `provider_rate_limit`, `provider_server_error`, `provider_auth_or_access`, `context_overflow`, `missing_config` (ошибка `role-routing`), `taskcontext_timeout`, `model_unavailable`, `step_stalled`, `runtime_died`, `cancelled`, `unknown`. Один классификатор по тексту ошибки. Места: `runtime/planSubtaskAdmission.ts`, `runtime/inProcessRun.ts`, `routes/subtasks.ts`.
2. **Первый получатель исхода — сервер, не оркестратор** (замечание владельца 06.10). Каждое завершение запуска шага (сдан, блок, сбой) создаёт событие с кодом, и сервер сам обрабатывает его по правилам, без модели и без чьей-либо живой сессии: повтор, перезапуск, снятие `dependency`-блока, старт следующего шага, `gave_up` после лимита, запись в ленту карточки. Следующему шагу плана приходит исход предыдущего. Причина: оркестратор живёт только пока открыта сессия; всё, что держится на нём или на сторожах (`tf_watch.py`), без него молчит. Образец — диспетчер kanban Гермеса (цикл, аренда, лимит неудач, автоблок) и стандартный взгляд карточки 71651ad0 («без оркестратора»).
   **Лестница получателей:** сервер по правилам → оркестратору только то, что правилами не решается (`needs_input`, `capability`, повторный блок того же вида, `gave_up` после того, как исчерпана вся цепочка моделей, развилка по плану) → владельцу только то, что меняет результат карточки. Оркестратору событие приходит новым ходом через `agent_inbox`, а не опросом.
3. **Политика повтора по коду** (в 71651ad0 уже есть автоперезапуск ≤2 раза). Временные (`rate_limit`, `server_error`, `taskcontext_timeout`, `runtime_died`) повторяются один-два раза в той же сессии. `context_overflow` — сжать и продолжить. `provider_quota_limit` и `provider_rate_limit` — не блок, а переключение на следующую модель цепочки (основная → запасная → бесплатная, `role-routing.yaml`, `providerFailover.ts`; метка занятости провайдера уже есть). Блок «лимит исчерпан» только когда исчерпана вся цепочка, включая бесплатную (владелец 06.10: до этого практически не дойдёт). `auth`, `missing_config`, `model_unavailable` модель не меняют и не повторяются: сразу блок с кодом и сигналом.
4. **Брошенный шаг как событие.** Шаг умер или завис: оркестратору приходит событие с хвостом журнала (20 строк) и снимком git рабочей копии «ветка @ коммит (N несохранённых файлов)». Дополнение к 71651ad0, вместо ручных рецептов восстановления.
5. **`blocked` с типом** (по kanban Гермеса): `dependency` (ждёт сама и продолжается), `needs_input` (оркестратору, владельцу только при условии ниже), `capability`, `transient`. Роль без вопроса к себе: «комментарий + блок с типом». Повторные блокировки одного вида поднимаются оркестратору.
6. **Срок жизни и быстрый отказ.** Сообщение роли с вопросом без ответа N минут возвращается отправителю со сроком «истёк»; адресат недоступен (нет исполнителя или запуска) — отказ сразу с причиной, а не письмо в пустоту.
7. **Инструкция ролей как протокол.** Список коллег с ролями в самой инструкции (не только `taskflow_agents`); одному подходящему адресату; «упёрся — блок с типом, не молчи»; пустое «принял»/«понял» заменяется токеном молчания `[SILENT]`, сервер такие сообщения в ленту не публикует (по образцу Гермеса `[SILENT]`/`NO_REPLY`).
8. **Шум уведомлений.** `agent_watch` («помечен рабочим, хотя задачу никто не держит» каждые 30 минут) заменяется типизированными событиями из пунктов 1–4; режим «кратко» по умолчанию.

9. **Исходящий вебхук** (добавлено 06.10 по просьбе владельца, в карточку MAK-99): типизированные события-исходы сервер отправляет POST-запросом на адрес из настроек (по умолчанию выключен), с токеном, повтором и дедупликацией. Приёмник у оркестратора — разовый фоновый процесс, завершающийся по первому событию; заменяет опрос сторожем `tf_watch.py`. Будит оркестратора только пока его сессия жива, поэтому первым получателем остаётся сервер.

## Решение владельца об эскалации (06.10.2026)
Владельцу писать только если отклонение кардинально меняет суть и результат задачи (то есть затрагивает «Результат», «Критерии приёмки», «Границы» карточки). Если «шаг влево, шаг вправо», а результат тот же — владельца не спрашивать. Но сюрпризов быть не должно: нюансы подсвечиваются и согласуются с оркестратором в рамках расписанного плана. Технически: тип `needs_input` с признаком «меняет результат» идёт владельцу в Telegram, остальное — оркестратору.
