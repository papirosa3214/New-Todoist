# Hermes Agent: связь и координация агентов по официальной документации (ресёрч 06.10.2026)

Источник: https://hermes-agent.nousresearch.com/docs/ и репозиторий https://github.com/NousResearch/hermes-agent (issues, PR). Собрал разведчик web-scout; внешний источник, проверку на инъекции не проходил (подозрительного не найдено).

**Оговорка о методе.** WebFetch у разведчика не работал (ошибка модели MiniMax-M2.7-highspeed), страницы не открывались. Все факты взяты из пересказов WebSearch по доменам сайта и github. Это не дословные цитаты; точные формулировки и числа с первоисточником не сверялись. Сверять перед тем как опираться.

## 1. Делегирование (`delegate_task`)
Страница: /docs/user-guide/features/delegation
- Вызов верхнего уровня идёт в фоне: сразу handle, результат приходит новым сообщением между ходами родителя. Родителю предписано завершить независимую работу и закончить ход, а не опрашивать.
- Пакет `tasks=[...]`: один handle, параллельно, итог одним сводным сообщением.
- Сбой ребёнка не тихий: нефатальная ошибка провайдера, таймаут, крэш, нет пригодного вывода. При таймауте с нулём вызовов API пишется диагностика `~/.hermes/logs/subagent-timeout-<session>-<timestamp>.log`.
- Монитор зависаний по прогрессу: 450 с простоя между ходами, 1200 с внутри инструмента. Ребёнок прерывается, родитель получает `status: "timeout"` с полями `stalled_after_quiet_seconds`, `stall_threshold_seconds`, `stall_phase`, `stall_grace_seconds` (PR #129941).
- Смерть процесса-владельца: делегация записывается как «unknown» (побочные эффекты не доказать); PR #116707 и #104373 возвращают реальные результаты завершённых детей.
- PR #117654: в событие восстановления добавлен хвост транскрипта (до 20 строк, 2000 символов) и снимок git владельца «branch @ sha subject (N uncommitted file(s))».
- Версии документации расходятся: страница delegation-patterns и ранняя версия описывают синхронную делегацию; лимит параллелизма то 10, то 3.
- Известные баги: #76605 (gateway молча теряет завершение фоновой делегации), #131578 (результат теряется при фоновом процессе с notify_on_complete), #48796 (жёсткое убийство по таймауту 600 с без частичного итога), #127918 (событие «owner-exited» при живом воркере).

## 2. Личка между агентами (Bot Mode, `message_agent`, peer)
Страница: /docs/user-guide/bot-mode. Релиз v0.21.0 (v2026.8.31), включён по умолчанию в десктопе.
- `message_agent(target="researcher", message="…")`; адресат: имя профиля, дружелюбное имя или @-тег; при совпадении имён вызов отклоняется со списком.
- Инструмент только в каноническом «Bot Chat» на установках под Bot Mode; в обычных чатах, группах, CLI и headless без десктопа его нет.
- Fire-and-forget подтверждено: отправитель получает подтверждение и заканчивает ход; уведомление о завершении фонового процесса несёт ответ либо сбой доставки и будит отправителя новым ходом.
- Peer: `hermes peer add|list|dm|run|status|stop|remove` (PR #88725), адреса вида `spark/researcher`.
- Срок жизни письма `bot_mode.envelope_ttl_seconds`, по умолчанию 900 с; просроченное отклоняется как `queued_expired`. Отправитель ждёт ответ до ~3120 с, затем `delivery_timeout` (issue #120250).
- Отдельного описания «быстрого отказа при офлайне» не найдено; есть код `runtime_offline`.
- Письма разным ботам доставляются параллельно (ответ на #111587).
- Баги доставки: сообщение «возможно, ещё будет доставлено» для просроченного (#120250, фикс #120251); поздний ответ после 300 с живого ожидания не доходит (#123034); причина терялась как `unknown` (#113532, фикс #114955); peer-доставка из непрофильных профилей падает (#93935).

## 3. Типизированные причины сбоев и повторы
- Закрытый список: `provider_auth_or_access`, `provider_quota_limit`, `provider_rate_limit`, `provider_server_error`, `context_overflow`, `missing_config`, `model_unavailable`, `runtime_offline`, `queued_expired`, `delivery_timeout`, `target_busy`, `unknown`.
- Шлюз цели классифицирует сбой, десктоп пересылает код, уведомление отправителю помечено `[reason: <code>]`; агент ветвится по коду.
- Повтор не более одного раза и только если помогает: офлайн, таймаут доставки, rate limit, ошибка сервера провайдера; `context_overflow` повторяется со сжатием транскрипта. Авторизация, квота, конфиг не повторяются. Повтор в той же сессии, у получателя ровно одна копия письма.
- Провайдеры: `agent/error_classifier.py` → `FailoverReason` (rate_limit, billing, auth, overloaded, server_error, timeout, model_entitlement).
- Пулы ключей: 429 — один повтор, затем ротация, кулдаун 1 час; 402 — сразу ротация, кулдаун 1 час; 401 — обновление OAuth, иначе ротация, кулдаун 5 мин.
- Резервные провайдеры: при 429 и 5xx после исчерпания повторов, при 401/403/404 сразу; не более одного раза за ход; кулдаун основного до времени сброса либо бэкофф 60 с…4 ч.
- Переполнение контекста: сжатие беседы, пересборка запроса, ограниченные доп. проходы.

## 4. Kanban и мультипрофильная работа
Страницы: /docs/user-guide/features/kanban, kanban-worker-lanes, kanban-tutorial.
- Диспетчер: цикл 60 с, видит `ready` и `running`; карточка с несуществующим исполнителем остаётся в `ready` с событием `skipped_nonspawnable`.
- Инструменты воркера: `kanban_complete` (итог и метаданные), `kanban_block` (причина: `dependency` ждёт сама, `needs_input`/`capability`/`transient` уходят человеку; повторные блокировки одного вида поднимаются в triage), `kanban_comment`, `kanban_heartbeat`.
- Воркеру нельзя `clarify` (headless, карточка молча висит в running): нужно `kanban_comment` + `kanban_block(reason=...)`.
- Тихие отказы ловятся: `crashed` (PID мёртв раньше срока аренды, хвост журнала в `last_failure_error`), `timed_out` (`max_runtime_seconds`, SIGTERM, через 5 с SIGKILL), аренда без heartbeat освобождается через 15 мин, если процесс мёртв; зависшая карточка забирается через 4 часа; лимит неудач `max_retries` → `kanban.failure_limit` → 2, затем `gave_up` и автоблокировка. Лимиты запросов сбоем не считаются.
- Передача: оркестратор через `kanban_create` с исполнителями и родителями (имена из `hermes profile list`); проверка `kanban_request_review` / `kanban_request_changes`.
- Слабые места: `consecutive_failures` не растёт, если воркер упал до первого heartbeat; dead-credential ловится только падением (#122703); общий список #35986.

## 5. Уведомление человека
- `terminal(background=true, notify_on_complete=true)` будит агента при выходе процесса; `watch_patterns` — при совпадении вывода, лимит 8 уведомлений за 10 с; `display.background_process_notifications`: concise (по умолчанию), all, result, error, off.
- Cron: вывод доставляется как итог; режим без агента: пустой stdout означает тихий тик (шаблон «сообщать только при неполадке»); `cron.delivery.notify` по умолчанию true.
- Approvals: `approvals.mode` (smart/manual/off), `timeout` 300 с; без ответа команда запрещается, просроченный запрос заново не открывается; inline-кнопки в Telegram/Discord/Slack, `/approve`, `/deny`; плагин ntfy-approval присылает push с кнопками.
- Баги: таймаут канала одобрения сообщается агенту как «User denied this command» (#130272); запрос оповещать, когда одобрение ждёт молча (#17934).

## 6. Наставления в системной инструкции
- Протокол Bot Mode: флаг `agent.bot_mode_protocol` (по умолчанию включён), ~916 байт стабильной секции промпта, только в сессиях «Bot Chat» (PR #87886); включает список команды (имена и роли из title/description профилей) и список peer.
- В групповых комнатах боты зовут друг друга через @имя, решения, требующие суждения, эскалируют через @user.
- Бот без реплики завершает ход токеном молчания `[SILENT]` / `NO_REPLY`; группа считается успокоившейся, когда целый раунд прошёл молча.
- Точный текст протокола не получен (логика в `tools/bot_mode_probe.py`).

## Сверка с локальным кодом на .110 (см. docs/2026-10-06-hermes-communication-study.md)
- Подтверждено: fire-and-forget с пробуждением новым ходом, причины с повтором по коду, срок письма 900 с, фоновая делегация с событием завершения, событие восстановления с хвостом журнала и снимком git.
- Не подтверждено: причина `agent_blocked` в документации не найдена (есть в локальном коде).
- Расхождения списка причин: на сайте есть `target_busy` и `provider_auth_or_access` и др.; `provider_quota_limit` не повторяется.
- «Быстрый отказ при офлайне» отдельно не описан.
