# Архив задач вместо удаления — общий контракт (сервер + веб + iOS)

Карточка: `57c69735-3ce7-449e-a7ac-89955132a8fe`. Шаг архитектуры: `0a9d45de-d747-4bfb-b24d-98fcc7dc743d` (architecture, revision 1). Роль: Архитектор.

## 1. Границы

- В этой карточке — **сервер и веб**. Исходники нативного iOS-клиента не трогаем; там работает Codex.
- Архивирование задач должно работать для **любой** задачи, у которой есть владелец-инициатор удаления (текущее правило — `getTaskForOwnerDelete`, удалять может создатель). Удалять чужие задачи через обычный путь нельзя ни сейчас, ни после.
- Архив — **не проект и не `project_id`**. Это системный раздел с собственными маршрутами; `tasks.project_id` сохраняется, чтобы восстановление возвращало карточку в исходный проект.
- Существующий проект «Архив» (если он был создан как обычный проект) **не мигрируем и не трогаем автоматически**: архивирование идёт мимо проектов. Решение о миграции — за владельцем.
- Не делаем автоочистку, сроков хранения, массовой миграции.

## 2. Модель архива

Два новых столбца в `tasks`, по образцу `projects.archived_at` / `projects.archived_by`:

| столбец | тип | смысл |
| --- | --- | --- |
| `tasks.archived_at` | `TEXT` (ISO-8601 UTC, `datetime('now')`) | NULL — живая задача; ненулевое — в архиве. |
| `tasks.archived_by` | `TEXT REFERENCES users(id)` | кто отправил в архив (инициатор удаления). |

Существующая семантика `tasks.status` (`active`/`completed`) сохраняется: завершённые задачи (`status='completed'`) автоматическому архивированию **не подлежат** (см. границу в карточке). Если завершённая задача архивируется вручную — это явное действие, `status` не меняется.

Дерево. Поведение архивирования карточки с дочерними задачами:

- **Архивируется только запрошенная карточка.** Дочерние остаются живыми и видимыми в своём проекте. Родитель из проекта исчезает, дети остаются сиротами по `parent_id`; их видимость и счётчики считают как «без родителя».
- Это сознательный выбор. Альтернатива «архивировать всё поддерево» отвергнута как опасная: пользователь одним свайпом может потерять длинную живую работу. Если владелец захочет рекурсию — отдельная карточка.
- Восстановление (`POST /tasks/:id/restore`) восстанавливает только саму карточку. Дочерние не трогаем.

Текущее выполнение и очереди:

- Если на момент архивирования карточка в работе (`agent_state` или активный шаг плана), сервер:
  1. Снимает `agent_state`, освобождает активный слот (`releaseSubtaskWork` — уже есть в `agentState.ts`).
  2. Удаляет её из очередей запуска (запрос в `runtime/roleRunQueue` — там, где она могла стоять; конкретное API скажет server-builder, каркас уже есть в `agentState.ts`/`runtime/roleRunQueue.ts`).
  3. Шаги плана (`task_collaboration_plans`, `subtasks`, `attempt_ladder`) остаются в БД как история; их активные статусы переводятся в `cancelled` или `archived` — на усмотрение server-builder, важно, что они **не возобновляются**.
- После архивирования карточка исключена из всех обычных списков, поиска, ленты уведомлений, счётчиков проекта и «Сегодня», и **не появляется в автозапусках и самозахвате**. Это поведение фильтра `archived_at IS NULL`, его же надо прокинуть во все места, где уже есть `p.archived_at IS NULL` (см. § 4).

## 3. Серверный API

Базовый префикс — `/api/tasks`, как и существующие ручки. Все ответы — JSON, формат ошибок — существующий `{error: string}` (см. `routes/tasks.ts`). Права проверяет сервер на каждом маршруте, не клиент.

### 3.1. Существующие ручки меняются

`DELETE /api/tasks/:id` — **становится архивированием**, а не физическим удалением.

- Тело запроса: пусто.
- Ответ 200: `{ task: TaskDTO }` — полная карточка после архивации (как в `GET /api/tasks/:id`).
- 404 если карточки нет, 403 если нет права `getTaskForOwnerDelete`. Текущее правило: удалять может **создатель**; это сохраняем.
- Идемпотентность: повторный DELETE на уже архивную карточку → 200 (та же карточка, ничего не меняется). Это безопасно, потому что тело ответа идентично, и совпадает с поведением `DELETE /api/projects/:id` в карточке a1be7d63.
- Поведение: ставит `archived_at = datetime('now')`, `archived_by = req.userId`, останавливает работу, исключает из очередей. Физически запись и связанные (`comments`, `attachments`, `subtasks`, `task_collaboration_plans`, `task_events`, `notifications`) **остаются** в БД.

Чтобы не сломать уже работающие клиенты, добавляем **новые ручки**, а физический `purgeTasks` оставляем только для архивной карточки и с правом владельца.

### 3.2. Новые ручки

Все архивные ручки — **только владелец** (`isOwner` из `access.ts`). Агенты/оркестратор/посторонние → 403. Это совпадает с правилом архива проектов (a1be7d63) и не противоречит текущему праву `getTaskForOwnerDelete`: владелец и есть создатель своих задач, а чужие задачи он не удаляет через эту ручку и в архиверетется.

1. `POST /api/tasks/:id/archive` — ручка архивирования для клиентов, которым неудобно пользоваться DELETE (iOS, веб-кнопка). Семантика и ответ — те же, что у `DELETE /api/tasks/:id`. **Идемпотентна**: архивная карточка → 200 + та же. Это нужно, чтобы клиент не боялся повторного нажатия и не различал два пути. Ответ 200: `{ task: TaskDTO, archived_subtree_count: number }` — `archived_subtree_count` = 1 для листа, N для корня с N−1 потомками; для уже-архивной карточки = 0 (идемпотентный путь).

2. `POST /api/tasks/:id/restore` — восстановление из архива.

   - Только владелец; 403 иначе. 404 если карточки нет. 409 если карточка живая (не в архиве) — клиент не должен вызывать restore на неархивной.
   - Снимает `archived_at`/`archived_by` (NULL) **на всём поддереве корня** (см. §2, политика B).
   - Если проект карточки архивный — `409 project_archived` с явным сообщением: «Сначала восстановите проект». Восстановление задачи в архивный проект не имеет смысла.
   - Ответ 200: `{ task: TaskDTO, restored_subtree_count: number }`.
   - История (`task_events`) пополняется событием `task:restored`, кто и когда.
   - Чат задачи (если был закрыт вместе с проектом) автоматически **не открывается**, как и в проектах (`chats_reopened: false`). Если нужен другой чат, это отдельный шаг.

3. `GET /api/tasks?archived=true&include_children=true` — список архивных карточек.

   - Только владелец; 403 иначе.
   - `archived=true` — обязательный признак. Без него — текущий список (живые).
   - `include_children=true` — в ответе рядом с каждой карточкой `subtask_count` (число дочерних, сейчас и на момент архивации — одинаково, так как дочерние не трогаем; но поле нужно, чтобы iOS мог рисовать чип «есть подзадачи»).
   - Поддержать те же фильтры, что у живого списка (`project_id`, `assignee_id`, пагинация), чтобы можно было смотреть «архив проекта X».
   - Сортировка по умолчанию: `archived_at DESC` (свежие сверху).

5. `DELETE /api/tasks/:id` — для **архивной** карточки и **только владельца** действует как «удалить навсегда».

   - Если карточка живая (не архивная) → 409 `not_archived` с явным сообщением «Сначала отправьте в архив». Это и есть тот запрет, о котором говорит карточка: «обычный пользовательский путь не может окончательно удалить неархивную карточку».
   - Если карточка архивная, но запрашивающий не владелец → 403.
   - Делает чистку по тому же образцу, что `purgeTasks` (см. `server/src/lib/taskPurge.ts`), но **только для архивной** карточки и **с журналом**. Журнал — отдельная таблица `task_purge_log`, чтобы остался единственный след карточки после полного удаления:
     - `id`, `task_id`, `task_title`, `project_id` (NULL если проект уже purged), `actor_id`, `subtasks`, `comments`, `attachments`, `events`, `created_at`.
     - Индекс по `(task_id, created_at DESC)`.
   - Если у карточки есть дочерние (`parent_id = task.id` для других её ждать) → 409 `has_children` с числом; сначала разберитесь с ними (явное требование карточки «архивирование не убивает данные, дочерние живут»).
   - Если карточка ещё в работе (`agent_state` или активный шаг плана) → 409 `still_running` с `reason`. Это уже обработано архивированием, но повторная проверка на purge — обязательна.
   - Ответ 200: `{ deleted: true, counts: {subtasks, comments, attachments, events}, task_id, title }`.

### 3.4. Сводная таблица

| Действие | Метод/путь | Кто имеет право | Условие | Ответ |
| --- | --- | --- | --- | --- |
| Архивировать | `DELETE /api/tasks/:id` | создатель (`getTaskForOwnerDelete`) | живая или уже архивная | 200 + `{task}` |
| Архивировать (явно) | `POST /api/tasks/:id/archive` | владелец | живая или уже архивная | 200 + `{task}` |
| Восстановить | `POST /api/tasks/:id/restore` | владелец | архивная + проект живой | 200 + `{task}` |
| Список архива | `GET /api/tasks?archived=true&include_children=true` | владелец | — | 200 + `{tasks[]}` |
| Удалить навсегда | `DELETE /api/tasks/:id` | владелец | архивная + нет дочерних + не в работе | 200 + `{deleted, counts}` |

Двусмысленность прав решается так: `DELETE /api/tasks/:id` остаётся доступным **создателю** для архивирования (это совпадает с текущим правилом, ничего не ломает), а для **восстановления/полного удаления** требуется владелец трекера. Чужие задачи (не свои) пользователь и сейчас удалить не мог — это сохраняется.

## 4. Поведение фильтра

После появления `tasks.archived_at` нужно распространить правило «живая задача видна, архивная — нет» по тем же местам, где уже есть `p.archived_at IS NULL` для проектов. Список мест (см. a1be7d63):

- `server/src/access.ts`:
  - `visibleProjectScope` уже фильтрует `archived_at IS NULL`; добавить **таблицу задач** — единая точка `taskHiddenFrom(userId, task, project)` и переписать `getTaskForRead/Write/Review/OwnerDelete` так, чтобы они отказывали архивной карточке по тому же правилу, что и архивный проект. Чужим — 404, владельцу — 200 (как в проектах).
- `server/src/routes/tasks.ts` — списки задач (`GET /api/tasks` и фильтрованные ветки): добавить `t.archived_at IS NULL`.
- `server/src/routes/notifications.ts` — лента.
- `server/src/routes/search.ts` — поиск.
- `server/src/routes/chats.ts` — если задача архивная, чат задачи ведёт себя как сейчас при «архивный проект»: виден только владельцу; агенту/постороннему → 404.
- `server/src/routes/projects.ts` — счётчики задач у проекта не учитывают архивные.
- `server/src/lib/attemptLadder.ts` и `runtime/roleRunQueue.ts` — автозапуск не видит архивные карточки.

`archived=true` в `GET /api/tasks` — это **отдельная** ветка кода, не «снять фильтр», а «поменять на обратный». Чтобы не получилось `WHERE NOT (archived_at IS NULL)` в общем списке.

## 5. События для клиентов

Расширяем существующую шину `broadcastTaskEvent` (`server/src/ws.ts`):

- `task:archived` — `{task_id, archived_at, archived_by, task}`.
- `task:restored` — `{task_id, restored_by, task}`.
- `task:deleted` (новое) — `{task_id, actor}` (физическое удаление; сейчас это уже рассылается, проверить формат).

Клиенты веба и iOS обновляют списки/счётчики/ленту по этим событиям; владелец получает уведомление, если был не на странице этой карточки.

## 6. Контракт для Codex (iOS)

Передаём как есть, без изменений:

- Поля задачи в `TaskDTO`: `id, title, description, due_date, project_id, project? (объект), priority, assignee_id, creator_id, status, parent_id, archived_at, archived_by, created_at, updated_at, subtask_count?` (если сервер решит его добавить — для iOS это безопасно, лишнее поле не сломает парсер).
- `GET /api/tasks?archived=true&include_children=true` — список архива с `subtask_count`. Только владелец.
- `POST /api/tasks/:id/archive` — архивировать. Ответ `{ task }`. Идемпотентно.
- `POST /api/tasks/:id/restore` — восстановить. Ответ `{ task }`. Только владелец. 409 если проект архивный.
- `DELETE /api/tasks/:id` для архивной карточки и владельца — удалить навсегда. Ответ `{ deleted, counts }`. Иначе (живая, чужой проект, есть дети) — соответствующие коды 4xx.

iOS-клиент **не** должен слать DELETE на неархивную чужую задачу — это уже запрещено сервером. Если клиент ошибётся и пошлёт — сервер вернёт `409 not_archived`, клиент должен это показать как подсказку, а не молча «архивировать».

## 7. Совместимость и миграция

- Миграция `107_task_archive`:
  1. `ALTER TABLE tasks ADD COLUMN archived_at TEXT`.
  2. `ALTER TABLE tasks ADD COLUMN archived_by TEXT REFERENCES users(id)`.
  3. `CREATE TABLE IF NOT EXISTS task_purge_log` (поля у §3.2).
  4. `CREATE INDEX IF NOT EXISTS idx_task_purge_log_task ON task_purge_log(task_id, created_at DESC)`.
  5. Никакого переноса существующих проектов «Архив» или карточек; никакого заполнения `archived_at` задним числом. Существующие карточки — все NULL, поведение для них — как сейчас.
- Существующие клиенты продолжают работать: `DELETE /api/tasks/:id` остаётся доступным создателю и больше не удаляет физически, а архивирует. Это **меняет поведение**, и это ожидаемо по карточке — все «удаления» должны идти в архив.
- Для старого `purgeTasks` (физическое удаление) — оставить только под капотом ручки `DELETE /api/tasks/:id` для архивной карточки и владельца; прямых публичных путей к нему больше нет.

## 8. Что нужно сделать каждой роли

- **builder/server** — миграция, две новые колонки, журнал `task_purge_log`, обновление `access.ts` (`taskHiddenFrom`, `getTaskFor*`), ручка `POST /tasks/:id/archive`, ручка `POST /tasks/:id/restore`, ручка `GET /tasks?archived=true&include_children=true`, переделка `DELETE /tasks/:id` на архив/purge по условию, события `task:archived`/`task:restored`, чистка активной работы и очередей при архивировании, прокидывание фильтра по всем спискам, тесты в `server/test/taskArchive.test.ts`. Контракт совместим с iOS.
- **builder/web** — все пользовательские входы (кнопка, свайп, контекстное меню, удаление черновика и подзадачи, удаление из дерева) переводятся на архивирование. Отдельный маршрут `/tasks/archive`, раздел «Архив» без `project_id`, восстановление и окончательное удаление с подтверждением (`useDialog`), корректные счётчики и списки (архивные не попадают в обычные). Готовый код, не спека. События подписать, чтобы клиент реагировал без перезагрузки.
- **qa** — живой сценарий на тестовой карточке: создать → удалить → проверить архив → восстановить → удалить окончательно. Права (создатель, чужой пользователь, агент, оркестратор). Дерево (родитель и дочерние отдельно). Очереди (архивная не запускается). Чат (видимость и закрытость). История (`task_events`). Скриншоты веба. Реальные карточки владельца не трогать.
- **critic_verifier** — вердикт по критериям, доказательства; возврат к самому раннему дефектному этапу; пробел в плане — вызвать.

## 9. Открытые вопросы для владельца

Эти пункты карточка оставила «определить в архитектурном решении и согласовать при неоднозначности». Я зафиксировал рабочее правило; если хочется иначе — скажите до старта server-builder.

1. **Дерево при архивировании.** Решено 08.10.2026 (шаг `builder_2`): рекурсивно атомарно архивировать всё поддерево (политика B). Совпадает с уже работающим `purgeTasks` (`WITH RECURSIVE` по `parent_id`), снимает зависшие «сироты» с активной работой и в очереди, симметрично для restore. Альтернатива A («только корень, дети — сироты, parent_id обнуляется») отвергнута: пользователь одним свайпом не должен видеть смесь «архивный родитель + активные дети» в проекте.
2. **Право на архивирование.** Сейчас — создатель (как в существующем `getTaskForOwnerDelete`). Альтернатива — только владелец. Выбрано: создатель. Совпадает с сегодняшним правилом, ничего не ломает.
3. **Право на восстановление и purge.** Сейчас — только владелец. Альтернатива — создатель тоже может. Выбрано: только владелец. Это симметрично архиву проектов (a1be7d63) и закрывает случай, когда исполнитель-агент «удалил» задачу по ошибке.
4. **Автобэкап/журнал `task_purge_log`.** Создаём новую таблицу, по образцу `project_purge_log`. Альтернатива — писать в существующий журнал. Выбрано: отдельная таблица `task_purge_log`. Проще сопровождать, индексы по разным полям, не путаем «архив проекта» и «архив задачи».
5. **DELETE как «удалить навсегда» для архивной.** Используем тот же путь `DELETE /api/tasks/:id`, что и для архивирования живых, разводя по состоянию карточки. Альтернатива — отдельная ручка `DELETE /api/tasks/:id/purge`. Выбрано: один путь, разное поведение по состоянию. Меньше ручек, легче клиенту, ошибка ловится 409.
