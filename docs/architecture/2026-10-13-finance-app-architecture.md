# Архитектура веб-приложения для учёта личных финансов

> Документ архитектуры по work_2 задачи `6cf6bd5e-d227-4c17-9af1-69cbc4372b15`.
> Ответственный: Архитектор. Основано на исследовании work_1 (обзор 10 коммерческих приложений, документ от 2026-10-13).

## Контекст и ограничения

- **Тип проекта**: персональный, локальный. Масштабирование под множество пользователей не преследуем — это значит, что можно держать SQLite, один сервис, простую аутентификацию.
- **Регион**: Россия/СНГ. Банковская интеграция должна учитывать, что у большинства российских банков нет публичных Open Banking API (PSD2-эквивалент отсутствует), а агрегаторы (Plaid, Salt Edge) для РФ покрыты слабо. Опыт Дзен-мани и CoinKeeper — это связка «логин в ЛК банка + SMS-парсинг как fallback», но для веб-приложения оба варианта ограничены.
- **Монетизация**: отсутствует. Из вывода work_1: модель «user as product» с рекламой — анти-паттерн (закрытие Mint, 23.03.2024, из-за подорожания Plaid). Поэтому в архитектуре нет рекламных модулей, нет внешних телеметрий и нет блокирующих зависимостей от внешних SaaS в бесплатной части.
- **MVP**: ручной ввод операций + импорт через выбранный провайдер/протокол + просмотр аналитики расходов и накоплений. Этого требует шаг work_3 (Разработчик). Дальнейшие этапы — в work_4 (roadmap).
- **Граница**: только веб. Никаких мобильных приложений на первом этапе (явное «не входит» в описании задачи).

## Принципы

- **Провайдер — абстракция**. Банковская интеграция идёт через единый интерфейс `BankProvider` (`fetchAccounts`, `fetchOperations`, `subscribe`); ниже — адаптеры. Это даёт замену провайдера без правок ядра (урок Wallet/Spendee, у которых Salt Edge ломает синхронизацию).
- **Ручной ввод — первый класс**. Все автоматические каналы — поверх, а не вместо ручного ввода. Любая операция может быть отредактирована, удалена, переклассифицирована.
- **Идемпотентность импорта**. Каждая импортированная операция имеет `external_id` от источника + `source`. Повторный импорт не создаёт дублей.
- **Локальность по умолчанию**. Данные владельца — на его сервере, не в облаке агрегатора. Агрегатор (если используется) — read-only.
- **Минимум внешних зависимостей**. Без блокирующих SaaS; всё, что можно заменить локальным эквивалентом, заменяемо.

## Выбор протокола/провайдера банков

Регион РФ делает однозначно лучший путь — гибрид: ручной ввод + файловый импорт (CSV/OFX/QFX/PDF-парсинг) как основа; агрегатор через API — опционально для банков вне РФ. Каждый источник за абстракцией `BankProvider`.

| Канал | Что даёт | Стоимость | Риск | Приоритет |
|---|---|---|---|---|
| Ручной ввод | Полный контроль, базовый сценарий | 0 | Ошибки ввода | P0 (MVP) |
| CSV/OFX/QFX импорт из ЛК банка | Импорт сотен операций за минуты | 0 | Разные форматы у банков | P0 (MVP) |
| Salt Edge | 5 000+ банков в 50+ странах, ISO 27001 | От $500/мес (growth plan) | Сбои sync 2024-25 по отзывам Wallet/Spendee; ограниченное покрытие РФ | P1 (опционально) |
| Enable Banking | PSD2 (EU/UK) | Pay-per-call | Не покрывает РФ | P1 (для счетов в ЕС) |
| Plaid | US/CA | Pay-per-link | Не покрывает РФ | P2 |
| PDF-выписка + OCR/парсинг | Для банков без CSV | 0 (Tesseract локально) | Качество распознавания | P2 |
| Email-парсинг (forward выписок на свой ящик) | Для банков, отправляющих выписки на email | 0 | Нужна настройка | P2 |
| SMS-парсинг | Для РФ — то, что делают Дзен-мани/CoinKeeper | 0 | Ограничено Android/iOS, политика банков | Не в MVP (на бумаге — браузер не имеет доступа к SMS) |

**Выбор для MVP (work_3)**:

1. **Ручной ввод** — обязательно, без него MVP не сдать.
2. **Файловый импорт** (CSV/OFX) — обязательно как минимальная автоматизация. Парсеры для топ-форматов (CSV 1СClientBankExchange, CSV Сбербанк; OFX; QFX) идут из коробки; новые форматы добавляются через парсер по образцу.
4. **Агрегатор через API — отложить** (после MVP). Интерфейс `BankProvider` проектируется так, чтобы Salt Edge/Enable Banking/Plaid добавлялись как новый адаптер без правок UI/БД.

**Контракт `BankProvider`** (TypeScript-style псевдокод для следующего шага):

```ts
interface BankProvider {
  id: string;                       // "saltedge", "enablebanking", "csv", "pdf", "manual"
  displayName: string;
  capabilities: Capability[];       // ["accounts:read","operations:read","sync"]
  listAccounts(connection: Connection): Promise<Account[]>;
  listOperations(connection: Connection, since: Date, until: Date): Promise<RawOperation[]>;
  // subscribe — опционально (webhook/поллинг); MVP использует pull-only
}
```

Все `RawOperation` содержат `externalId` и `source`; дедупликация — на стороне ядра по `(account_id, external_id, source)`.

## Стек

**Замечание о решении по стеку**: задача говорит «решение по стеку зафиксировано владельцем», но в доступной истории чатов и базе знаний явная фиксация (конкретный фреймворк, БД, рантайм) не найдена. Поэтому ниже — обоснованное предложение, которое владелец подтверждает или меняет одним сообщением в чат задачи. Если уже есть иное решение — оно приоритетнее, и документ обновится в этом разделе.

**Предлагаемый стек (MVP)**:

- **Фронтенд**: Next.js 15 (App Router) + TypeScript + React 18. Один проект — UI и backend, минимум движущихся деталей, простой деплой, server components для дашборда аналитики.
- **Стили**: Tailwind CSS + shadcn/ui (готовые компоненты без блокирующей зависимости; копируются в репозиторий).
- **Backend**: Next.js API routes + Server Actions. Тот же процесс — Node.js 20 LTS.
- **БД**: SQLite через `better-sqlite3` (или Postgres через `pg`, если выбран Docker). Для персонального проекта SQLite — нормальный выбор: одна БД-файл, миграции через Drizzle или Prisma, бэкап — `cp`. Если владелец предпочитает Postgres — заменяется без правок доменной логики.
- **ORM/миграции**: Drizzle ORM (легче, чем Prisma, лучше для SQLite, миграции в виде SQL).
- **Аутентификация**: локальный аккаунт владельца, пароль + TOTP (опционально). Без OAuth/SaaS. Библиотека — `lucia-auth` или собственная реализация на сессионной куке с хэшем пароля (`argon2`).
- **Графики**: Recharts (компонентный, простой, без отдельного рендерера). Альтернатива — visx, если нужны свечные графики для активов.
- **Файловый импорт**: парсеры на чистом TypeScript (CSV через `papaparse`, OFX — кастомный мини-парсер).
- **PDF-OCR (P2)**: Tesseract.js (локально) + `pdfjs-dist` для извлечения текста.
- **Тесты**: Vitest + Playwright (e2e ключевых сценариев).
- **Линт/формат**: ESLint, Prettier.
- **Деплой**: один Docker-контейнер (Next.js standalone + SQLite-файл через volume). Альтернатива — запуск на домашнем сервере владельца без Docker через `pm2`.

**Почему так, а не иначе**:

- Next.js вместо отдельного React SPA + Express: один репозиторий, одна модель данных, нет CORS-сложностей, server-side агрегации для аналитики без перерасходов на клиенте.
- SQLite вместо Postgres на старте: для одного владельца PostgreSQL — избыточная операционная стоимость (бэкапы, апгрейды). SQLite работает с тем же SQL, миграция на Postgres возможна в будущем.
- Drizzle вместо Prisma: меньше магии, прозрачные SQL-миграции, лёгкий старт.
- Без агрегатора в MVP: исследования показали риск сбоев провайдера (Salt Edge) и высокую стоимость (Plaid). Ручной + файловый импорт закрывает 80% пользы бесплатно.

**Альтернативы, осознанно отвергнутые**:

- Vue/Nuxt: владелец не назвал предпочтение; Next.js крупнее сообщество для финансовых приложений, но решение за владельцем.
- Svelte/SvelteKit: отличная альтернатива, но меньше примеров банковской аналитики.
- React + Vite + отдельный Node.js backend: больше деталей, та же функциональность. Имеет смысл, если владелец предпочитает «классический» фронт/бэк-сплит.
- Postgres + Prisma: требуется, если планируется несколько инсталляций или рост.

## Структура аналитики

Аналитика — производное от операций. Не дублируем данные, считаем на лету для небольших объёмов (один владелец — десятки тысяч операций за годы), материализуем только месячные/годовые «снимки» для быстрого дашборда.

**Витрины (read-модели) для UI**:

1. **Текущий баланс по счетам** — сумма операций по каждому счёту + начальный баланс. Индекс по `(account_id, date)`.
2. **Расходы по категориям за период** — группировка операций с отрицательной суммой по `category_id`. Период: день/неделя/месяц/год/произвольный.
3. **Доходы по категориям за период** — то же для положительных сумм.
4. **Топ-контрагенты** — группировка по `merchant` за период (для понимания, на что уходят деньги).
5. **Накопления во времени** — net worth (по счетам), ежемесячный снимок; график «линия».
6. **Кэш-флоу** — доходы − расходы помесячно; столбчатая диаграмма.
7. **Категория-тренд** — изменение доли категории от месяца к месяцу (тренд).
8. **Сравнение периодов** — текущий месяц vs прошлый, текущий год vs прошлый.

**Дашборд (главный экран аналитики)**:

- Сетка карточек, каждая — отдельный компонент:
  - Текущий баланс по счетам (список)
  - Расходы за месяц по категориям (круговая + топ-5)
  - Кэш-флоу помесячно (столбчатая за 12 мес.)
  - Топ-контрагенты за месяц (список)
  - Net worth помесячно (линия за 12 мес.)
- Каждая карточка — отдельный `fetch` (Server Action), не блокирует общий рендер.
- Период — общий селектор (неделя/месяц/квартал/год/произвольный); сохраняется в URL.

**Отчёты (страницы, не карточки)**:

- Отчёт за месяц: доход/расход/баланс/топ категории/топ контрагенты/сравнение с прошлым месяцем.
- Отчёт за год: помесячный кэш-флоу + категории за год.
- Список операций с фильтрами (период, счёт, категория, тег, контрагент, поиск по описанию).

**Бюджеты (P1, после MVP)**:

- Лимит по категории на период (месяц/неделя).
- Прогресс-бар «потрачено / лимит» в карточке категории.

## Схема данных (Drizzle-style псевдокод)

```ts
// Все идентификаторы — ULID, не auto-increment (порядок и читаемость).
accounts: {
  id: string PK
  name: string
  type: "cash" | "card" | "deposit" | "investment" | "other"
  currency: string                 // ISO 4217
  opening_balance: decimal
  opening_date: date
  archived: boolean
  provider_id: string?             // FK → providers.id (если подключён агрегатор)
  external_id: string?             // ID счёта у провайдера
  created_at: timestamp
}

operations: {
  id: string PK
  account_id: string FK            // accounts.id
  date: date
  amount: decimal                  // signed; расход < 0, доход > 0
  currency: string
  description: string
  merchant: string?                // нормализованное имя
  category_id: string? FK          // categories.id
  source: "manual" | "csv" | "ofx" | "saltedge" | "enablebanking" | ...
  external_id: string?             // ID операции у источника
  imported_at: timestamp
  created_at: timestamp
  updated_at: timestamp
  // Уникальность импорта: (account_id, source, external_id)
}

categories: {
  id: string PK
  parent_id: string? FK            // иерархия (max 2 уровня)
  name: string
  icon: string?                    // эмодзи или ключ иконки
  archived: boolean
}

tags: {
  id: string PK
  name: string
  color: string?
}

operation_tags: {
  operation_id: string FK
  tag_id: string FK
  PK (operation_id, tag_id)
}

provider_connections: {
  id: string PK
  provider_id: string FK           // "saltedge", "enablebanking", ...
  account_id: string? FK           // счёт, к которому привязано подключение
  status: "active" | "expired" | "revoked" | "error"
  config_json: string              // токены, refresh — шифруются на уровне приложения
  last_sync_at: timestamp?
  last_error: string?
}

balance_snapshots: {               // материализованный net worth
  id: string PK
  account_id: string FK
  date: date
  amount: decimal
  // PK (account_id, date)
}
```

**Индексы**:

- `operations(account_id, date DESC)` — список операций по счёту.
- `operations(category_id, date DESC)` — аналитика по категориям.
- `operations(date DESC)` — общий отчёт за период.
- `operations(source, external_id)` — дедупликация при импорте.
- `balance_snapshots(account_id, date DESC)` — дашборд net worth.

**Идемпотентность импорта**:

- Перед вставкой — `SELECT` по `(account_id, source, external_id)`. Если найдено — обновляем поля, которые могут измениться (баланс, статус), но не трогаем пользовательские (category_id, tags).
- Если `external_id` отсутствует (ручной ввод, файлы без ID) — генерируем детерминированный `external_id = hash(source, account_id, date, amount, description)`. Это даёт защиту от дублей при повторном импорте того же CSV.

## Контракты API

Все эндпоинты — Next.js API routes; UI общается через Server Actions, где возможно.

- `POST /api/operations` — создание операции (ручной ввод).
- `PATCH /api/operations/:id` — редактирование.
- `DELETE /api/operations/:id` — удаление.
- `GET /api/operations?account=…&from=…&to=…&category=…` — список с фильтрами.
- `POST /api/imports/csv` — multipart: файл + счёт + маппинг колонок (если первый раз).
- `POST /api/imports/ofx` — то же для OFX/QFX.
- `POST /api/providers/:id/connect` — старт OAuth/логин flow (Salt Edge, Enable Banking).
- `POST /api/providers/:id/sync` — pull операций с провайдера.
- `GET /api/analytics/dashboard?period=…` — данные для дашборда.
- `GET /api/analytics/categories?period=…` — расходы по категориям.
- `GET /api/analytics/networth?from=…&to=…` — net worth по дням/месяцам.

**Контракты ответов** — JSON с явными полями. Ошибки — `{error: {code, message, details?}}` с HTTP-кодом. Никаких частично-заполненных ответов.

## Отказные сценарии

- **Провайдер не отвечает** — UI показывает «Последняя синхронизация: N дней назад», кнопка «Sync now». Не блокирует работу с уже импортированными данными.
- **Файл импорта повреждён** — парсер показывает, какие строки не распознаны (с предпросмотром), пользователь решает — пропустить, поправить или отменить.
- **Дубль при импорте** — операция не создаётся, пользователю отчёт «X операций уже были, Y новых, Z пропущено».
- **Нет сети на клиенте** — UI блокируется корректно; локальные изменения (draft) сохраняются в `localStorage`.
- **БД недоступна** — UI показывает страницу ошибки с предложением проверить БД; запись не теряется, форма не закрывается.
- **Сбой сессии** — следующий запрос возвращает 401, UI перенаправляет на логин с возвратом на исходную страницу.
- **Кража токена провайдера** — соединение отзывается; пользователь переподключает.

## Наблюдаемость

- Структурный лог сервера (`pino`), все запросы и ошибки.
- Аудит-таблица `audit_log`: кто/что/когда менял (для отладки дублей и спорных операций).
- Метрики времени ответа эндпоинтов — экспорт в `/metrics` (P2).

## Безопасность

- Пароли — argon2id.
- Сессии — случайный 32-байтный токен, хранится в HTTP-only куке.
- Токены провайдеров (`provider_connections.config_json`) — шифруются ключом из env (`BANK_KEY`); ключ не коммитится.
- CSP включена; никаких внешних скриптов кроме своих.
- CSV-импорт — парсер не исполняет формулы (`=cmd|…`); проверка полей.
- Загружаемые PDF — без исполнения JS (рендер в iframe sandbox).

## Компромиссы и открытые вопросы

- **Без агрегатора в MVP**: ограничивает удобство, но убирает риск зависимости от внешнего SaaS и его цены. Цена — больше ручного ввода. Это сознательный выбор по уроку Mint.
- **SQLite вместо Postgres**: держит сложность деплоя низкой; цена — ограничение на 1 писателя. Для персонального использования это не проблема. Если понадобится Postgres — миграция на Drizzle проста.
- **Без TOTP/2FA на старте**: MVP с паролем; TOTP добавляется в roadmap.
- **Без мобильного приложения**: задача это явно исключает.
- **Открытый вопрос к владельцу**:
  1. Стек — подтвердить Next.js+TS+SQLite+Drizzle или назвать другой.
  2. Регион — точно РФ, или планируются счета в ЕС/US? (от этого зависит, включать ли Salt Edge / Enable Banking в MVP.)
  3. Аутентификация — один владелец или несколько пользователей на одном инстансе? (от этого — один логин или полноценная система пользователей.)
