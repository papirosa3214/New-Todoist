### Что должно работать

- `GET /api/notes/:id` увеличивает `access_count` и пишет строку в
  `note_accesses` с автором обращения
- поломка учёта **не должна** ронять чтение заметки — обёрнуто в `try`
- служебные заметки пробы убираются и в конце проверки, и при старте

## 3. Порог разбора заметок

| | |
| --- | --- |
| **Что смотрит** | Сколько заметок ждёт разбора (`kb_temp_category` проставлен, `kb_category` пуст) |
| **Зачем** | Разбор базы знаний нельзя гонять по календарю: работа впустую вредна. И нельзя пропустить: неразобранные заметки не попадают в базу и в срез роли |
| **Где код** | `server/src/lib/kbTriageWatcher.ts`, подключён в `server/src/index.ts` |
| **Как проверяет** | По счётчику, а не «структура на месте»: набралось 20 заметок с временной меткой — пора |
| **Как часто** | При старте сервера и раз в 30 минут |
| **При срабатывании** | Задача **Секретарю** в основной проект — разбор рутина, не поломка. В «Серверные уведомления» летят только сбои приборов |
| **Тесты** | `server/test/kbTriageWatch.test.ts` (4) |
| **Добавлен** | 10.10.2026 |

### Что должно работать

- Ниже порога — молчит. Выше порога — задача с инструкцией: что делать,
  какие категории, чего не делать
- Порог проверяется **внутри** `raise()`, а не в вызывающем коде: иначе любой
  путь мимо таймера завёл бы задачу на пять заметок
- Не чаще одной задачи в сутки
- Если проекта разбора нет — молчит, а не сыпет задачи в хаб

### Связанное

Секретарь при разборе **не удаляет** ничего: мусор помечается и остаётся
видимым. Окончательное решение принимается по факту обращений ролей —
см. сторожа №1.

## Как добавить сторожа

1. Создать сторожа рядом с прибором, в той же задаче.
2. Проверка — **пробным ходом**, не «структура есть».
3. Тревога — задачей в «Серверные уведомления», не чаще раза в сутки.
4. Запись сюда: что, зачем, где код, как должно работать, что было.
5. Тест на живой схеме: «сторож молчит, когда всё хорошо» — обязателен.
   Сторож, который молчит всегда, хуже отсутствия сторожа.
