# История сдачи задач: проба падала с «no such column: OLD.id» (карточка 2e1e0988)

Дата: 30.10.2026. Роль: Инженер .110. Ветка: `roles/2e1e0988-d792-4512-9772-e2f626d71d88`.

## Что было

Сторож «Durable review history» (`server/src/lib/reviewHistory.ts`) каждые 15 минут
проверяет: записать карточку, сдать её на проверку, повторить событие, удалить
событие и карточку — и убедиться, что в реестре `task_review_history` остался
ровно один факт. Проба падала с `no such column: OLD.id`, и сервер завёл
служебную карточку починки (инцидент `review-history-alert`, id 2e1e0988).

## Причина

Ошибку давал не сам реестр истории, а триггеры журнала изменений задач
(`server/src/lib/taskChanges.ts`).

25.10.2026 в 22:06:11 выкладка (`deploy-when-idle.py`) поставила сборку
`d96358f9` — «дельты задач GET /api/tasks/changes». В ней условие «колонка
изменилась» (`NEW."col" IS NOT OLD."col"`) стояло и на INSERT-триггерах, где
строки OLD не существует. SQLite отвергает такую ссылку — любая вставка в
`task_events` (а это лента карточек) падала с `no such column: OLD.id`.
Проба истории вставляет событие — она падала на этом же шаге.

Карточка инцидента создана в 22:06:26 MSK (в БД: `2026-10-25 19:06:26` UTC) —
через несколько секунд после выкладки. В 22:39 выложена сборка `947bc389`, в
которую вошёл фикс `030b9f18` («условие только на UPDATE, пересоздание вместо
IF NOT EXISTS»): триггеры пересоздались, поломка ушла. **Карточку инцидента
никто не закрыл** — она висела пять дней (25.10 → 30.10), пока владелец не
взял её в работу.

Почему «старый» триггер вообще мог выжить в базе: `CREATE TRIGGER IF NOT
EXISTS` не заменяет уже лежащее определение — новое правило появилось только
в коде.

## Что сделано

1. `server/src/lib/reviewHistory.ts`
   - Триггеры `review_history_*` теперь **пересоздаются** (`DROP TRIGGER IF
     EXISTS` + `CREATE`), а не «создаются, если нет». Старое определение,
     пережившее правку кода, больше не может остаться в базе.
   - `checkReviewHistory()` называет **шаг**, на котором сломалось: тревога
     приходит с текстом «шаг «повторная запись события»: no such column:
     OLD.id» — по нему видно, что чинить, без догадок.
   - Сторож **лечит сам**: если проба не прошла, оба набора триггеров (свои и
     журнала изменений) переустанавливаются и проба повторяется. Частая
     поломка проходит без тревоги и без ожидания выкладки.
   - Сторож **пишет результат каждой пробы в журнал сервера**
     (`[review-history] проба записи и удаления проходит`) — видно, что он
     жив, даже когда тревоги нет.
   - Когда поломка ушла, а карточка инцидента ещё открыта, в неё пишется
     событие `review_history_recovered`: «проба снова проходит — карточку можно
     закрыть». Раньше такие карточки висели незакрытыми.
2. `server/src/lib/taskChanges.ts` — добавлена `reinstallTaskChangesLedger()`:
   обычная `ensureTaskChangesLedger()` работает один раз за процесс, для
   самолечения нужна явная переустановка.
3. `server/test/reviewHistory.test.ts` — четыре новых теста (переустановка
   триггера, название шага сбоя, поломка триггером журнала и её лечение,
   событие восстановления в карточке инцидента).

## Проверки

- `npx vitest run test/reviewHistory.test.ts` — 9/9 зелёные.
- `npx tsc -p tsconfig.json --noEmit` — чисто.
- Проба на снимке живой БД (`server/backups/pre-deploy-20261030-1433.db`,
  снят перед выкладкой 14:34) — `{"ok":true}`; реестр: 377 фактов на 377
  карточек, дублей нет.
- Тот же снимок со сломанными триггерами сборки `d96358f9` (как 25.10):
  проба → `шаг «повторная запись события»: no such column: OLD.id`; после
  `repairReviewHistoryTriggers()` → `{"ok":true}`.

  владельцу машины, группа и права не пускают. Проверка велась на снимках,
  которые снимает сама выкладка и ночной бэкап.
- Живой сервер не перезапускался: выкладка идёт по правилам репозитория, в
  шаге интеграции.
