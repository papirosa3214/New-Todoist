# Как заполнять задачи в Linear (стандарт для всех, кто их заводит)

Решение владельца 06.10.2026: все заводят задачи в Linear одинаково, владелец потом импортирует их в TaskFlow одним импортом (`lib/linearImport.ts`). Ниже — что именно импорт читает, поэтому заполнять надо так.

## Что импорт берёт из задачи Linear

| Поле Linear | Куда попадает в TaskFlow | Как заполнять |
| --- | --- | --- |
| Название | название карточки (обрезаются пробелы) | Суть проблемы или результата одной строкой. Не ярлык, не «доделать». Без номера в начале, без Markdown-экранирования (`\-`, `\(`), без ссылок. |
| Описание | описание карточки как есть (Markdown) | Четыре раздела строго по порядку, см. ниже. |
| Приоритет | приоритет 1–4; «без приоритета» станет 4 | Ставить осознанно: 1 срочный, 2 высокий, 3 средний, 4 низкий. |
| Срок | срок | Только если срок реальный. |
| Статус | «выполнена» только если Done; всё остальное, включая Canceled, станет активной карточкой | Отменённые задачи в импортируемом проекте не держать (иначе оживут как активные). |
| Родитель (подзадача) | дочерняя карточка, глубина любая | Подзадача — только если у куска работы свой самостоятельный результат. Шаги исполнения (сделать, проверить, принять) подзадачами не оформлять: это слоты ролей, их создаёт план. |
| Связь «блокирует» (и обратная «заблокирована») | зависимость «после завершения» | Ставить сразу. Порядок работы задаёт граф. Связи «связано» и «дубликат» зависимостями не становятся. |
| Метки | метки | Из общего набора, новых не плодить. |
| Комментарии, история, документы | переносятся комментариями в карточку | Решения и контекст — комментарием, а не в описании. |
| Вложения | ссылки на оригиналы | Файлы не скачиваются. |
| **Не переносятся** | веха, исполнитель, оценка, цикл | Веха — этап проекта, живёт только в Linear. Исполнитель в Linear ни на что не влияет. |

## Описание — четыре раздела, всегда в таком порядке

```
## Работа
Что сделать и исходный контекст.

## Результат
Что должно получиться: документ, изменение, проверяемый эффект.

## Критерии приёмки
Как проверить. Сборка или HTTP 200 сами по себе приёмкой не считаются.

## Границы
Что входит, что исключено, ограничения владельца. Не названы — «Дополнительные ограничения не указаны».
```

Условия владельца сохранять дословно. Сроки, исполнителей и материалы не выдумывать. Не хватает сведений — спросить, а не подставлять догадку.

## Проект и вехи

1. Проект называется по итогу работы. Метка «Сейчас» — делаем сейчас; «Задумка на будущее» — только записано.
2. В проекте 3–4 вехи, пронумерованные («1. Основа», «2. Компоненты», «3. Приёмка»). Каждая задача привязана к вехе.
3. Задачи с вехой и связями заводятся до импорта, а не после: импорт видит связи только между теми задачами, которые выбраны вместе.

## Перед импортом проверить

- У всех задач проекта есть четыре раздела описания и осознанный приоритет.
- Связи «блокирует» расставлены; цикла нет (импорт откажется на цикле родителей).
- Отменённых задач в выборке нет.
- Названия без номеров и экранирования.
