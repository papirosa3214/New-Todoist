# Диагностика провайдеров и моделей — 28.10.2026

## Результат

Общий ModelRuntime теперь пишет структурированные записи с префиксом
`[provider-diagnostics]` в stderr живого сервера (server/dev-server.log).
Источник ошибки фиксируется до преобразования SDK в короткое сообщение.
Настройки повторов, выбор модели и правила блокировки ролей не изменены.

Покрыты внутренние роли на карточках, чаты, обсуждения, разговорные ходы
слотов и служебные complete/completeSimple через общий runtime.

## Что сохраняется

- Время UTC, версия формата, провайдер, модель, API, endpoint без query и
  credentials, транспорт, настроенные таймауты и повторы.
- session_id, роль, run_id, task_id/subtask_id либо chat_id/message_id,
  discussion_id — где эти данные есть.
- call_id объединяет один вызов модели; request_id и attempt выделяют каждую
  сетевую попытку. Повтор на уровне сессии отдельно виден как auto_retry_start/end.
- Время до заголовков и первого блока, длительность попытки, полученные байты,
  HTTP-статус, request ID провайдера, retry-after/retry-after-ms.
- Исходные name/message/code/errno/syscall/hostname/address/port/status,
  ограниченный stack, вложенные cause и AggregateError.errors.
- Ошибки DNS, TLS, соединения, сброс сокета, таймаут, отмена, неуспех HTTP,
  ошибки внутри SSE, исходный stop_reason, отказ модели, лимит вывода,
  пустой ответ, итог SDK.
- Текст/тип/код JSON-ошибки API из отдельной копии ответа: не более 16 KiB
  чтения и 1 секунды. Полное тело ответа не записывается.
- События SDK о сбое WebSocket и fallback на SSE; только разрешённые
  диагностические поля.
- Размер сформированного запроса, число сообщений/инструментов, токены
  ответа; без содержимого промптов, ответов и аргументов инструментов.

## Транспорт и ограничения

Для адаптеров с поддержкой custom fetch сохраняется исходная ошибка fetch
и чтения тела. Исходный объект ошибки передаётся SDK без изменения.
Поток остаётся потоковым; тело успешного ответа целиком не буферизуется.

Google Generative AI/Vertex запрещают custom fetch: их транспорт сохраняется,
а ошибки Node HTTP/undici наблюдаются через diagnostics_channel и
AsyncLocalStorage. Так же наблюдаются запросы обновления OAuth.
Обёрнутый fetch исключён из этого наблюдения, чтобы попытки не считались дважды.

Данные WebSocket берутся из диагностических событий SDK и доступных каналов
Node. Если SDK или транспорт не предоставил исходный низкоуровневый факт,
журнал сохраняет доступный итог; не выдумывает HTTP-статус или сетевую причину.
Неизвестная причина остаётся unknown/sdk_error, а не объявляется аварией провайдера.

Внешние CLI-процессы и отдельный голосовой Python worker не используют
ModelRuntime; их внутренний транспорт этой правкой не перехватывается.

Известные ключи из request headers/apiKey и стандартные формы секретов
маскируются; query URL, arbitrary headers, cookies, тела запросов и произвольные
поля ошибок не записываются. Метаданные сессий ограничены 4096 записями.
Ошибка самого логгера не влияет на модель.

## Как читать журнал

1. Найти `[provider-diagnostics]` и task_id/chat_id либо session_id.
2. По call_id собрать вызов модели; request_id разделяет сетевые попытки.
3. `transport_error` показывает фазу request/response_body и исходную cause.
4. `http_error` + `http_error_detail` показывают отказ API, статус и код.
5. `provider_stream_error` / `provider_stop` — ошибка внутри потока или
   причина остановки, ещё до преобразования SDK.
6. `model_result` — окончательный итог; `sdk_diagnostic` — доступные
   сведения SDK о транспорте. События auto_retry_* показывают решение о повторе.
7. `native_*` — наблюдение штатного транспорта без custom fetch.

39 секунд всего хода и usage.calls не используются как время и количество
сетевых попыток. Для этого теперь существуют отдельные поля.
