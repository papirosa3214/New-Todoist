# Отметки пунктов checklist-виджета: приём на сервере и чтение ролью

**Карточка:** 21842242-9add-4628-8535-1ae3458fef40 · **Шаг:** widget_state (builder) · **Дата:** 2026-10-19
**Миграция:** `156_chat_checklist_items`

До 19.10.2026 состояние пунктов checklist-виджета жило только в клиенте: роль
не видела ни отметки в ленте `taskflow_chat_read`, ни отдельной операции
чтения. Теперь отметка — полноценная серверная сущность, устроенная как
реакция на сообщение: клиент её шлёт, сервер хранит и отдаёт роли и клиенту.

## 2. Контракт для клиента (iOS, мак)

Отметка пункта — один POST, как у реакции:

```
POST /api/chats/{chatId}/messages/{messageId}/checklist
Authorization: Bearer <токен владельца>
{ "widget_key": "0", "item_key": "pay", "done": true }
```

| Поле | Что это | Если нет |
|---|---|---|
| `widget_key` | `id`/`key` блока виджета, иначе его номер в сообщении строкой | `"0"` — первый блок |
| `item_key` | `key`/`id` пункта, иначе его номер строкой; можно прислать `item_index` | 400 «нужен item_key или item_index» |
| `done` | `true` / `false` — снятие отметки тоже честная запись | 400 «нужно done: true или false» |

Ответ: `{ "checklist_state": [{widget_key, item_key, done}], "message": {...} }` —
состояние всего сообщения и готовое сообщение для отрисовки.

Отказы, которые клиенту важно различать:

- **404 «Чат не найден»** — отправитель не участник чата;
- **404 «Сообщение не найдено»** — сообщение из другого чата;
- **400 «В сообщении нет checklist-виджета …» / «… нет пункта …»** — блок в
  сообщении переписан или не checklist; отметка не записана, клиент должен
  перечитать сообщение, а не молча считать успех.

Что видит клиент при чтении ленты: у каждого сообщения `checklist_state` —
список `{widget_key, item_key, done}`; пустой массив означает «отметок не
было». Подписи пунктов клиент берёт из самого блока виджета — дублет их в
состоянии нет.

## 3. Контракт для роли

Операция чтения (объявлена чтением: `request_id` не нужен, доступна всем ролям,
кроме тех, кому закрыт `taskflow_chat_read`):

```
taskflow_checklist_state
  chat_id   — переписка; без него берётся текущий чат хода
  only_done — только отмеченные пункты
→ { отмечено, всего, сообщения: [{message_id, task_id, widgets: [{widget_key, title, items: [{item_key, label, done}]}]}] }
```

`label` — подпись пункта, по ней Помощник владельца сопоставляет пункт со
своим делом в Things 3. Пустой чат даёт не ошибку, а понятную подсказку.

## 4. Границы и решения

1. **Ключи — из самого виджета.** `id`/`key` блока и `key`/`id` пункта, иначе
   номер строкой. Клиенту не нужно ничего изобретать: у него уже разобран
   блок. Состояние хранится под настоящим `widget_key`, даже если клиент
   прислал номер.
2. **Пункт проверяется по тексту сообщения.** Отметка несуществующего пункта
   не пишется: иначе в базе копился бы мусор из устаревших блоков.
3. **Разбор общий с нормализатором виджетов** (`canonicalizeWidget`), поэтому
   отметка находится и в каноническом блоке, и в старом формате Помощника
   владельца (`checklists` / `checked`), и в композитном блоке.
4. **Виджет из сообщения переписан, отметка остаётся.** Такое состояние
   показывается с подписью-ключом, а не молча пропадает.
5. **Ограничения по размеру:** не больше 50 сообщений и 50 пунктов в
   ответе роли — чтобы один длинный чат не съел контекст.
6. **Нативный клиент отметку пока не шлёт.** Маршрут и контракт готовы;
   правка `ChatWidgetView.swift` — отдельная работа на маке.
