## Обоснованные оптимизации

Полнота recovery достигнута выборкой только трёх идентификаторов вместо полной строки с payload. Webhook остаётся ограниченным страницей 200, а поиск совместимости ограничен диапазоном одного event id для использования существующего индекса. Новый формат ключа убирает ненужные повторные доставки. Миграций, новых таймеров, метрик и произвольного рефакторинга нет. Замеры производительности production не проводились.

## Оставшиеся риски и следующий охват

1. Гарантия exactly-once внешней операции не достигается одной серверной очередью: crash между побочным эффектом и durable подтверждением требует идемпотентности получателя. Двойная рассылка исправлена; потери сети и host-side dedupe полностью не исследованы.
2. Результаты из разных сокетов одной и той же зарегистрированной машины по-прежнему доверены машине как одному principal. Отдельная привязка op к сокету не вводилась.
3. Recovery последователен; один долгий вызов задерживает последующие. Снимок всех pending требует O(N) памяти по коротким идентификаторам. Ошибочная запись остаётся для диагностики; автоматическое исправление payload и отдельный периодический retry не добавлены.
4. Webhook scan cursor живёт в процессе, после restart начинается с начала, а durable dedupe предотвращает повтор уже подтверждённой доставки. При backlog повторная попытка ждёт обхода страниц; SLA задержки и большой sustained поток не измерялись. Окно доставки 24 часа сохранено.
5. Crash после успешного HTTP до записи webhook_deliveries и прямые параллельные вызовы processWebhookDeliveryPass могут дать at-least-once повтор; существующий background busy-guard защищает один loop, но не несколько процессов.
6. Runtime модели и долгие role-run leases, полные переходы review/plan/cancel, все маршруты авторизации, файловые пути/SSRF, миграции и восстановление БД требуют отдельного дальнейшего охвата. Нет оснований объявлять их полностью проверенными по этому отчёту.
