# Контракт: чатовый чек-лист — хранение, явная сдача пункта, серверный допуск следующего (25.10.2026)

Шаг `contract` карточки b504958a-4550-4ef3-ac0c-5bc285abcab0. Вход: исследование note://c27023b5-7c07-45b3-9172-1d97dba0edf9 и принятые результаты карточки 252c400e-aa8e-4cab-9993-0d7e85388e1e (контракт Pi, чат, обсуждение, QA, критик). Проверено по живому коду ветки этой карточки (main + коммит 9aea9b36).

## 0. Решение в одном абзаце

Чек-лист одной роли в чате перестаёт быть подсказкой модели. Сервер хранит один документ на пару (чат, роль): пункты в порядке исполнения, версию и серверную запись результатов. Текущий пункт определяет сервер — первый не сданный. Роль **явно сдаёт** результат текущего пункта отдельным действием; сервер отмечает пункт, повышает версию и только тогда выдаёт следующий. Состояния «остановлен» и «заблокирован» ставит сервер, а не модель. Отмена хода, очередь, поколение, выжимка и восстановление переиспользуются как есть — второй конвейер не заводится.

## 1. Границы

**Входит:** серверное хранение и правила чатового чек-листа, явная сдача пункта, серверный допуск следующего, остановка плана, состояния для клиента, критерии проверки.

**Не входит:** командные слоты и граф плана (карточки остаются как есть), обязательная проверка (QA) каждого пользовательского пункта, замороженный веб, живые модельные прогоны, выкладка и перезапуск боевого сервера.

**Принцип:** конвейер управляет движением по пунктам, но не правильностью содержания. Сданный пункт означает «роль объявила результат и сервер это принял», а не «результат верен».

## 3. Хранение

### 3.1. Схема — одна таблица

Расширяем `chat_work_plans` (ключ `(chat_id, role_id)` уже есть). Миграция `176_chat_work_plan_outcomes` — только `ALTER TABLE ADD COLUMN`, без CHECK и без пересборки таблицы:

| Колонка | Тип | Смысл |
|---|---|---|
| `status` | TEXT NOT NULL DEFAULT 'active' | `active` / `finished` / `stopped` — состояние плана. Ставит только сервер |
| `stop_reason` | TEXT | `owner_stop` / `budget_exhausted` / `session_reset` / `error` |
| `stopped_at` | TEXT | Когда остановлен |
| `source_message_id` | TEXT | Сообщение-поручение, с которого план открыт (заполняет сервер) |
| `outcomes_json` | TEXT NOT NULL DEFAULT '{}' | Серверная запись результатов по пунктам |

`items_json` остаётся тем, что пишет роль: порядок и названия. Состояния в нём — подсказка, не истина.

`outcomes_json` — объект по `item_id`:

```json
{
  "impl": {
    "state": "done",
    "result": "Серверный конвейер сдачи и допуска работает.",
    "block_type": null,
    "reason": null,
    "submitted_at": "2026-10-25T04:10:00Z",
    "submission_id": "cmq_...:impl:done",
    "session_generation": 7,
    "plan_revision": 3,
    "stale": false
  }
}
```

Запись пишет только сервер. Модель не может ни положить туда поле, ни изменить его через запись плана.

### 3.2. Правила записи плана (`PUT /api/chats/:id/work-plan`)

Существующие проверки (`validateWorkPlan`: 1–20 пунктов, устойчивые id, не больше одного `in_progress`) остаются. Добавляется:

1. **Версия.** `base_revision` обязателен при активном плане (как сейчас). Несовпадение → 409 с текущим планом.
2. **Пункты неизменяемы после начала.** Пункт с записью в `outcomes_json` (сдан, заблокирован, остановлен) нельзя удалить и переименовать. Можно добавлять новые пункты в конец и менять/удалять только ещё не начатые (`pending`).
3. **Текущий пункт не удаляется** — иначе появился бы обходной путь «пропустить пункт, стерев его». Ответ 409 с `current_item_id` и подсказкой: сдай или останови план.
4. **Заявка «done» без сдачи не принимается.** Пришёл пункт со `state: "done"`, а записи сдачи нет → 409 `item_not_submitted` с подсказкой сдавать через `taskflow_work_item_submit`. План не меняется.
5. **`in_progress` ставит сервер.** Значение от модели игнорируется: сервер сам помечает текущий пункт. Модель не может объявить текущим второй пункт.
6. **Остановленный или закрытый план заменяется новым** без `base_revision` (как сейчас с закрытым): `outcomes_json` очищается, `status` → `active`, `revision` растёт. Старый план не возобновляется.

Каждая принятая запись повышает `revision` и рассылает существующее событие `chat:work_plan` с полным представлением плана.

### 3.3. Вычисляемое представление (единственный источник для клиента и промпта)

`chatPlanView(chatId, roleId)` возвращает:

- `status`, `stop_reason`, `stopped_at`;
- `current_item_id` — первый по порядку пункт без принятой сдачи (если план `active`); `null` для `finished` и `stopped`;
- `items[]` — `{id, title, state, result?, block_reason?}`, где `state` ∈ `pending | in_progress | done | blocked | stopped`:
  - `done` — есть принятая (не `stale`) сдача;
  - `blocked` — есть принятая блокировка;
  - `stopped` — план остановлен и это был текущий пункт;
  - `in_progress` — текущий пункт активного плана;
  - `pending` — остальное, включая отклонённую (`stale`) сдачу.

Итог для владельца собирается из этого же представления: сданные пункты с результатами, остановленный пункт с причиной, оставшиеся — как не начатые.

## 4. Пункт — это результат

- Пункт = законченный результат с наблюдаемым итогом, а не вызов инструмента. Несколько инструментов и один длинный шаг внутри пункта не создают ни нового пункта, ни нового запуска.
- Простая работа — **один пункт**. План не обязателен для короткого ответа. Формулировку `CHAT_PLAN_MISSING_PROMPT` правим: «3–7 этапов» перестаёт быть обязательным минимумом, допустим один содержательный пункт.
- Ужесточений «минимум 3» и «обрыв на каждое действие» нет: это прямо запрещено границами карточки.
- Пункт не превращается в подзадачу, слот, claim, ревью или отчёт перед проверяющим. Командный граф карточек не меняется.

## 5. Явная сдача текущего пункта

### 5.1. Маршрут

`POST /api/chats/:id/work-plan/submit` (только роль — участник чата, только свой план):

```json
{ "item_id": "impl", "result": "1–2 предложения итога", "outcome": "done", "block_type": "needs_input" }
```

`block_type` — только для `blocked`, из существующего набора: `dependency | needs_input | capability | transient`.

Ответ: `{plan_revision, item, current_item_id, next_item, status}` — `next_item` и есть серверный допуск следующего пункта.

### 5.2. Инструмент в ходе чата

Новый инструмент чатового хода `taskflow_work_item_submit`. Поля те же, что у маршрута, без `submission_id`: ключ идемпотентности выводит сервер из (ход доставки, пункт, итог). Модель не придумывает ключи и не может подделать повтор.

Описание инструмента (коротко, без процесса): «Сдать текущий пункт чатового чек-листа: result — 1–2 предложения, что сделано. Сервер отметит пункт и выдаст следующий. Пункт — законченный результат, не вызов инструмента. Пункт вне очереди не принимается».

### 5.3. Правила приёма

Принимается только в ходе чата (есть живая доставка этой роли в этом чате):

1. Плана нет → 409 `chat_plan_missing` («сначала заведи чек-лист»).
2. План `stopped` → 409 `plan_stopped` с `stop_reason`.
3. `item_id` ≠ `current_item_id` → 409 `item_not_current` с `current_item_id`. Прямой переход через несданный пункт отвергается.
4. Пункт уже сдан: тот же ключ идемпотентности → 200 с прежним результатом (без второй записи); другой ключ → 409 `item_already_done`.
5. `outcome=done` без `result` (1–400 символов) → 400. `outcome=blocked` без `block_type` → 400.
6. Ход устарел (доставка `superseded`/`failed` либо поколение пары больше записанного в ходе) → 409 `run_stale`; сдача записывается как `stale: true`, состояние пункта не меняется.

Принятая сдача в одной транзакции: запись в `outcomes_json`, `revision + 1`, при последнем пункте `status='finished'`, рассылка `chat:work_plan`.

### 5.4. Почему именно эти правила

- «Явно» означает отдельное действие с результатом — иначе модель закрывает пункт переписыванием списка, что и есть текущая проблема.
- Идемпотентность по ключу даёт повтор запроса и восстановление после рестарта без второго эффекта.
- Проверка поколения отсекает поздний ответ старого запуска: он виден, но ничего не двигает.

## 6. Серверный допуск следующего

Три точки контроля, других нет:

1. **Начало хода.** `startChatRun` берёт `chatPlanView` и кладёт в системную инструкцию: список пунктов (✓/▶), текущий пункт и его id, требование сдавать результат сдачей, запрет брать остальные. Для `stopped` — «план остановлен, следующие пункты не начинай, покажи сделанное и остановленное». Для `finished` и отсутствия плана — как сейчас.
2. **Сдача.** Только текущий пункт (§5.3). Следующий становится текущим лишь после принятой сдачи.
3. **Запись плана.** Нельзя удалить текущий пункт, нельзя объявить `done` без сдачи, нельзя назначить второй текущий (§3.2).

Отдельного «разрешения на запуск» пункта нет: запуск хода по-прежнему открывает сообщение владельца или восстановление очереди. Пункт не запускает сервер — сервер допускает пункт в уже идущем ходе и выдаёт следующий по сдаче.

## 7. Стоп, блокировка, исчерпание бюджета

Разделяем три разных действия — это разные вещи и для владельца, и для кода:

| Действие | Что происходит | План |
|---|---|---|
| Уточнение (новое сообщение владельца) | Граница поколения, отмена хода, следующий запуск с выжимкой; текущий пункт тот же | `active` |
| Отмена ответа (кнопка «Остановить» в окне чата, `POST /api/chats/:id/stop`) | Отменяется ход; написанное ролью сохраняется как прерванный ответ | `active` |
| Стоп плана (`POST /api/chats/:id/work-plan/stop`, кнопка на полоске чек-листа) | План → `stopped`, `stop_reason='owner_stop'`, текущий пункт → `stopped`, живые ходы роли в этом чате отменяются | `stopped` |

Правила:

- `blocked` ставит роль через сдачу с `outcome=blocked` (нужен ответ владельца, нет доступа, сбой). Следующий пункт не допускается, пока пункт блокирован; ответ владельца приходит обычным сообщением и обычным ходом.
- Исчерпание настроенных пределов (ожидание очереди, повторы доставки, жёсткий останов) ставит `blocked` с `block_type='transient'` и причиной, если ход ещё может быть продолжен, и `stopped` с `stop_reason='budget_exhausted'`, если предел исчерпан окончательно. Второго молчаливого повтора нет.
- Остановленный план новые пункты не принимает; продолжить работу можно только новым планом (§3.2, п.6). Это сознательно: «стоп» останавливает, а не «ставит на паузу».

## 8. Уточнения, поколение и контекст

- Приём сообщения независим от исполнения: строка сохраняется, HTTP отвечает, доставка идёт следом (существующее поведение).
- Уточнение в активном ходе подмешивается на границе следующего вызова модели (`offerChatSteering`), квитанция различает «принято ходом» и «ушло в очередь» — это и есть то различие, которое видит владелец.
- Уточнение, меняющее смысл текущего пункта: отмена хода (граница поколения) и новый запуск с актуальным контекстом. Пункт при этом остаётся тем же; чтобы заменить его на другой, владелец останавливает план и заводит новый.
- Выжимка следующего хода дополнительно называет текущий пункт (id и название) — иначе свежая сессия начинает пункт заново.
- Новой нумерации ввода нет: поколение пары (чат, роль) одно, как в принятом контракте note://f3ada2e0-9fc0-4b61-a8fd-522d7668f12a.

## 9. Рестарт и дубли

- План, результаты и остановка живут в SQLite: после рестарта представление то же.
- Рестарт никогда не двигает пункт: продвигает только принятая сдача.
- Поброшенный ход поднимает существующий `sweepRecoverableDeliveries` → `recoverAgentDelivery`: холодный fence, затем обычный ход с тем же текущим пунктом.
- Повтор запроса сдачи и повтор сообщения (`delivery_id`, ключ идемпотентности) не создают второго эффекта.
- Поздний ответ остановленного или устаревшего хода сохраняется как текст с `stop_reason`/`partial`, но сдача из него не принимается (§5.3, п.6).

## 10. Что получает iOS (после этого шага, шаг `ios`)

- `GET /api/chats/:id/work-plans` и `GET /api/chats/:id/work-plan` отдают представление §3.3 — клиент ничего не вычисляет сам.
- Показываются четыре состояния пункта (`in_progress`, `done`, `blocked`, `stopped`) плюс `pending`, и состояние плана целиком с причиной остановки.
- Итог: сданные пункты с результатами, остановленный пункт с причиной, не начатые.
- Различение сообщения: `saved` (строка есть) и `accepted` (доставка взята в ход или уточнение принято) — вычисляется из `chat_message_queue` по `message_id`, отдельного хранилища не заводим.
- Кнопка «Остановить» в окне чата и «Стоп плана» на полоске — два разных действия (§7).

## 12. Сценарии приёмки (для шага `qa`)

1. Три пункта; уточнение во время первого: сообщение сохранено сразу, ход отменён, поколение выросло, следующий ход объявляет **тот же** пункт и содержит уточнение; второй пункт становится текущим только после сдачи первого.
2. Стоп во время второго: второй `stopped`, третий не допускается; поздняя сдача из остановленного хода → 409, состояние не меняется.
3. Прямой переход через несданный пункт отвергается (`item_not_current`), план не изменился.
4. Модель помечает пункт `done` в записи плана без сдачи → 409 `item_not_submitted`.
5. Простая работа — один пункт: один запуск, несколько инструментов внутри, одна сдача, план `finished`, лишних запусков нет (счёт по `chat_message_queue`).
6. Дубли: повтор сообщения и повтор сдачи не дают второго эффекта; рестарт между сдачей и следующим ходом не задваивает результат.
7. Изменение плана: добавление пункта и переименование не начатого — принимается; удаление сданного или текущего — 409.
8. Пределы: исчерпание ожидания очереди/повторов даёт явное состояние с причиной, без тихого повтора.
9. Совместимость: старый клиент без новых полей по-прежнему рисует полоску; старые маршруты отвечают как раньше.

## 13. Чего не делаем

- Не возвращаем удалённый одиночный dispatch и второй исполнитель.
- Не переносим командные слоты, граф плана и обязательную проверку каждого пункта в продуктовый чат.
- Не заводим вторую нумерацию поколений, вторую очередь, вторую таблицу планов.
- Не пересобираем таблицы и не добавляем CHECK в существующие (`chat_work_plans`, `chats`, `chat_messages`): только `ADD COLUMN` и `CREATE TABLE`.
- Не трогаем веб, пакет Pi, настройки моделей и числовые значения по умолчанию чужих механизмов.
- Не считаем сдачу подтверждением правильности содержания.

## 14. Числа: что конфигурируемо и что решает владелец

Переиспользуются существующие: `TASKFLOW_CHAT_QUEUE_WAIT_MS` (ожидание очереди), предел повторов доставки (`chatDeliveryMaxRestarts`), предел ожидания остановки (`DEFAULT_STOP_WAIT_MS`, 10 с, из принятой ветки), аренда доставки (`TASKFLOW_CHAT_DELIVERY_LEASE_MIN`).

Новые пределы (число пунктов на поручение сверх плана, общий бюджет поручения, предел автопродолжений) **не вводятся без решения владельца**: до согласования тесты используют явные малые значения и проверяют границу N/N+1, а новый путь в production не включается.

## 15. Риски и границы гарантий

- Сдача подтверждает факт результата, но не его правильность: проверка содержания остаётся делом владельца и штатной проверки продукта, а не каждого пункта.
- Отмена не доказывает завершение внешней работы: неотменяемое действие остаётся видимым, в выжимке — «результат неизвестен», слепого повтора нет.
- Ответ устаревшего хода всё равно виден в ленте как текст: сдача из него не принимается, но модель могла написать «сделано» — это расхождение честно показывается в итоге плана.
- Один документ на пару (чат, роль) означает, что параллельные записи сериализуются проверкой версии; при конфликте роль перечитывает план (существующее поведение 409).
- Конвейер не мешает модели ошибаться в содержании пункта: он мешает только пропускать пункты и продвигаться без результата.
