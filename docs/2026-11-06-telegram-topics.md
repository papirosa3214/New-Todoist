# Топики Telegram как рабочие пространства (этап 7, карточка 7406889e)

## Результат

`/topic <имя>` создаёт топик в личном чате и привязывает его к отдельной комнате TaskFlow: сообщения разных топиков больше не лежат одной лентой. Внутри топика доставка идёт строго по порядку, разные топики обрабатываются параллельно (не больше 8 одновременно). При выключенном флаге `TASKFLOW_TELEGRAM_TOPICS` поведение полностью прежнее.

## Что сделано

- **Адрес беседы.** `TelegramInbound.thread_id` — часть адреса `{channel, account, chat, thread, principal}`. Номер треда хранится в `telegram_inbound_ledger.thread_id` и в `telegram_delivery_outbox.thread_id`, а также дублируется в payload доставки.
- **Способ адресации — из живого факта, не из документации.** Отчёт Лайф-тестировщика 06.11.2026 (note `artifact_sav_38bfdddc-0d4c-47c1-9c15-53e852c60c61`): в личном чате топик адресуется `message_thread_id`; `direct_messages_topic_id` там сообщение в топик не кладёт, а `createForumTopic` отвечает «the chat is not a forum», пока режим топиков не включён в @BotFather. Поэтому в Bot API уходит только `message_thread_id`.
- **Привязка.** Новая таблица `telegram_topic_binding(bot_id, chat_id, thread_id, chat_id_target, role_id, title, created_at)`. Комната под топик создаётся в `chats` с устойчивым id `chat-topic-<хеш>` и двумя участниками (владелец и Секретарь).
- **`/topic <имя>`** — служебная команда, а не ход роли: кладёт намерение `createForumTopic` в outbox. Id треда известен только после ответа Bot API, поэтому привязка появляется там же (`settleTelegramTopicDelivery` по `/outbox/:id/result`), а подтверждение владельцу уходит уже в новый топик.
- **`/topic rename <имя>`** — `editForumTopic` по уже известному треду и одновременное переименование комнаты.
- **Порядок.** Gateway группирует пачку outbox по ключу `{chat}:{thread}`: один ключ — последовательно (FIFO), разные ключи — параллельно, потолок `CONVERSATION_LIMIT = 8`. Строка статуса и «печатает…» тоже раздельные по треду.
- **Прежнее поведение.** Без флага тред не читается и не передаётся, `/topic` — обычный текст, всё идёт в `chat-secretary`. Ключ `status-bubbles.json` стал `{chat}:{thread}:{reply_to}` — для старых записей (два сегмента) поведение то же при треде 0; история не переписывается.
- **`captureTelegramFinal`** и захват вопроса ищут связи через ledger и теперь переносят `thread_id` в доставку: ответ уходит в тот же топик.

## Миграция

`202_telegram_topics` — `ALTER TABLE … ADD COLUMN thread_id` (обе таблицы, с проверкой `PRAGMA table_info`) плюс `CREATE TABLE IF NOT EXISTS telegram_topic_binding`. Ставлена сразу за `201_telegram_secretary_integration`: таблицы telegram-интеграции появляются именно там.

Откат — обратная миграция: `DROP TABLE telegram_topic_binding;` и (при необходимости) `ALTER TABLE … DROP COLUMN thread_id`; колонки аддитивные, код без них не падает — при выключенном флаге они не читаются.

Штатный порядок выкладки: резервная копия базы (штатный `sqlite3 .backup` — как в `server/scripts/backup.sh`; при выкладке `deploy-when-idle.py` снимает `pre-deploy-*.db`), очередь ролей и чатов пуста, сборка `dist`, рестарт сервера (миграции идут в `runMigrations()` при старте), затем рестарт gateway — в этом порядке, чтобы gateway не увидел метод, которого сервер ещё не знает.

- Живой Bot API не вызывался: режим топиков у @ckor22_bot выключен (см. отчёт Лайф-тестировщика), включение — действие владельца в @BotFather.

## Ограничения

- Живой сценарий «/topic создаёт топик, три быстрых сообщения идут по порядку» не выполнен: без включённого в @BotFather режима топиков `createForumTopic` отвечает отказом. Код разбора, привязки и маршрутизации проверен на временной базе, поведение Bot API — нет.
- `sendMessageDraft` и реакции в топик не адресуются отдельно (у них нет параметра треда); черновик и статус идут в общий топик.
- Пауза между частями и лимит параллельности 8 проверены чтением кода; нагрузочной проверки не было.
