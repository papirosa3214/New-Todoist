**Карточка:** 3e27dafe-ae7f-4449-8978-ba68d40f6aea · **Шаг:** widget_implementation (builder) · **Дата:** 2026-10-14
**Коммит сервера:** `b49a8cab`
**Визуальная часть:** `docs/2026-10-14-widget-gallery-layouts-and-types.md` (дизайнер, коммит b6d27ed4) и `docs/2026-10-14-widget-visual-language.md`.

Этот документ — то, что сервер обещает клиенту: какие типы и с какими полями
дойдут до `ChatWidgetView`, в каком виде нормализуются и когда их начнёт
предлагать секретарь. Визуальные решения сюда не дублируются.

## 2. Типы и поля: что клиент получает на вход

Точные ограничения — в документе дизайнера, раздел 5. Здесь важны три вещи,
из-за которых клиент обязан быть готов к любому из этих блоков.

| `type` | Обязательные поля | Массивы, которые клиент обязан уметь рисовать |
|---|---|---|
| `status_board` | `groups` | `groups[]`: `label`, `value`, `tone`; опционально `share`, `icon` |
| `bars_list` | `items` | `items[]`: `label`, `value`, `max`, `tone`; опционально `meta` |
| `chain` | `links` | `links[]`: `label`, `state`; опционально `meta` |
| `ladder` | `steps` | `steps[]`: `label`, `value`, `state`; опционально `note` |
| `timeline` | `items` | `items[]`: `date`, `label`, `state`; опционально `meta` |
| `calendar_grid` | `month`, `cells` | `cells[]`: `date`, `count`; опционально `tone` |
| `heatmap` | `weeks`, `cells`, `max` | `cells[]`: `date`, `value` |
| `compare` | `left`, `right` | объекты `{label, value}`, у каждого опционально `link` (только `https`) |

Значения `tone` и `state` — из смысловой таблицы: `done`, `inprog`, `over`,
`future`, `block`, `review`, `free`. Валидатор отклоняет всё остальное и
предупреждает про лишние поля внутри элементов: поле, которого нет в
контракте, клиент не рисует, а молча пропавший столбец читается как ошибка
данных.

Общее для всех восьми (из раздела 8.2 галереи): высота до 320 pt без
прокрутки, ширина от 320 pt, блок до 8 КБ, никаких внешних ресурсов,
`link.url` только `https`, неизвестное значение — прочерк, а не ноль.

## 3. Нормализация: что именно дойдёт без искажений

1. **Новый тип проходит байт в байт.** Нормализатор отдаёт канонический блок
   как есть; ключи, порядок и значения не меняются. Проверено тестом на всех
   восьми примерах из документа галереи.
2. **Старые шесть типов и старый формат секретаря** (без `type`, с
   `metrics[]`, `chart{type,data}`, `checklists[]`, `checked`) ведут себя как
   раньше — на них написаны 112 блоков в 57 рецептах.
3. **Запрещённый корень.** Тип, которого нет в `CANONICAL_TYPES`, идёт в
   ветку «старый формат секретаря»: если у него в корне есть `chart`,
   `metrics` или `checklists`, имя типа теряется и блок уезжает в чужую схему.
   Валидатор это отвергает, тест держит правило.
4. **Обратная сторона.** Зарегистрированный тип с лишним корневым ключом
   (например `heatmap` с `chart`) нормализатором больше не переписывается —
   клиент получит `heatmap` и проигнорирует неизвестный ключ. Это безопаснее
   потери типа, но лишний ключ в блоке — ошибка автора блока.

## 4. Данные: откуда роль берёт то, что нечем наполнить

Три типа без данных рисуются выдуманными датами — это хуже, чем не отправить
блок. Сервер дал роли три источника:

| Тип | Инструмент роли | Что отдаёт |
|---|---|---|
| `timeline`, просрочки по дням, компоновка К2 | `taskflow_my_tasks`, `taskflow_project_tasks` | у каждой задачи теперь есть `срок` (ГГГГ-ММ-ДД) и `приоритет` (1–4), когда они есть |
| `heatmap` | `taskflow_task_daily(from, to, bucket)` | ячейка на каждый день периода, включая нули, плюс `total` и `max` |
| `calendar_grid` | `taskflow_calendar_events(date или from/to)` | события, сгруппированные по дням; неподключённый календарь даёт пустой список, а не ошибку |

Тот же агрегат доступен как маршрут: `GET /api/tasks/summary?from=…&to=…&bucket=due|created|completed`.
Даты вне календаря и приоритет вне 1–4 отбрасываются на сервере: в блок не
попадёт «2026-02-30».

## 5. Фиче-флаг: когда секретарь начнёт предлагать новое

Сервер принимает восемь новых типов **всегда** — блок, который пришёл, не
портится и не теряет имя типа.

Предлагать их в инструкции роли можно только когда клиент их рисует,
поэтому перечень новых типов в инструкции закрыт флагом:

- `TASKFLOW_WIDGET_NEW_TYPES=1` (или `on`/`true`/`yes`) — новое включено;
- не задана, пуста или любое другое значение — выключено, секретарь работает
  на шести старых типах.

**Порядок для команды:** сначала клиент на Mac учится рисовать новые типы
и проверяется на симуляторе; затем включается флаг на сервере. Включать флаг
раньше бессмысленно: роль отправит блок, который клиент нарисует пустым.

## 6. Где сервер проверить нельзя

- Рендер в живом чате: веб-клиент на .110 виджеты не рисует вовсе
  (`src/screens/ChatScreen.tsx:80`), нативный клиент живёт на Mac.
- Светлая и тёмная тема, отступы, смена темы на лету, VoiceOver, анимации.
- Живой вход в календарь Google: маршрут есть, но проверялся только на
  пустом ответе без подключённого календаря.

## 7. Передача на клиент (Мак, `ChatWidgetView.swift`)

1. Реестр `type → компонент` на 14 типов: шесть существующих, восемь новых
   из раздела 2.
2. Для шести старых — приём новых полей компоновок K1–K6 (`tone`, `icon`,
   `state`, `overdue_days`, `progress`, `layout`) без поломки старых блоков.
3. Текстовый запасной вариант для неизвестного типа (раздел 8.3 галереи) —
   сейчас неизвестный тип даёт «виджет не разработан», то есть молчаливую
   поломку на стороне владельца.
4. Ограничения раздела 8.2 и поведение при плохих данных из 8.4.

Ответственный за перенос серверной части в main — оркестратор, шаг `assemble`.
