# Как у Гермеса устроена связь между агентами (разбор 06.10.2026)

Источник: код на машине, `~/.hermes/hermes-agent/tools/` (`bot_relay.py`, `bot_mode_dm.py`, `bot_failure_reasons.py`, `async_delegation.py`, `async_delegation_recovery_hints.py`), `~/.hermes/bot_relay/`. Только чтение, настройки Гермеса не менялись.

## Что есть у Гермеса

1. **Личка как инструмент `message_agent`.** Агент пишет коллеге по имени из списка команды (список имён и ролей лежит в его системной инструкции). Сервер сам ставит префикс «сообщение от …», проверяет адресата по живому списку, отправляет в фоне. Наставление в описании инструмента: «пиши одному подходящему, не рассылай всем», «сформулируй сам, не вставляй чужие слова», «не жди и не опрашивай».
2. **Ответ сам будит отправителя.** Отправка «выстрелил и забыл»: агент заканчивает ход, а по завершении фонового процесса отправитель просыпается новым ходом с исходом — либо ответ коллеги, либо ошибка доставки. Ждать и опрашивать не нужно.
3. **Сбой это обычный результат, приходит так же, как ответ.** Закрытый словарь причин (`bot_failure_reasons.py`): `runtime_offline`, `queued_expired`, `delivery_timeout`, `agent_blocked`, `cancelled`, `provider_auth_or_access`, `provider_quota_limit`, `provider_rate_limit`, `provider_server_error`, `context_overflow`, `missing_config`, `model_unavailable`, `unknown`. Классификатор разбирает текст ошибки провайдера в код.
4. **Политика повтора по коду.** Временные (офлайн, таймаут, лимит частоты, ошибка сервера) повторяются автоматически один раз в той же сессии. Переполнение контекста: сжать и продолжить. Авторизация, квота, конфиг, модель — не повторять (только жжёт квоту), вернуть сбой отправителю.
5. **Быстрый отказ.** Адресат точно офлайн — отказ сразу с причиной, а не письмо в пустоту. Письмо старше 15 минут — отказ `queued_expired`. Просроченное без ответа ещё раз предлагается один раз; потом вечно не висит.
6. **Фоновая делегация (`delegate_task(background=true)`).** Родитель получает дескриптор и идёт дальше; по завершению ребёнка в общую очередь кладётся событие, и родитель получает НОВЫЙ ход. Результат пишется в базу (`sqlite`), события доставки с арендой на 300 с, не более 8 попыток, потом `dropped`, не бесконечность.
7. **Смерть исполнителя тоже сообщается.** Если процесс умер (OOM, падение) до записи результата, выпускается событие «брошенная делегация» с хвостом транскрипта (20 строк) и снимком git (ветка, коммит, число несохранённых файлов). Родитель решает «продолжить или перезапустить» без расследования. Свёртка осиротевших событий каждые 30 с.

## Чем у нас иначе (проверено по коду и базе)

- Наше сообщение — запись в чат и в `agent_inbox`; ответ отправителя будит только если адресован. Исход доставки отправителю не возвращается (по базе не вижу такого события).
- Сбои (`plan_subtask_autostart_failed`, `plan_subtask_stalled_blocked`, `model_failover`) пишутся только в `task_events`, получателя нет. У Гермеса сбой возвращается тому, кто ждал.
- Коды причин у нас свободным текстом (`TaskContext >15 с`, `429 {...}`), решений по ним нет, кроме переключения модели.
- Нет «быстрого отказа» и срока жизни сообщения.
- При гибели шага нет события с хвостом журнала и снимком git для оркестратора; восстанавливаем руками.
- В системной инструкции ролей список коллег не лежит, только вызов `taskflow_agents`.

## Что перенимать (кандидаты)

1. Исход каждого действия возвращается тому, кто его запустил, новым ходом: ответ ИЛИ код причины сбоя.
2. Закрытый словарь причин сбоя + политика повтора по коду (повторять временные, не повторять auth/quota/config).
3. Срок жизни задания в очереди и быстрый отказ при недоступном адресате.
4. Событие «шаг брошен» с хвостом журнала и снимком git родителю/оркестратору.
5. Список коллег с ролями в инструкции роли, наставление «одному подходящему, суть первой строкой».
