# Умная очередь сообщений у ролей (21.10.2026)

## Задача

Владелец 21.10.2026: «настроить умную очередь сообщений у ролей в приложении iOS
в чатах». Спецификация дословно:

1. Любое сообщение занятой роли, от вас или от коллеги, из любого чата, сразу
   подмешивается в её текущий ход с пометкой: от кого, откуда и что делать.
   Относится к текущей работе — учти сейчас. Не относится — не отвлекайся.
2. Решает сама роль. Если она ответила или учла сообщение по ходу, оно снимается
   из очереди.
3. Ничего не теряется. Если роль его не тронула, после окончания хода оно
   приходит обычной очередью.
4. Служебные строки. Вместо «вопрос в очереди» будет статус «доставлено в
   работу», после ответа строка исчезает.
5. Подмешивание срабатывает между шагами модели. Инструмент, который уже начал
   работать, не прерывается.

До этой работы подмешивание в ход работало только для сообщений владельца и
только в тот же чат (коммит `6e58a34d`).

## Что сделано

### Реестр подмешивания — по роли, а не по паре (чат, роль)

`server/src/runtime/chatSteering.ts`

Было: `Map<chatId, Map<roleId, Registration>>` — уточнение находило только ход
в том же чате, что и сообщение.

Стало: `Map<roleId, Map<chatId, Registration>>` — реестр ведётся по роли, внутри
по чату. Правило выбора хода:

- ход в том же чате — берётся он;
- ходов несколько, в этом чате хода нет — берётся единственный активный ход
  роли (если он один);
- ходов несколько и ни одного в этом чате — сообщение **не подмешивается**:
  непонятно, чей ход. Сообщение уходит обычной очередью и ничего не теряется.

### Снято ограничение «только владелец»

`server/src/routes/chats.ts`, `dispatchRoleReplies`

Гейт `isOwner(args.fromUserId)` убран: уточнение может прийти от коллеги-роли.
Риск петли ролей ограничен уже существующим `MAX_AGENT_HOPS`.

### Пометка источника

Подмешиваемый текст теперь такой:

```
Сообщение в ход (сообщение <id>):
от <кто> из чата «<название чата>»:
<текст сообщения>
Ответь автору через taskflow_chat_reply(message_id=<id>, text=…) — в этом чате он твоего ответа не увидит.
```

Последняя строка добавляется **только** для сообщения из другого чата: автор
ждёт ответа у себя, в чат, где идёт ход, его ответ не дойдёт. Для своего чата
вызова ответа не требуется — итог хода и так уходит в переписку.

### Служебная строка «доставлено в работу»

`server/src/runtime/chatCoordination.ts` — три новые функции:

- `registerCoordinationOriginSelf(questionId, requesterId)` — исток обращения для
  сообщения владельца (сам вопрос — исток); существующий исток не перетирается;
- `markDeliveredToWork(questionId, recipientId, requesterId?)` — создать или
  обновить карточку координации: статус `delivered`, activity «Доставлено в
  работу»;
- `markCoordinationAnswered(questionId, recipientId)` — статус `answered`,
  terminal: строка закрыта (в приложении прячется).

Отметка «доставлено в работу» ставится **сразу**, как только SDK взял ввод
(`receipt.delivered`), а не в конце хода. Это важно: обработчик очереди роли в
момент подмешивания занят тем же ходом — ждать его конца нельзя, строка должна
быть видна во время работы. Поэтому отметка вешается в пути ответа на POST
сообщения, а не в FIFO-обработчике доставки.

Ответ роли закрывает строку двумя путями: `coordinationDeliveryChanged` (когда
роль ответила связанным сообщением — с текстом ответа) и `markCoordinationAnswered`
(когда ход закончился, а ответ пришёл в общий чат).

### Разделение «в очереди» и «в работе»

`server/src/runtime/inProcessRun.ts`

`deliverChatToWork`/`deliverTopicToWork` теперь различают:

- `working` — сообщение подмешано в текущую работу роли;
- `queued` — слот вот-вот начнётся, сообщение ждёт;
- `busy` — ходов несколько, адресат не определён;
- `idle` — хода нет.

Потребители смотрят только на `!== "idle"` и `=== "busy"`, поэтому расширение
контракта безопасно; два существующих теста в `server/test/inProcessRun.test.ts`
обновлены под новое значение.

### Канон системной инструкции роли

`server/scripts/role-system-prompt.md` — раздел «Уточнения в ход»:

- относится к текущей работе — учесть немедленно;
- не относится — не отвлекаться, после хода придёт очередью;
- из другого чата — ответить через `taskflow_chat_reply(message_id=…, text=…)`;
- отвечать на уже учтённое уточнение не нужно.

Канон копируется в папку роли как `SYSTEM.md` с кэшем по mtime — рестарт
сервера не нужен.

## Грабли

1. **Реестр подмешивания должен быть по роли.** Пара (чат, роль) физически не
   даёт подмешивать сообщение из соседнего чата.
2. **Отметку «доставлено в работу» нельзя вешать в FIFO-обработчике доставки:**
   он стоит в очереди за текущим ходом роли и отработает только после него —
   строка «доставлено в работу» не появилась бы никогда. Она вешается по
   факту взятия ввода SDK.
3. **«Занято» у роли — это два разных состояния:** «слот скоро начнётся»
   (очередь) и «уже подмешано в текущую работу» (в работе). Смешивать их нельзя:
   служебная строка показывает разные вещи.
4. **Ответ из другого чата** нельзя отдавать итогом хода: автор пишет в своём
   чате, а ход идёт в другом. Отдельный вызов `taskflow_chat_reply`.
5. **Таргет снапшот-тестов iOS сломан в HEAD** (`TodayEmptyIllustration` удалён
   коммитом `b8073dc3`, а `SnapshotTests/TaskRowSnapshotTests.swift` на него
   ссылается) — сборка `build-for-testing` падает на чужом таргете. Для сборки
   таргет временно убирали из схемы, `project.yml` восстанавливали сразу.
