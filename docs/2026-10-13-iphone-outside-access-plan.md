# Выход iPhone к TaskFlow вне дома — разбиение работы по ролям

Карточка: `b5a16110-abdc-4368-8db2-c857816b18d8` («Доступ iPhone к TaskFlow вне дома: ретранслятор и привязка по QR»).
План: `tcp_bf95c969-fd18-454b-b491-89a41f684c1c`, версия 2, профиль `orchestrated`.
Документ описывает решения шага «Разложить работу по ролям и запустить команду» (Оркестратор) и является
записью для проверяющего и для сборки. Это не документ решения по существу задачи — его пишет архитектор.

## Граф шагов

```
orchestrate (Оркестратор, разбиение)
  └─ relay_research (Исследователь)      разведка внешних вариантов
       └─ design_doc (Архитектор)         документ решения + контракты
            └─ server_pairing (Разработчик)  реализация в server/ + тесты
                 └─ verify_review (Критик)    независимая проверка критериев
                      └─ assemble (Оркестратор) приёмка, перенос в main, итог
```

Параллельных веток нет. Каждый шаг ведёт в `assemble` — сборка не начнётся, пока не сданы все результаты.

## Почему связи линейные

- `relay_research → design_doc`: критерий приёмки 1 требует «выбор ретранслятора с обоснованием».
  Обоснование опирается на сравнение внешних вариантов (своя прослойка на VPS против готовых решений);
  без него архитектор выбирал бы наугад.
- `design_doc → server_pairing`: реализация берёт документ как контракт — эндпоинты, поля, таймауты,
  что хранится хешем, коды ошибок, список тест-кейсов. Общий изменяемый артефакт один и тот же.
- `server_pairing → verify_review`: независимая проверка критериев 2 и 3 имеет смысл только по коду.
- Все шаги работают с одним и тем же артефактом (сервер TaskFlow и один документ решения).
  Разделить их по файлам нельзя: это не два независимых куска, а последовательные стадии одного решения.
- Одна роль — один шаг: параллельность появилась бы только из двух веток на разных ролях
  с непересекающимися файлами, таких здесь нет.

Ожидаемый режим работы: одновременно один исполнитель, пик параллелизма — 1.

## Роли и их результаты

| Слот | Роль | Что сдаёт |
|---|---|---|
| `relay_research` | Исследователь | Сравнение вариантов ретранслятора с рекомендацией + пригодное для переноса из App Relay (EKKO Studio) |
| `design_doc` | Архитектор | Документ решения в проекте «Доступ к TaskFlow вне дома»: схема, выбор, угрозы, требования к iOS, контракты |
| `server_pairing` | Разработчик | Миграция и адреса выдачи одноразового QR (5 минут, в базе только хеш), обмена на токен устройства, отзыва + тесты |
| `verify_review` | Критик | Вердикт против трёх критериев приёмки через `taskflow_review` |

## Почему лайф-тестировщик не привлечён

Проверяемого экрана нет: сценарий — серверные адреса для iPhone вне домашней сети, сам ретранслятор по карточке
не разворачивается (выкладка и перезапуск .110 — отдельное решение владельца). Прогон в браузере не проверял бы
ничего из критериев. Реализацию и тесты проверяет критик по коду.

## Ответственный за интеграцию

Оркестратор, шаг `assemble`: приёмка результатов, перенос принятого кода в main, итоговый документ карточки.
Отдельного шага «Интеграция» в этом режиме нет. Поля «Ответственный за интеграцию» через доступные оркестратору
инструменты не видно; действует автоматический выбор сервера (оркестратор → архитектор → единственный исполнитель).

## Границы, переданные в шаги

Входит: `server/` и документ решения. Не входит: правки iOS-клиента (ведётся на маке отдельно), выкладка
на живой сервер и перезапуск, прямой канал WebRTC и мобильный интерфейс, если этого не потребует документ решения.
