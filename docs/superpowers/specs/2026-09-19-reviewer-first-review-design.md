# Reviewer-first ревью для TaskFlow

**Дата:** 2026-09-19  
**Статус:** согласовано по частям, ожидает финального просмотра перед реализацией

## Цель

Новые задачи по умолчанию должны пройти Reviewer до финального закрытия
владельцем. Владелец может отключить этот маршрут у конкретной карточки и
проверять её сам.

## Пользовательский поток

```
Исполнитель сдаёт работу → review
  ├─ requires_reviewer_review = 1
  │   ├─ Reviewer одобряет, комментарий необязателен
  │   │   └─ карточка остаётся active/review и ждёт владельца
  │   └─ Reviewer возвращает на доработку, комментарий обязателен
  │       └─ in_progress; поручение доставляется исполнителю
  └─ requires_reviewer_review = 0
      └─ владелец сам закрывает или возвращает с обязательным комментарием
```

Одобрение Reviewer никогда само не закрывает карточку. Финальное закрытие
остается действием владельца.

## Модель данных и совместимость

В `tasks` добавляется `requires_reviewer_review INTEGER NOT NULL DEFAULT 1`.

- Миграция после добавления колонки явно обновляет уже существующие записи до
  `0`: они сохраняют сегодняшний маршрут и не оказываются внезапно в очереди
  Reviewer.
- Новая карточка получает `1`, если клиент не передал явное значение.
- Флаг доступен в API задачи и разрешён владельцу в create/PATCH.
- Вводить отдельное состояние после одобрения не нужно. Задача остаётся в
  `agent_state='review'`; источником истины служит актуальная запись в
  `reviews` для текущей версии результата.

## Серверные правила

1. Для `requires_reviewer_review=1` право закрыть задачу появляется только
   после `approved`-вердикта, записанного учётной записью с `isReviewer` для
   текущей версии результата. Одобрение владельца не заменяет Reviewer;
   сервер отклоняет такой обход и через `POST /api/reviews`.
2. Reviewer может записать `approved` с пустым либо непустым `findings`.
   После этого сервер уведомляет владельца и карточка остаётся активной.
   Непустой текст показывается в истории ревью карточки как комментарий
   Reviewer к вердикту.
3. Reviewer может выполнить только `review → in_progress`; для этого текста
   комментария требует сервер. Существующая доставка `review_return` в inbox
   исполнителя сохраняется.
4. На карточке с включённым флагом владелец и исполнитель не могут обойти
   Reviewer возвратом из `review`; переход разрешён только Reviewer.
5. При выключенном флаге сохраняется сегодняшний сценарий: владелец может
   вернуть в работу с комментарием или закрыть. Внешние агенты не получают
   новых полномочий.
6. Вердикт привязан к версии результата. После возврата и повторной сдачи
   старая запись одобрения не годится для нового закрытия.

## API

Существующие `POST /api/reviews` и `POST /api/tasks/:id/state` остаются
основными точками входа.

- `POST /api/reviews`, `verdict='approved'`: принимает Reviewer; `findings`
  необязателен. В ответе и событиях фиксируется автор вердикта.
- `POST /api/tasks/:id/state`, `review → in_progress`: принимает комментарий
  и проводит проверку флага и роли до изменения строки задачи.
- `POST/PATCH /api/tasks`: принимают `requires_reviewer_review` только от
  владельца. При создании отсутствие поля означает `true`.
- `PATCH /api/tasks/:id` со `status='completed'`: при включённом флаге
  проверяет одобрение Reviewer актуальной версии; при выключенном использует
  существующее правило владельческой приёмки.

## Клиенты

### Web

- В форме задачи — переключатель «Сначала ревьюер», включённый по умолчанию.
- Владелец до вердикта видит «На ревью у Reviewer», без действий закрытия или
  возврата.
- Reviewer видит «Одобрить» (необязательный комментарий) и «Вернуть на
  доработку» (обязательный комментарий).
- После одобрения Reviewer владелец видит «Закрыть задачу» и запись Reviewer
  в журнале.

### iOS

Те же флаг, подписи и ограничения, что в web. Нативный клиент отправляет
переключатель при создании/редактировании и не отображает владельческие
кнопки раньше вердикта Reviewer.

## Тесты

Серверные интеграционные тесты покрывают:

1. Новый task получает флаг `1`, существующая карточка после миграции — `0`.
2. Reviewer одобряет с комментарием и без него; задача не закрывается.
3. Карточка с флагом `1` не закрывается владельцем до одобрения Reviewer и
   закрывается после него.
4. Reviewer возвращает с текстом, текст попадает в inbox исполнителя;
   пустой текст даёт 400.
5. Владелец и исполнитель не могут вернуть такую карточку из review.
6. При флаге `0` владелец сохраняет прямой маршрут.
7. Повторная сдача создаёт новую версию и блокирует закрытие по старому
   одобрению.

Web и iOS покрывают сериализацию флага и видимость доступных действий.

## Не входит в эту поставку

- Автоматическое закрытие карточки после Reviewer.
- Выбор произвольного Reviewer на карточку: используется действующая учётная
  запись Reviewer.
- Назначение Reviewer через чат или его включение в исполнительскую очередь.
