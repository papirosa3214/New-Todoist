## Что сделано в этой сессии

### 1. Reviewer-first (ревьюер)
- `role_critic_verifier` («Критик-проверяющий») — полноценный ревьюер
  (`Critic/Verifier`); отдельная учётка `Reviewer` удалена, её 17 сообщений
  чата перевешены на верификатора.
- Инструмент вердикта **`taskflow_review`** (одобрить/вернуть с обязательным
  комментарием), добавлен в ролевые профили Pi.
- Будильник поднимает верификатора на сдаче (`requires_reviewer_review`),
  когда служба включена.
- Вердикт виден в ленте карточки (комментарий) + уведомление владельцу.
- **Правило:** гейты ревью — только для агентов; **владелец вне процесса**.
- Настройка **«Сначала проверка Reviewer»** — общая (`users.reviewer_first_default`),
  решается **в моменте**; тумблер в «Обзор → Система» (iOS) / «Настройки → Сервер» (web).
- Кнопки ручного запуска в карточке: **«Запустить исполнителя»** и
  **«Отправить на проверку верификатору»** — разовый заход
  `trigger.py --once` через `POST /api/tasks/:id/run`.

### 2. Процесс и отчёт
- В `AGENT_RULES` (server/src/agentState.ts) и `AGENT-PROTOCOL.md` — обязательный
  **«Отчёт по задаче»** с шаблоном (цель/итог/этапы/заключение/решения/грабли/
  границы/хвосты/доказательства/ссылки), сводный отчёт по родительской задаче.
- В `AGENT-PROTOCOL.md` зафиксировано правило **«Владелец вне процесса»**.

### 3. Модельная лесенка (эскалация по лимитам/способностям)
- Миграция **048**: таблица `model_ladder` (5 ступеней) и `provider_limits`
  (лимит помечается на **учётку**, не на модель).
  Ступени: 0 `MiniMax-M3`; 1 `claude-haiku-4-5 | gpt-5.6-luna`;
  2 `claude-sonnet-5 | gpt-5.6-terra`; 3 `claude-opus-5 | gpt-5.6-sol`;
  4 `claude-fable-5-1 | gpt-6-astra`.
- `server/src/lib/modelLadder.ts`; маршрут `/stop` ходит по ступеням:
  лимит — **вбок** (с одиночной ступени 0 — вверх), нехватка —
  **вверх**, нет живой учётки — **блок**.
- Разбор провала захода в `trigger.py` (`classify_failure`): лимит →
  `provider_limit` (+ окно 5ч/нед), нехватка → `insufficient_capability`;
  `/stop` принимает `window_kind`.
- **Проект лесенки:** карточка `dca29510`; полное описание —
  `~/reply-to-reviewer.md`, раздел «ПРОЕКТ: эскалация моделей по ступеням».
  Карточка реализации — **`f8e8a055`**.

### 4. Расписание: запуск по времени + повтор
- Поля карточки (миграции **049**, **050**): `run_at` (собирается из
  даты+времени, **09:00 по умолчанию**), `run_repeat`
  (`none|daily|weekdays|weekly|monthly`), `repeat_until`, `recurrence_spawned`.
- Воркер **`taskflow-scheduler`** (systemd-таймер, раз в 5 минут; живёт
  **независимо от будильника**):
  - **ветка 4** — запуск по времени: активная неначатая карточка с
    агентом-ролью, `run_at ≤ now` (окно догона 24ч) → одиночный заход;
  - **ветка 5** — повтор «одна за раз»: по завершённой карточке создаётся
    следующее вхождение с новой датой, максимум одна будущая; серия
    **ограничена календарным годом** (31 декабря), дальше не идёт.
- **Лампа «Расписание»** (web «Настройки → Сервер», iOS «Обзор → Система»):
  работает / молчит N мин / не работает, по отпечатку живости воркера
  (`~/.local/state/taskflow-scheduler/last-run.json`, отдаётся в
  `GET /api/agent-service` → `scheduler`).
- **Конец года:** воркер не обрывает молча — шлёт уведомление «Серия «…» дошла
  до конца года. Продлить?»; в карточке — **«Продлить на год»**
  (`POST /api/tasks/:id/repeat-extend`, владелец).
- iOS: в редакторе срока — выбор повтора, «повторять до», подсказка
  «старт 9:00, если время не задано».
- Следующее вхождение — обычная карточка с датой, поэтому **отражается в
  «Сегодня/Предстоящих» и календаре**.

### 5. Прочее
- **«Без проекта»** — раздел в «Проектах» (iOS + web): все задачи без проекта
  одним списком.
- **Владелец в списке исполнителей** (iOS + web): карточка на нём
  неприкосновенна для агентов и воркера.
- **Чат:** ответ Секретаря появляется в ленте сразу, без перезахода.
- **Задачи проекта:** список обновляется после удаления и свайпа.
- **Одно действие принятия** с одной подписью («Принять и закрыть задачу»).
- MCP-инструмент **`taskflow_runtime`** — что реально подключено у Pi.

## Грабли (важно)
- **`tsx watch` перезапускает код, но НЕ прогоняет новые миграции.**
  Новую миграцию применять руками:
  `cd server && npx tsx -e "import { runMigrations } from './src/migrations.ts'; runMigrations()"`.
- **MCP трекера может отвалиться посреди сессии.** Работать через HTTP-API:
  `ssh maksim 'python3 ~/.claude/vault-run.py --secret T=TASKFLOW_AGENT_TOKEN -- python3 ...'`.
  Ролевые токены: `TASKFLOW_AGENT_TOKEN_BUILDER`, `_ARCHITECT`, `_CRITIC_VERIFIER` и т.д.
  Сам трекер-API: `http://localhost:3001`.
- **Серверный intake ≠ будильник.** Подбор роли и флаг делает серверный
  `applyIntakeToNewTask`; гейты — «Режим» (`users.task_intake_mode`) и
  (после 19.09) включённый будильник для назначения. Выключенный будильник
  не гасит intake.
- **Владелец вне гейтов** — любые маршруты/ограничения только для агентов.
- **Службы на `.110`:** `taskflow-server` (tsx watch), `taskflow-trigger`
  (будильник; сейчас **выключен**), `taskflow-scheduler` (таймер 5 мин — воркер),
  `taskflow-mcp-net`, `taskflow-agent-watch`, `taskflow-chat-watch`.
