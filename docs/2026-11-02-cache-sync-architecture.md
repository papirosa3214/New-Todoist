## 2. Какая дырка осталась (суть задачи)

**Догон после разрыва связи есть только для карточек. Всё остальное, что показывает телефон, после разрыва может остаться старым навсегда.**

1. **Журнал изменений покрывает только карточки.** `task_changes` пишут триггеры по `tasks` и десяти дочерним таблицам. Таблицы `projects`, `labels`, `user_notes`, `journal_entries`, `task_schedules`, `attachments` в журнал не пишутся.
2. **Сокет эти правки покрывает, но только «в моменте».** `server/src/lib/realtimeInvalidation.ts` шлёт `project:changed`, `label:changed`, `note:changed`, `schedule:changed`, `attachment:changed`; iOS их обрабатывает (`Sources/Core/Realtime/RealtimeEvent.swift:215`). Событие, случившееся в разрыв сокета, до телефона не приходит никогда.
3. **Догон при переподключении неполон.** `Sources/App/TaskFlowApp.swift:206-225` перечитывает карточки (дельтой), непрочитанные уведомления, проекты и метки. Заметки, рутины, вложения и дневник не перечитываются.
4. **У сокета нет номера события.** В `server/src/ws.ts` нет сквозного `seq` и нет replay: догон пропущенного через сокет невозможен. Единственный работающий путь — HTTP по курсору, и он покрывает только карточки.
5. **Карта «напоминание Apple ↔ задача» лежит только в телефоне** (`UserDefaults`, `Sources/Features/Settings/AppleEventKitAccess.swift:97-109`) — переустановка её убивает.

По эталонной заметке (разделы 3.4 и 4.2-А) это риск «А. Неполнота журнала».

### 2.1. Уточнения, найденные при повторной сверке кода 02.11.2026

Первая версия решения (сформулирована по разбору 01.11) недооценивала объём: часть выводов требовала локальных таблиц и точечных маршрутов, которых в коде нет. Проверено по коду сервера (`main` на `c8c22c79`) и клиента (`main` на `83fab963`, мак онлайн 02.11).

**У1. Правка заметки не порождает событие вообще.** Сервер следит за таблицей `notes` (`server/src/lib/realtimeInvalidation.ts:61`), а заметки лежат в `user_notes` (`server/src/routes/notes.ts`: «имя notes занято заброшенной таблицей»). Таблица `notes` — заброшенная, в ней одна строка `main`. Значит правка заметки не доезжает до телефона даже «в моменте»: не событием, не дельтой, а только ручным обновлением экрана. Это отдельный и самый заметный пользовательский дефект — он первым идёт в реализацию.

**У2. Локальной базы для этих сущностей на телефоне нет.** `taskflow.sqlite` содержит только `chat`, `message`, `task`, `notification`, `sync_state` (`Sources/Core/Store/LocalDatabase.swift`: `create(table:)` — пять таблиц). Проекты, метки, рутины и заметки клиент держит в памяти (`ProjectStore`, `LabelStore` — `@Observable`) и берёт из сети по событию `realtime.entityRevision`. Значит «применить дельту одной транзакцией в локальную базу» применимо только к карточкам и переписке; для остальных типов локальной копии не существует, и заводить её в этой карточке — отдельная работа (D14).

**У3. Точечных маршрутов «сущность по id» для большинства типов нет.** Есть `GET /api/projects`, `GET /api/labels` (`routes/projects.ts:699`), `GET /api/schedules` (`routes/schedules.ts:94`), `GET /api/notes` (список с превью, без контента — `routes/notes.ts:52`), но точечных `GET /api/projects/:id`, `GET /api/labels/:id` нет. У вложений есть только `GET /api/attachments/:id` (скачивание файла) и нет списка.

Из У1–У3 следуют поправки к решению: дельта отдаёт **идентификаторы**, а не тела (D6), а клиент для типов без локальной копии **перечитывает дешёвый список целиком** (D8), вместо того чтобы заводить под них локальные таблицы.

## 3. Техническое решение

### 3.1. Источник правды — HTTP-дельта по курсору, сокет — только сигнал

**D1.** Источник правды синхронизации — журнал на сервере + чтение по курсору. События сокета ускоряют обновление, но пропуск события не ведёт к рассинхрону. Это осознанный отказ от replay-сокета (Discord-подход с `seq`/`Resume`): он требует серверного буфера и нового формата событий при том же результате, который даёт дельта.

### 3.2. Один журнал на все сущности, один формат дельты

**D2.** Заводится общий журнал `sync_changes` по образцу `task_changes`: `seq` (монотонный), `entity_type`, `entity_id`, `changed_at`, `deleted`, поля видимости. Триггеры — на `projects`, `labels`, `user_notes`, `journal_entries`, `task_schedules`, `attachments`. Карточки в новый журнал не переносятся: у них уже есть `task_changes` с посчитанной видимостью.

**D3.** Единая точка чтения: `GET /api/sync/changes?since=<курсор>` возвращает по типам `changed_ids`/`removed_ids` и новый курсор. `GET /api/tasks/changes` не меняется и остаётся рабочим для старых клиентов.

**D4.** Курсор общего журнала — монотонный `seq`, а не время (эталон, S11 Notion: окна по времени дают пропуски и дубли). Временной курсор журнала карточек остаётся как есть.

**D5.** Обратная совместимость: сервер принимает и новый формат `s:<seq>`, и старый временной; клиент хранит оба раздельно и двигает в одной транзакции с телами.

### 3.3. Что отдаёт дельта по типам

**D6.** Дельта отдаёт **идентификаторы и признак удаления**, а не тела — как в эталоне (S4, Linear: дельта отдаёт id и тип изменения, а не готовые тяжёлые объекты). Тела добирает клиент тем маршрутом, который для типа уже есть:

| Тип | Что отдаёт дельта | Как клиент добирает тело |
|---|---|---|
| `tasks` | `changed_ids` / `removed_ids` | батчем `POST /api/tasks/batch` — так уже сделано и проверено |
| `projects`, `labels` | `changed_ids` / `removed_ids` | перечитывание списка `GET /api/projects`, `GET /api/labels` — списки маленькие, точечных маршрутов по id нет (У3) |
| `task_schedules` | `changed_ids` / `removed_ids` | перечитывание списка `GET /api/schedules` |
| `user_notes` | `changed_ids` / `removed_ids` | перечитывание списка `GET /api/notes` — он уже отдаёт превью без TipTap-контента |
| `attachments` | не в объёме | у вложений нет списка, и они приезжают вместе с карточкой (`GET /api/attachments/:id` — только скачивание). Отдельная дельта по вложениям — лишняя работа |

Для `projects`, `labels`, `task_schedules`, `user_notes` клиент после дельты перечитывает список целиком: списки маленькие, а отдельных точечных маршрутов нет — это дешевле, чем городить точечные GET. Это не отступление от эталона: эталон требует, чтобы догон был по всем сущностям экрана, а не чтобы дельта несла тела.

**D7.** Удаление едет тем же потоком, что и правка: `removed_ids` → удаление строки в локальной базе. Клиент не «угадывает» удаление по отсутствию сущности в списке.

### 3.4. Клиент

**D8.** Правило транзакционности разделяется по наличию локальной копии (У2):
- **Есть локальная таблица** (`tasks`, и переписка): тела и новый курсор пишутся **одной транзакцией**; курсор не двигается, пока тела не записаны. Это правило уже сделано и проверено для карточек (`TaskSyncCachePolicy.canAdvanceCursor`).
- **Локальной копии нет** (`projects`, `labels`, `task_schedules`, `user_notes`): курсор двигается **только после успешной перечитки списка**; неудачная перечитка — курсор на месте, дыра закрывается следующим проходом. Правило «курсор после данных» то же, способ хранения — другой.

**D9.** Догон после разрыва покрывает все типы, а не только карточки. Сейчас `TaskFlowApp.onReconnected` перечитывает карточки, непрочитанные уведомления, проекты и метки — но **не** рутины и не заметки. Дополнить: после переподключения перечитываются рутины (`GET /api/schedules`) и заметки (`GET /api/notes`). Это главный пользовательский дефект.

**D10.** Применение идемпотентно (upsert по id), при конфликте версий побеждает серверное `updated_at`.

**D11.** Локальная база остаётся источником отрисовки; старт — «сначала база, потом сеть». Это уже так.

### 3.5. Что в этой карточке не делаем

**D12.** Перенос карты «напоминание Apple ↔ задача» на сервер — вне объёма карточки (отдельная подсистема, риск регрессий в обе стороны). Решение зафиксировано: серверная таблица по образцу `task_external_mappings`.

**D13.** Политика размера и вытеснения локальной базы (`taskflow.sqlite`: `chat`, `message`, `task`, `notification`, `sync_state`) — отдельная работа; в эталоне готового правила нет. Фиксируем требование: задать порог и порядок вытеснения.

**D14.** Локальный офлайн-кэш проектов, меток, рутин и заметок (таблицы в `taskflow.sqlite`) — **вне объёма этой карточки**. Сейчас эти сущности живут в памяти клиента и в офлайне не показываются вовсе. Заведение локальных таблиц — отдельная работа с собственной политикой размера; здесь правило одно: догон чинит рассинхрон, а не добавляет офлайн-режим.

**D15.** В первый состав работ входит правка У1: сервер должен следить за `user_notes` (и `journal_folders`), а не за заброшенной `notes`. Без этого событие по заметкам не появится даже после починки догоня.

## 4. Риски

| # | Риск | Как страхуем |
|---|---|---|
| R1 | Новый формат курсора ломает сохранённые курсоры | Сервер принимает оба формата; старый маршрут не меняется; `sync_state` расширяем, а не переписываем |
| R2 | Журнал растёт без границ | 7 дней и обрезка по числу строк — как в `pruneTaskChanges` |
| R3 | Утечка чужих приватных данных в дельте | Видимость фильтруется на сервере до выдачи (`owner_id`, `is_private`) |
| R4 | Каскадное удаление теряется в дельте | Триггеры пишут tombstone по каждой удалённой записи |
| R5 | Дельта по заметкам раздувает трафик | Контент не едет в дельте |
| R6 | Событие и дельта в разном порядке | Применение идемпотентно, источник правды — дельта |
| R7 | Правка одного текста с двух устройств | «Последний по серверному времени»; для пользовательского текста вопрос открыт, решение нужно от владельца |
| R8 | Локальные часы телефона врут | Курсор выдаёт сервер |
| R9 | iOS-код — только на маке, сервер — на .110 | Правила вынесены в чистый файл без БД и сети — тестируются на macOS без симулятора |
| R10 | Физический iPhone может быть офлайн | Критерий «сценарий пройден вживую» не закрывается — фиксируется как ограничение |
| R11 | Новые триггеры ломают существующие маршруты | Триггеры только на новых таблицах; `task_changes` не трогаем; тесты на изолированной копии базы |
| R12 | Слежение за `user_notes` вместо `notes` (У1) меняет поведение живых экранов | Замена точечная: одна строка в списке `watched`; правка заметок начинает слать событие — ожидаемое изменение, а не регрессия; проверяется на изолированной копии базы |
| R13 | Перечитывание списка при догоне дороже точечного GET (У3) | Списки маленькие (проекты, метки, рутины) и заметки отдаются превью; лишние запросы исключены тем, что перечитывание идёт один раз на тип, а не на сущность |

## 5. Интерфейсы (для этапа реализации)

**Сервер — `New-Todoist` (.110):**

- `GET /api/sync/changes?since=<курсор>` → `{ server_time, cursor, full, entities: { projects: {changed_ids, removed_ids}, labels: {...}, schedules: {...}, notes: {...} } }`; `full: true` — курсор вне окна хранения.
- Таблица `sync_changes` + триггеры на `projects`, `labels`, `task_schedules`, `user_notes`; обрезка по сроку и числу строк; видимость — на сервере.
- Правка У1: в списке `watched` (`server/src/lib/realtimeInvalidation.ts`) вместо `notes` — `user_notes` (+ `journal_folders`).

**Клиент — `TaskFlowNativeBuild` (мак):**

- Расширение `sync_state`: курсоры по типам.
- Для карточек — применение дельты одной транзакцией с курсором (правило уже есть в `TaskSyncCachePolicy`).
- Для проектов, меток, рутин, заметок — перечитывание списка; курсор двигается только после успешной перечитки.
- `TaskFlowApp.swift`: догон по всем типам, включая рутины и заметки (D9).
- Правила — в отдельном чистом файле (без БД и сети).

**Проверки реализации:** серверные тесты (журнал пишется, дельта отдаёт id, `full` при старом курсоре, чужие приватные данные не выдаются); клиентские тесты правил (курсор не двигается при неполном применении, удаление едет тем же потоком); сборка iOS на маке; живой сценарий на телефоне — отдельный этап.

## 6. Границы приёмки

1. Правка рутины, заметки, проекта или метки на сервере во время разрыва связи доезжает до телефона после восстановления сети без перезапуска приложения и без ручного обновления экрана.
1a. Правка заметки, сделанная на сервере при живом сокете, доезжает до экрана заметок без ручного обновления (У1: события по заметкам не было вообще).
2. Удалённая на сервере рутина или заметка исчезает с телефона тем же проходом.
3. Курсор не двигается, если часть дельты не применилась, — дыра закрывается следующим проходом.
4. Чужие приватные проекты и метки в дельту не попадают.
