Правка первых трёх дефектов уже в `main` обоих репозиториев, отдельная работа по ним не нужна:

| Дефект (был) | Как закрыт | Где |

## 2. Какая дырка осталась (суть задачи)

**Догон после разрыва связи есть только для карточек. Всё остальное, что показывает телефон, после разрыва может остаться старым навсегда.**

1. **Журнал изменений покрывает только карточки.** `task_changes` пишут триггеры по `tasks` и десяти дочерним таблицам. Таблицы `projects`, `labels`, `user_notes`, `journal_entries`, `task_schedules`, `attachments` в журнал не пишутся.
2. **Сокет эти правки покрывает, но только «в моменте».** `server/src/lib/realtimeInvalidation.ts` шлёт `project:changed`, `label:changed`, `note:changed`, `schedule:changed`, `attachment:changed`; iOS их обрабатывает (`Sources/Core/Realtime/RealtimeEvent.swift:215`). Событие, случившееся в разрыв сокета, до телефона не приходит никогда.
3. **Догон при переподключении неполон.** `Sources/App/TaskFlowApp.swift:206-225` перечитывает карточки (дельтой), непрочитанные уведомления, проекты и метки. Заметки, рутины, вложения и дневник не перечитываются.
4. **У сокета нет номера события.** В `server/src/ws.ts` нет сквозного `seq` и нет replay: догон пропущенного через сокет невозможен. Единственный работающий путь — HTTP по курсору, и он покрывает только карточки.
5. **Карта «напоминание Apple ↔ задача» лежит только в телефоне** (`UserDefaults`, `Sources/Features/Settings/AppleEventKitAccess.swift:97-109`) — переустановка её убивает.

По эталонной заметке (разделы 3.4 и 4.2-А) это риск «А. Неполнота журнала».

## 3. Техническое решение

### 3.1. Источник правды — HTTP-дельта по курсору, сокет — только сигнал

**D1.** Источник правды синхронизации — журнал на сервере + чтение по курсору. События сокета ускоряют обновление, но пропуск события не ведёт к рассинхрону. Это осознанный отказ от replay-сокета (Discord-подход с `seq`/`Resume`): он требует серверного буфера и нового формата событий при том же результате, который даёт дельта.

### 3.2. Один журнал на все сущности, один формат дельты

**D2.** Заводится общий журнал `sync_changes` по образцу `task_changes`: `seq` (монотонный), `entity_type`, `entity_id`, `changed_at`, `deleted`, поля видимости. Триггеры — на `projects`, `labels`, `user_notes`, `journal_entries`, `task_schedules`, `attachments`. Карточки в новый журнал не переносятся: у них уже есть `task_changes` с посчитанной видимостью.

**D3.** Единая точка чтения: `GET /api/sync/changes?since=<курсор>` возвращает по типам `changed_ids`/`removed_ids` и новый курсор. `GET /api/tasks/changes` не меняется и остаётся рабочим для старых клиентов.

**D4.** Курсор общего журнала — монотонный `seq`, а не время (эталон, S11 Notion: окна по времени дают пропуски и дубли). Временной курсор журнала карточек остаётся как есть.

**D5.** Обратная совместимость: сервер принимает и новый формат `s:<seq>`, и старый временной; клиент хранит оба раздельно и двигает в одной транзакции с телами.

### 3.3. Что отдаёт дельта по типам

**D6.** Форма по типу выбирается по объёму и наличию «точечного» маршрута:

| Тип | Что отдаёт дельта | Почему |
|---|---|---|
| `tasks` | `changed_ids`/`removed_ids`, тела — батчем `POST /api/tasks/batch` | так уже сделано и проверено |
| `projects`, `labels`, `task_schedules` | готовые строки целиком | списки маленькие, GET по id нет — дельта дешевле лишнего запроса |
| `user_notes`, `journal_entries` | `id` + `updated_at` + превью; контент — по `GET /api/notes/:id` | контент — TipTap-JSON, тянуть его в дельте нельзя |
| `attachments` | метаданные; содержимое — по `GET /api/attachments/:id` | файлы не хранятся в дельте |

**D7.** Удаление едет тем же потоком, что и правка: `removed_ids` → удаление строки в локальной базе. Клиент не «угадывает» удаление по отсутствию сущности в списке.

### 3.4. Клиент

**D8.** Применение дельты по всем типам — одной транзакцией: тела + новые курсоры.

**D9.** Догон после разрыва покрывает все типы, а не только карточки: `TaskFlowApp.swift` перечитывает также заметки, рутины и вложения. Сейчас это главный пользовательский дефект.

**D10.** Применение идемпотентно (upsert по id), при конфликте версий побеждает серверное `updated_at`.

**D11.** Локальная база остаётся источником отрисовки; старт — «сначала база, потом сеть». Это уже так.

### 3.5. Что в этой карточке не делаем

**D12.** Перенос карты «напоминание Apple ↔ задача» на сервер — вне объёма карточки (отдельная подсистема, риск регрессий в обе стороны). Решение зафиксировано: серверная таблица по образцу `task_external_mappings`.

**D13.** Политика размера и вытеснения локальной базы (`taskflow.sqlite`: `chat`, `message`, `task`, `notification`, `sync_state`) — отдельная работа; в эталоне готового правила нет. Фиксируем требование: задать порог и порядок вытеснения.

## 4. Риски

| # | Риск | Как страхуем |
|---|---|---|
| R1 | Новый формат курсора ломает сохранённые курсоры | Сервер принимает оба формата; старый маршрут не меняется; `sync_state` расширяем, а не переписываем |
| R2 | Журнал растёт без границ | 7 дней и обрезка по числу строк — как в `pruneTaskChanges` |
| R3 | Утечка чужих приватных данных в дельте | Видимость фильтруется на сервере до выдачи (`owner_id`, `is_private`) |
| R4 | Каскадное удаление теряется в дельте | Триггеры пишут tombstone по каждой удалённой записи |
| R5 | Дельта по заметкам раздувает трафик | Контент не едет в дельте |
| R6 | Событие и дельта в разном порядке | Применение идемпотентно, источник правды — дельта |
| R7 | Правка одного текста с двух устройств | «Последний по серверному времени»; для пользовательского текста вопрос открыт, решение нужно от владельца |
| R8 | Локальные часы телефона врут | Курсор выдаёт сервер |
| R9 | iOS-код — только на маке, сервер — на .110 | Правила вынесены в чистый файл без БД и сети — тестируются на macOS без симулятора |
| R10 | Физический iPhone может быть офлайн | Критерий «сценарий пройден вживую» не закрывается — фиксируется как ограничение |
| R11 | Новые триггеры ломают существующие маршруты | Триггеры только на новых таблицах; `task_changes` не трогаем; тесты на изолированной копии базы |

## 5. Интерфейсы (для этапа реализации)

**Сервер — `New-Todoist` (.110):**

- `GET /api/sync/changes?since=<курсор>` → `{ server_time, cursor, full, entities: { projects: {changed_ids, removed_ids, rows?}, labels: {...}, notes: {...}, schedules: {...}, attachments: {...} } }`; `full: true` — курсор вне окна хранения.
- Таблица `sync_changes` + триггеры на шесть таблиц; обрезка по сроку и числу строк; видимость — на сервере.

**Клиент — `TaskFlowNativeBuild` (мак):**

- Расширение `sync_state`: курсоры по типам.
- Применение дельты по всем типам одной транзакцией; курсор — только после применения.
- `TaskFlowApp.swift`: догон по всем типам (D9).
- Правила — в отдельном чистом файле (без БД и сети).

**Проверки реализации:** серверные тесты (журнал пишется, дельта отдаёт id, `full` при старом курсоре, чужие приватные данные не выдаются); клиентские тесты правил (курсор не двигается при неполном применении, удаление едет тем же потоком); сборка iOS на маке; живой сценарий на телефоне — отдельный этап.

## 6. Границы приёмки

1. Правка рутины, заметки, проекта или метки на сервере во время разрыва связи доезжает до телефона после восстановления сети без перезапуска приложения и без ручного обновления экрана.
2. Удалённая на сервере рутина или заметка исчезает с телефона тем же проходом.
3. Курсор не двигается, если часть дельты не применилась, — дыра закрывается следующим проходом.
4. Чужие приватные проекты и метки в дельту не попадают.
