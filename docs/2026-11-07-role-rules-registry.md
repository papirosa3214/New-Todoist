# Реестр правил ролей

Решение владельца 06.11.2026: единый реестр правил — канон инструкции роли.
Документ описывает, как реестр устроен, как в него добавлять правила и как
отдать правило одной роли. Составлен 07.11.2026.

## Что это

`server/scripts/role-rules.json` — массив правил. На 07.11.2026 в нём 607
правил: от одной фразы до строки списка. Рядом лежит `role-rules.md` — та же
таблица для чтения (длинные правила обрезаны до 400 знаков); правится только
JSON, `.md` — производная.

Путь можно переопределить переменной `TASKFLOW_ROLE_RULES` (нужно тестам и
нестандартным раскладкам).

## Как собирается инструкция роли

1. `loadRoleRules()` — `server/src/lib/roleRules.ts:49`. Читает файл и держит
   кеш по mtime и размеру: правка подхватывается без рестарта сервера.
2. `rulesFor(role, channel)` — `:64`. Отбирает правила (фильтры ниже) и
   сортирует: блоки категорий в порядке `INCLUDED_CATEGORIES`, внутри
   категории — порядок файла.
3. `renderRules()` — `:78`. Склеивает текст. Заголовки строятся из
   `sources[0].section`: «A > B > C» превращается в `#`, `##`, `###`.
   Подставляет `{{IDENTITY}}`, `{{FOLDER}}`, `{{BLOCKS}}`.
4. `registryInstructionText()` — `server/src/runtime/roleRegistryPrompt.ts:23`.
   Добавляет строку о грамматическом роде и пишет журнал сборки в
   `role_rules_log`: роль, канал, хэш, id правил, длина, число сборок.

## Поля правила

| Поле | Обязательное | Что делает |
| --- | --- | --- |
| `id` | да | Идентификатор (`R001`). На него ссылаются тесты и `ids` составов |
| `text` | да | Текст правила. Строка списка начинается с `- ` |
| `kind` | да | `rule` — обычное правило; `data` — только подстановка `{{...}}`; `character` — характер; `compose` — состав шаблона из кода |
| `category` | да | Блок инструкции. В сборку идут только категории из `INCLUDED_CATEGORIES` |
| `roles` | да | `"all"` или список ключей ролей (`["builder"]`) |
| `channels` | нет | `chat`, `card`, `voice`. Если не задано — выводится из `where` |
| `where` | нет | Человеческое «где действует»; из него выводятся каналы |
| `enabled` | нет | `false` выключает правило из сборки |
| `disabled_reason` | нет | Почему выключено |
| `sources` | нет | Откуда правило взято. `section` задаёт заголовки, `file`/`line` — трассировка |
| `condition`, `site`, `ids`, `data_part` | нет | Только для правил «из кода» (ниже) |

Категории, которые попадают в инструкцию (`INCLUDED_CATEGORIES`):
«общий шаблон v2», «общий шаблон», «личные инструкции», «характер»,
«новое 06.11.2026». Остальные в сборку не идут.

## Какие правила попадают в инструкцию

Правило проходит, если выполнено всё:

- `enabled` не `false`;
- категория входит в `INCLUDED_CATEGORIES` (или это строка-подстановка `data`);
- `kind: "data"` допускается только как чистая подстановка `{{NAME}}`;
- `roles` равно `"all"` или содержит ключ роли;
- `channels` содержит канал сборки.

Канал — `chat`, `card` или `voice`. Он определяется видом хода: чат, карточка,
голосовой ввод. Одно правило может действовать в нескольких каналах.

## Правила «из кода»

Часть текста исторически жила в коде (`instructionDefaults.ts`, `agentState.ts`
и др.). Она заведена в реестр категорией «из кода» с полями:

- `condition` — условие применения (например, `defaults:task.start`);
- `site` — место в коде;
- `kind: "compose"` + `ids` — состав шаблона этого места: порядок строк, часть
  из которых общая для нескольких шаблонов;
- `data_part` — данные, которые остаются подстановкой в шаблоне.

Код берёт такой текст через `registryText(condition, role, site)`
(`roleRules.ts:127`), а не литералом. Если строк в реестре нет — работает
прежний литерал из кода (`registryTextOr`).

## Как добавить правило

1. Дописать объект в конец `role-rules.json` (в конец категории — так он встанет
   в конец блока).
2. Указать `sources[0].section` — иначе правило попадёт в текст без заголовка.
3. Проверить сборку (ниже).

Пример правила для всех ролей в чате и карточке:

```json
{
  "id": "R608",
  "text": "- Ответ на уточнение — одной фразой.",
  "kind": "rule",
  "category": "общий шаблон",
  "roles": "all",
  "channels": ["chat", "card"],
  "sources": [{ "file": "server/scripts/role-rules.json", "line": 1, "section": "Лаконичность" }]
}
```

## Как отдать правило одной роли или выключить

- Одной роли: `"roles": ["builder"]` вместо `"all"`.
- Группе: перечислить ключи — `["builder", "qa"]`.
- Выключить всем: `"enabled": false` и `"disabled_reason": "..."`. Удалять
  правило не обязательно — выключенное сохраняет трассировку и историю.

## Как проверить

- Сборка: `npx vitest run test/roleRegistryPrompt.test.ts
  test/roleRegistryChannels.test.ts test/roleRegistryCode.test.ts --maxWorkers=4`.
- Журнал фактических сборок: `sqlite3 db.sqlite "select role, channel, uses,
  text_len, last_at from role_rules_log order by last_at desc limit 10;"`.
  По нему видно, какие правила реально ушли в модель и в каком объёме.

## Выключатель

Настройка `role_registry_enabled` (по умолчанию `true`), окружение —
`TASKFLOW_SETTING_ROLE_REGISTRY_ENABLED=false`. При `false` сборка идёт
прежним путём: `SYSTEM.md` роли (из `server/scripts/role-system-prompt.md`) +
`AGENTS.md` роли + строка о роде.

## Статус прежнего канона

`server/scripts/role-system-prompt.md` при включённом реестре инструкцию не
формирует. Он остаётся в двух ролях:

- запасной путь при `role_registry_enabled=false`;
- слой `role.system` в приложении — экран «Общие инструкции агентов»
  (`Sources/Features/Roles/AgentsScreen.swift:77`, редактор
  `RoleInstructionEditor.swift`).

Важное следствие: правки в экране «Общие инструкции агентов» до модели сейчас
не доходят — инструкция собирается из реестра. Либо экран переводится на
реестр, либо канон и экран убираются вместе.
